# EDF (Earliest Deadline First) — планирование по дедлайну

[🇬🇧 English version](edf.md) · [← Каталог моделей](../models.ru.md)

**Простыми словами:** у каждой заявки свой дедлайн (жёсткое обещание доставки, SLO,
real-time-ограничение); как только сервер освобождается, он выбирает ОЖИДАЮЩУЮ заявку с ближайшим
дедлайном, а не первую пришедшую (FCFS) и не заявку из фиксированного высокоприоритетного класса
([статические](priority.md)/[динамические](priority-dynamic.md) приоритеты). Это отличается от
[SLA-слоя](sla.md) (EPIC-021): тот слой считает вероятность нарушения дедлайна ПОВЕРХ уже
зафиксированной дисциплиной картины ожидания — он никогда не меняет, кого обслужат следующим.
Здесь дедлайн И ЕСТЬ правило планирования.

### Почему нет точного калькулятора

Все родственные страницы каталога дают точный теоретический калькулятор, кросс-проверенный против
DES. EDF — намеренное исключение: точный конечномерный/closed-form анализ EDF остаётся открытой
задачей даже для простейшего 2-классового M/M/1-случая — подтверждено и литературой (только
heavy-traffic/fluid-результаты, напр. Panwar & Towsley, 2001), и тремя гипотезами о «неожиданном
сведении», которые были проверены и численно ОПРОВЕРГНУТЫ здесь: экспоненциальные дедлайны НЕ
эквивалентны случайному порядку обслуживания (SIRO); «гонка» экспоненциальных часов по классам НЕ
сводит EDF к простой Марковской цепи уровней `(n1,n2)`; классический закон сохранения работы НЕ
выполняется точно при заметном reneging (потере заявок по дедлайну). См.
[`docs/research/edf-scheduling-2026.md`](../research/edf-scheduling-2026.md) для полных численных
доказательств — зафиксировано, чтобы никто не переоткрывал (и не переопровергал) те же гипотезы
снова.

### Дисциплина EDF (симуляция, точна по построению)

**Описание:** `K` классов делят один сервер; абсолютный дедлайн заявки фиксируется при приходе
(`время_прихода + D`, `D` — из любого поддерживаемого распределения на класс, детерминированного
или случайного); освободившийся сервер берёт ожидающую заявку с наименьшим абсолютным дедлайном;
заявка, чей дедлайн наступил раньше начала обслуживания, покидает систему необслуженной
(reneging). Сама дисциплина симулируется точно (без приближений в том, ЧТО происходит) —
приближены только аналитические проверки ниже.

**Симуляция:** `EDFQueueSim` (`most_queue.sim.edf`)

```python
from most_queue.sim.edf import EDFQueueSim

sim = EDFQueueSim(n_classes=2, seed=42)
sim.set_sources([{"type": "M", "params": 0.4}, {"type": "M", "params": 0.4}])
sim.set_servers([{"type": "M", "params": 1.0}, {"type": "M", "params": 1.0}])
sim.set_deadlines([{"type": "M", "params": 0.3}, {"type": "M", "params": 0.6}])  # средний дедлайн 1/theta на класс
res = sim.run(300_000)
# res.w[k], res.v[k] -- моменты ожидания/пребывания ОБСЛУЖЕННЫХ заявок класса k
# res.miss_prob[k] -- доля заявок класса k, не успевших к дедлайну (не обслужены)
```

Параметр `discipline="fcfs"` даёт честную FCFS-с-reneging базовую линию для сравнения (та же
логика прихода/обслуживания/reneging, меняется только правило выбора) — используется, чтобы
подтвердить, что EDF снижает суммарную долю пропусков дедлайна относительно FCFS на тех же
параметрах.

### Композиция с SLA-слоем (EPIC-021)

Для ДЕТЕРМИНИРОВАННОГО дедлайна на класс `most_queue.theory.utils.sla.deadline_violation_prob`,
применённая к моментам ожидания ОБСЛУЖЕННЫХ заявок, даёт содержательную (хоть и приближённую,
fit-based) проверку согласованности: реальное ожидание обслуженной заявки по построению не
превышает её дедлайн, поэтому подогнанная `P(W > D)` должна получаться малой (не строго нулевой,
поскольку гладкая H2/Gamma-подгонка не знает о жёстком обрезании):

```python
from most_queue.theory.utils.sla import deadline_violation_prob

p = deadline_violation_prob(res.w[0], deadline=3.0)  # должна быть малой
```

### Точность и охват

Дисциплина точна по построению (DES). **Закон сохранения работы**
(`Σ_k ρ_k·E[W_k] = ρ·E0/(1-ρ)`) точен только при пренебрежимо редком reneging (проверено:
сходится к нему по мере уменьшения вероятности пропуска дедлайна) — используется как
regression-тест только в режиме редкого reneging, а не как общая кросс-проверка. Точной
per-class формулы среднего/распределения ожидания не предоставляется; см.
[`docs/roadmaps/edf_scheduling_roadmap.md`](../roadmaps/edf_scheduling_roadmap.md) §7 для резерва
(ближайшая опубликованная точная трактовка 2-классового случая — «delayed accumulating priority
queue» Mojalal, Stanford, Taylor & Ziedins, но её формулы платно недоступны/основаны на рядах, пока
не перенесены сюда).
