# Системы с пакетным поступлением

[🇬🇧 English version](batch.md) · [← Каталог моделей](../models.ru.md)

![Схема пакетного поступления](../figures/batch.ru.png)

**Простыми словами:** заявки приходят не по одной, а пачками случайного размера — автобус
с туристами, пакет транзакций, batch задач от планировщика. Даже при той же средней
интенсивности пачечность заметно удлиняет очередь: пришедшие вместе вынуждены ждать друг
друга.

### Mˣ/M/1

**Описание:** Система, где заявки поступают пакетами случайного размера.

**Класс расчета:** `BatchMM1`

**Пример:**

```python
from most_queue.theory.batch.mm1 import BatchMM1

calc = BatchMM1()
# Вероятности размеров пакетов: [p(1), p(2), p(3), ...]
batch_probs = [0.2, 0.3, 0.1, 0.2, 0.2]
calc.set_sources(l=0.5, batch_probs=batch_probs)
calc.set_servers(mu=1.0)
results = calc.run()
```

### M/M^[a,b]/1 — групповое (пакетное) обслуживание

**Описание:** Сервер обслуживает заявки **пакетами**: стартует, когда в очереди накопилось не менее
`a`, берёт до `b` заявок и обслуживает весь пакет за одно экспоненциальное время. Базовая модель для
**батчинга запросов в LLM-инференсе** — интенсивность обслуживания пакета может зависеть от его
размера (больший пакет медленнее на пакет, но амортизирует фиксированную стоимость по запросам,
поэтому есть оптимальный максимальный размер пакета). Решается точной CTMC над (пакет-в-обслуживании,
число ожидающих).

**Класс расчета:** `BulkServiceMM1Calc` (`most_queue.theory.batch.bulk_service`) ·
**Симулятор:** `BulkServiceSim` (`most_queue.sim.bulk_service`)

**Пример:**

```python
from most_queue.theory.batch.bulk_service import BulkServiceMM1Calc

calc = BulkServiceMM1Calc(a=1, b=8)   # обслуживать до 8 за раз
calc.set_sources(2.0)
calc.set_servers(lambda size: 1.0 / (0.3 + 0.08 * size))  # LLM: время пакета растёт с размером
results = calc.run()  # results.v[0] среднее пребывание, results.w[0] среднее ожидание
```

### Точные моменты времени ожидания (не только среднее)

**Описание:** `run()`.`w` раньше давал грубую оценку только среднего (`E[V] - 1/mu(фикс. размер)`,
неточную, когда размер пакета реально варьируется, т.е. при `a<b`). `get_w(num=4)` даёт **точные**
моменты времени ожидания через PASTA: приходящий клиент застаёт стационарное состояние
(пакет-в-обслуживании, число ожидающих); если сервер занят, ожидание = оставшееся время текущего
пакета (`Exp(mu(i))`, без памяти) + время на все ПОЛНЫЕ пакеты размера `b` впереди —
гипоэкспоненциальное распределение. `run()` теперь автоматически использует этот точный результат
при `a=1` (типичный случай для GPU/LLM dynamic batching — там нет минимального порога пакета, см.
[`docs/research/bulk-service-waiting-moments-2026.md`](../research/bulk-service-waiting-moments-2026.md)
для целевой литературы по GPU-инференсу). `get_n_moments(num=4)` даёт точные моменты числа в
системе для ЛЮБЫХ `a`, `b` — тривиально, прямое суммирование по уже решённому стационарному
распределению.

```python
calc = BulkServiceMM1Calc(a=1, b=8)          # a=1 нужно для точных моментов W
calc.set_sources(2.0)
calc.set_servers(lambda size: 1.0 / (0.3 + 0.08 * size))
w_moments = calc.get_w(num=4)                 # E[W], E[W^2], E[W^3], E[W^4] -- точно
n_moments = calc.get_n_moments(num=4)         # E[N], E[N^2], ... -- точно при любых a, b
```

**Граница точности:** `get_w()` кидает `ValueError` при `a>1` — вывод предполагает, что пакет
`min(b, остаток)` формируется сразу, как только сервер освобождается, что верно только при `a=1`;
при `a>1` сервер может уйти в простой в ожидании дозаполнения порога после неполного остатка, что
ломает простую декомпозицию (проверено численно: ~18% ошибка при `a=2` до введения этого
ограничения). `run()` сохраняет старую приближённую оценку среднего при `a>1`, теперь явно
помеченную как приближение. Моменты времени пребывания (`V`) выше среднего не предоставляются даже
при `a=1` — итоговый размер собственного пакета помеченного клиента зависит от приходов во время
его собственного ожидания, коррелирован с `W`, поэтому `V ≠ W + S` простой свёрткой (см. раздел
«резерв» research-доки).

**См. также:** [SLA / вероятность нарушения дедлайна](sla.ru.md) — превратить эти моменты в вероятность нарушения дедлайна или SLO-квантиль.
