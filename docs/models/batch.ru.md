# Системы с пакетным поступлением

[🇬🇧 English version](batch.md) · [← Каталог моделей](../models.ru.md)

![Схема пакетного поступления](../figures/batch.ru.png)

**Простыми словами:** заявки приходят не по одной, а пачками случайного размера — автобус
с туристами, пакет транзакций, batch задач от планировщика. Даже при той же средней
интенсивности пачечность заметно удлиняет очередь: пришедшие вместе вынуждены ждать друг
друга.

### Mˣ/M/1

**Описание:** Система, где заявки поступают пакетами случайного размера.

**Класс расчета:** `BatchMM1`

**Пример:**

```python
from most_queue.theory.batch.mm1 import BatchMM1

calc = BatchMM1()
# Вероятности размеров пакетов: [p(1), p(2), p(3), ...]
batch_probs = [0.2, 0.3, 0.1, 0.2, 0.2]
calc.set_sources(l=0.5, batch_probs=batch_probs)
calc.set_servers(mu=1.0)
results = calc.run()
```

### M/M^[a,b]/1 — групповое (пакетное) обслуживание

**Описание:** Сервер обслуживает заявки **пакетами**: стартует, когда в очереди накопилось не менее
`a`, берёт до `b` заявок и обслуживает весь пакет за одно экспоненциальное время. Базовая модель для
**батчинга запросов в LLM-инференсе** — интенсивность обслуживания пакета может зависеть от его
размера (больший пакет медленнее на пакет, но амортизирует фиксированную стоимость по запросам,
поэтому есть оптимальный максимальный размер пакета). Решается точной CTMC над (пакет-в-обслуживании,
число ожидающих).

**Класс расчета:** `BulkServiceMM1Calc` (`most_queue.theory.batch.bulk_service`) ·
**Симулятор:** `BulkServiceSim` (`most_queue.sim.bulk_service`)

**Пример:**

```python
from most_queue.theory.batch.bulk_service import BulkServiceMM1Calc

calc = BulkServiceMM1Calc(a=1, b=8)   # обслуживать до 8 за раз
calc.set_sources(2.0)
calc.set_servers(lambda size: 1.0 / (0.3 + 0.08 * size))  # LLM: время пакета растёт с размером
results = calc.run()  # results.v[0] среднее пребывание, results.w[0] среднее ожидание
```

### Точные моменты времени ожидания (не только среднее)

**Описание:** `run()`.`w` раньше давал грубую оценку только среднего (`E[V] - 1/mu(фикс. размер)`,
неточную, когда размер пакета реально варьируется, т.е. при `a<b`). `get_w(num=4)` даёт **точные**
моменты времени ожидания через PASTA: приходящий клиент застаёт стационарное состояние
(пакет-в-обслуживании, число ожидающих); если сервер занят, ожидание = оставшееся время текущего
пакета (`Exp(mu(i))`, без памяти) + время на все ПОЛНЫЕ пакеты размера `b` впереди —
гипоэкспоненциальное распределение (а если остаток после них ниже порога `a` — ГОНКА между новыми
приходами и оставшимся обслуживанием, см. ниже). `run()` использует этот точный результат
автоматически при ЛЮБОМ `1<=a<=b` (EPIC-067 снял прежнее ограничение `a=1`, см.
[`docs/epics/EPIC-067-bulk-service-idle-refill.md`](../epics/EPIC-067-bulk-service-idle-refill.md)).
`get_n_moments(num=4)` даёт точные моменты числа в системе для ЛЮБЫХ `a`, `b` — тривиально, прямое
суммирование по уже решённому стационарному распределению.

```python
calc = BulkServiceMM1Calc(a=1, b=8)          # подойдёт любой 1 <= a <= b (EPIC-067)
calc.set_sources(2.0)
calc.set_servers(lambda size: 1.0 / (0.3 + 0.08 * size))
w_moments = calc.get_w(num=4)                 # E[W], E[W^2], E[W^3], E[W^4] -- точно
n_moments = calc.get_n_moments(num=4)         # E[N], E[N^2], ... -- точно при любых a, b
p_violation = calc.get_tail(3.0)              # P(W > 3.0) -- ТОЧНО, не подгонка (EPIC-066)
```

**Граница точности:** при `a>1`, если остаток после полных батчей впереди ниже порога `a`,
собственный пакет помеченного клиента не может начаться сразу, как только отработают батчи
впереди. Наивное решение (ещё одна последовательная Erlang-фаза рефилла, в предположении, что
новых приходов во время обслуживания батчей впереди не случается) было численно опровергнуто
(~18% ошибка при `a=2`) ещё до того, как `get_w()`/`get_tail()` были ограничены случаем `a=1`.
EPIC-067 вывел и провалидировал корректную конструкцию — гонку между новыми приходами по Пуассону
и оставшейся последовательностью фаз обслуживания — полностью снимающую ограничение;
`get_w()`/`get_tail()`/`run()` теперь точны при любых `1<=a<=b`. Моменты времени пребывания (`V`)
выше среднего по-прежнему не предоставляются — итоговый размер собственного пакета помеченного
клиента зависит от приходов во время его собственного ожидания, коррелирован с `W`, поэтому
`V ≠ W + S` простой свёрткой (см. раздел «резерв» research-доки).

### Общее (Erlang-подогнанное) время обслуживания батча

**Описание:** `BulkServiceMM1Calc` выше предполагает **экспоненциальное** время обслуживания
батча. Этот раздел закрывает резерв для **общего** распределения — подогнанного к
Erlang(`k`, `rate`) фазовому представлению по моментам (та же конвенция подгонки, что и по всей
библиотеке: `MaxDistribution`, SLA-слой). Erlang естественно представляет низкий CV (`≤1`) времени
обслуживания батча — реалистичный режим для GPU/LLM-батчинга, где время обработки батча довольно
предсказуемо, а не сильно изменчиво. Состояние CTMC получает дополнительное фазовое измерение:
`(размер батча i, Erlang-фаза p, ожидающие j)`. При `k=1` (Erlang сводится к экспоненте) результат
ТОЧНО совпадает с `BulkServiceMM1Calc` — основная регрессионная проверка.

**Найденная и исправленная ошибка размерности:** ставка перехода между фазами сначала была
установлена как `k*rate` (в расчёте на «суммарную ставку по k фазам»), что на самом деле даёт
суммарное среднее `1/rate` вместо корректного `k/rate` — ошибка в `k²` раз. Случайно всё ещё
проходила регрессию на `k=1` (`k*rate=rate` при k=1), но резко разошлась с независимой DES при
`k=3` — поймано до фиксации вывода. См.
[`docs/research/bulk-service-general-erlang-2026.md`](../research/bulk-service-general-erlang-2026.md)
для полного отчёта, включая почему классический embedded-chain/PGF метод (Neuts 1975,
Chaudhry-Templeton) был отложен в пользу этого более безопасного, фазового подхода.

**Класс расчёта:** `BulkServiceErlangCalc` (`most_queue.theory.batch.bulk_service_erlang`)

```python
from most_queue.theory.batch.bulk_service_erlang import BulkServiceErlangCalc

calc = BulkServiceErlangCalc(a=1, b=4, k=3)   # Erlang(3, rate): CV = 1/sqrt(3)
calc.set_sources(1.0)
calc.set_servers(rate=1.5)                     # среднее обслуживание батча = k/rate = 2.0
res = calc.run()                                # res.v[0] среднее; res.w -- точные моменты, любое a (см. ниже)

# точные моменты W (не только среднее), любое 1 <= a <= b:
w_moments = calc.get_w(num=4)                   # [E[W], E[W^2], E[W^3], E[W^4]]

# либо подогнать (k, rate) напрямую по моментам:
calc2 = BulkServiceErlangCalc(a=1, b=4, k=1)   # k будет переписан подгонкой
calc2.set_sources(1.0)
calc2.set_servers_from_moments([2.0, 4.5])     # [среднее, E[S^2]] времени обслуживания батча

# rate может быть и callable rate(размер_батча) -- k (число фаз) остаётся фиксированным,
# меняется только ставка на фазу в зависимости от размера обслуживаемого батча:
calc3 = BulkServiceErlangCalc(a=1, b=4, k=3)
calc3.set_sources(1.0)
calc3.set_servers(lambda size: 3.0 + 0.2 * size)  # большие батчи медленнее на фазу (LLM/GPU-стиль)
```

**Точность и охват:** точно при заданном Erlang-подогнанном семействе, при любых `1<=a<=b`
(EPIC-067). `get_w()` даёт ТОЧНЫЕ моменты `W` (EPIC-043, перенос PASTA/гипоэкспоненциальной
техники EPIC-032 на этот фазовый случай — оставшееся обслуживание батча, застанного прибывающим в
процессе, это `Erlang(k-p, rate)`, где `p` — застанная фаза, плюс `j//b` полных батчей впереди,
каждый `Erlang(k, rate(b))`, свёрнутые, плюс фаза гонки-рефилла, если остаток не дотягивает до
порога `a`); `run()` использует это точное среднее при любом `a`.
`get_tail(D)`/`get_cdf(D)` (EPIC-066) дают ТОЧНУЮ вероятность нарушения SLA `P(W>D)` тоже при
любом `a` — матричная экспонента на том же phase-type разложении, точная регрессия к
`BulkServiceMM1Calc.get_tail` при `k=1`; см.
[точный хвост batch-service](../research/batch-service-sla-exact-tail-results-2026.md). Не
покрыто (резерв): batch-size-зависимое ЧИСЛО ФАЗ (`k`) — EPIC-042 перенёс
callable-ставку экспоненциальной модели на этот фазовый случай, но `k` остаётся фиксированным по
всем размерам батча (заметно более сложное расширение, тот же класс сложности, что и
per-server число фаз в EPIC-041).

### Общее (H2-подогнанное) время обслуживания батча (CV ≥ 1)

**Описание:** комплементарный Erlang-случаю выше режим CV`≥1` — время обслуживания батча,
подогнанное к H2(`p1`,`mu1`,`mu2`) (гиперэкспоненциальная смесь из двух фаз) представлению по
моментам, для более изменчивого, чем экспоненциальное, времени обслуживания батча. В отличие от
Erlang (последовательная цепочка фаз), H2 — это «ветвление»: в момент старта обслуживания батча
одна из двух экспоненциальных фаз выбирается один раз (фаза 0 с вероятностью `p1`, ставка `mu1`;
фаза 1 с вероятностью `p2=1-p1`, ставка `mu2`), и батч остаётся в этой фазе до завершения — без
переключений фазы в середине обслуживания. Состояние CTMC получает дополнительное фазовое
измерение: `(размер батча i, фаза ∈ {0,1}, ожидающие j)`; каждый переход «батч стартует»
расщепляется на две взвешенные подставки (`×p1`, `×p2`) вместо единственного детерминированного
перехода у Erlang. При `p1=1` (H2 сводится к `Exp(mu1)`) результат ТОЧНО совпадает с
`BulkServiceMM1Calc` — основная регрессионная проверка, подтверждена до полной точности float64.
В отличие от Erlang-случая, общий (действительно двухфазный) случай совпал с независимой DES с
первой попытки — ошибок не найдено, вероятно потому что «выбор фазы один раз при старте» структурно
проще корректно закодировать, чем последовательное продвижение фазы у Erlang. См.
[`docs/research/bulk-service-general-h2-2026.md`](../research/bulk-service-general-h2-2026.md) для
полного отчёта.

**Класс расчёта:** `BulkServiceH2Calc` (`most_queue.theory.batch.bulk_service_h2`)

```python
from most_queue.theory.batch.bulk_service_h2 import BulkServiceH2Calc

calc = BulkServiceH2Calc(a=1, b=4)
calc.set_sources(1.0)
calc.set_servers(p1=0.5, mu1=1.0, mu2=3.0)     # среднее обслуживание батча = p1/mu1 + p2/mu2
res = calc.run()                                # res.v[0], res.w[0] -- только среднее (см. ниже)

# либо подогнать (p1, mu1, mu2) напрямую по моментам:
calc2 = BulkServiceH2Calc(a=1, b=4)
calc2.set_sources(1.0)
calc2.set_servers_from_moments([2.0, 12.0, 100.0])   # [среднее, E[S^2], E[S^3]], CV >= 1

# p1/mu1/mu2 могут быть callable f(размер_батча) -- структура из двух ветвей остаётся
# фиксированной, меняется только вероятность/ставки ветвей в зависимости от размера НОВОГО батча:
calc3 = BulkServiceH2Calc(a=1, b=4)
calc3.set_sources(1.0)
calc3.set_servers(lambda size: 0.3 + 0.1 * size, mu1=1.5, mu2=3.0)
```

**Точность и охват:** точно при заданном H2-подогнанном семействе (только среднее через `run()`;
точных `get_w()` для H2 нет, в отличие от Erlang/MM1 — отдельный резерв, не связанный с `a`).
`get_tail(D)`/`get_cdf(D)` (EPIC-066, обобщено на любые `1<=a<=b` в EPIC-067) дают ТОЧНУЮ
`P(W>D)`: именно здесь этот случай сложнее Erlang — каждый полный батч ВПЕРЕДИ заново независимо
выбирает свою H2-фазу (настоящее ветвление, не последовательное продвижение фазы Erlang), поэтому
phase-type подгенератор строится явно, а не переиспользует простую двухдиагональную цепь (а
гонка-рефилл, если нужна, ветвится только на ПОСЛЕДНЕМ слое перед батчем помеченного клиента);
точная регрессия к `BulkServiceMM1Calc.get_tail` при `p1=1`. См.
[точный хвост batch-service](../research/batch-service-sla-exact-tail-results-2026.md). Не
покрыто (резерв): точные МОМЕНТЫ выше среднего (нужен другой PASTA-аргумент, который также
отслеживает, в какой фазе прибывающий застаёт батч — не то же самое, что вывод для хвоста);
batch-size-зависимое ЧИСЛО ВЕТВЕЙ (структура из двух ветвей сама остаётся фиксированной — EPIC-042
сделал batch-size-зависимыми только вероятность/ставки на ветвь).

### Нетерпеливые заявки (abandonment / impatience)

**Описание:** марковское (безpамятное) терпение — каждый из `j` ожидающих клиентов
независимо уходит (`reneging`) со ставкой `gamma` (та же конвенция, что
`most_queue.theory.impatience.mm1.MM1Impatience`). Передаётся параметром `gamma` в
конструктор `BulkServiceMM1Calc`/`BulkServiceErlangCalc`/`BulkServiceH2Calc`
(`gamma=0.0` по умолчанию — поведение не меняется). При `gamma>0`:

- `get_abandonment_prob()` (MM1, Erlang) — точная вероятность, что ПОМЕЧЕННЫЙ
  клиент, приходящий по PASTA, уйдёт по терпению до начала своего батча.
- `get_w()`/`get_tail()` (MM1, Erlang) переключаются на вариант УСЛОВНЫЙ на «дождался»
  (нормировка на `1 - get_abandonment_prob()`); безусловная картина требует обе
  величины вместе.
- `BulkServiceH2Calc` ([EPIC-071](../epics/EPIC-071-bulk-service-h2-impatience.md))
  также поддерживает `get_abandonment_prob()` и условные (на «дождался»)
  `get_w()`/`get_tail()` при `gamma>0`, через отдельную H2-ветвящуюся конструкцию
  (`_h2_abandonment_chain`): в отличие от последовательной фазовой цепи MM1/Erlang,
  каждый батч впереди помеченной заявки заново выбирает свою ветвь при старте,
  поэтому цепь несёт 3 сегмента на пару `(R,K)` — «first» (уже наблюдаемый батч,
  его фаза уже известна по PASTA — ветвления там нет) и «ahead»-ветка-0/ветка-1
  (каждая зацикливается сама на себя) — вместо числа фаз, растущего с количеством
  батчей впереди. При `gamma==0` `get_w()` всё ещё поднимает `NotImplementedError`
  — точные моменты без нетерпения остаются отдельным, не связанным резервом (см.
  раздел «Общий случай (Erlang/H₂)» выше).

**Почему наивная гипотеза не сработала:** количество клиентов впереди помеченного
(`R`) при наличии abandonment — само процесс смерти (каждый из `R` уходит
независимо), идущий ОДНОВРЕМЕННО с формированием батчей, а не фиксированная
величина, как в чисто race-конструкции EPIC-067 без abandonment. Простая гипотеза
«race-цепь EPIC-067 + отдельный конкурирующий gamma-выход» давала ошибку 17–38% на
разных состояниях. Корректная конструкция (`most_queue.theory.batch._idle_refill.
abandonment_chain`) добавляет `R` и `K` (новые приходы позади помеченного) как
состояния; см. [EPIC-068](../epics/EPIC-068-bulk-service-impatience.md) для полного
вывода, включая реальную ошибку (фактор `(-A)^-1` в формуле момента), пойманную
DES-тестом до поставки.

```python
from most_queue.theory.batch.bulk_service import BulkServiceMM1Calc

calc = BulkServiceMM1Calc(a=2, b=4, gamma=0.4)   # ставка терпения
calc.set_sources(0.6)
calc.set_servers(1.5)

p_abandon = calc.get_abandonment_prob()   # точная вероятность ухода до начала батча
w_given_served = calc.get_w(num=1)[0]     # E[W | дождался]
```

H2 работает так же (при `p1=1` точно сводится к результату MM1 выше):

```python
from most_queue.theory.batch.bulk_service_h2 import BulkServiceH2Calc

calc = BulkServiceH2Calc(a=2, b=4, gamma=0.4)
calc.set_sources(0.6)
calc.set_servers(p1=0.3, mu1=0.9, mu2=2.5)

p_abandon = calc.get_abandonment_prob()
w_given_served = calc.get_w(num=1)[0]
```

### M/M^[a,b]/c — несколько независимых серверов с общей очередью

**Описание:** `c` ИДЕНТИЧНЫХ серверов обслуживают батчи из ОДНОЙ общей FCFS-очереди — прямая модель
пула из нескольких GPU-реплик (каждая со своим continuous-batching движком) за одним
роутером запросов. Когда хотя бы один сервер свободен, батч стартует мгновенно, как только
очередь дотягивает до `a`; когда все `c` заняты, очередь может вырасти, и освободившийся сервер
забирает до `b`.

**Класс расчёта:** `BulkServiceMultiserverCalc` (`most_queue.theory.batch.bulk_service_multiserver`)

```python
from most_queue.theory.batch.bulk_service_multiserver import BulkServiceMultiserverCalc

calc = BulkServiceMultiserverCalc(a=2, b=4, c=3)   # 3 сервера, общая очередь
calc.set_sources(1.0)
calc.set_servers(1.2)                               # на сервер; может быть callable(size)
res = calc.run()                                    # res.v[0], res.w[0]

n_moments = calc.get_n_moments(num=4)   # точно, любые a<=b, c, включая batch-size-зависимый mu
w_moments = calc.get_w(num=4)           # точно -- ТОЛЬКО batch-size-НЕЗАВИСИМый mu
p_violation = calc.get_tail(3.0)        # P(W > 3.0) -- точно, та же оговорка
```

**Точность и охват:** `get_n_moments()` — точно при любых `a<=b`, `c>=1`, включая batch-size-
зависимый `mu(size)`. `get_w()`/`get_tail()` — точно, но только при batch-size-независимом `mu`
(иначе `NotImplementedError`): ключевая находка — при постоянном `mu` агрегированная ставка
«следующее освобождение» среди всех `c` занятых серверов всегда ровно `c·mu`, независимо от того,
какие размеры батчей они сейчас обслуживают, поэтому ожидание помеченного клиента не требует
отслеживать вектор занятости — конструкция переиспользует «ahead»-сегмент цепи из
[EPIC-068](../epics/EPIC-068-bulk-service-impatience.md) при нулевом терпении. При
batch-size-зависимом `mu` агрегированная ставка действительно зависит от полного вектора
занятости — настоящий взрыв размерности состояния, резерв (не реализовано). `c=1` — точная
регрессия к `BulkServiceMM1Calc`. См.
[EPIC-069](../epics/EPIC-069-bulk-service-multiserver.md) для полного вывода.

**Нетерпеливые заявки ([EPIC-070](../epics/EPIC-070-bulk-service-multiserver-impatience.md)):**
параметр `gamma` (ставка терпения, конвенция `MM1Impatience`) даёт `get_abandonment_prob()` и
условные (на «дождался») `get_w()`/`get_tail()` — только при batch-size-независимом `mu`. Эта
комбинация не потребовала новой конструкции: та же «агрегированная ставка `c·mu`» сводит задачу
к уже готовому `abandonment_chain` из EPIC-068, который изначально поддерживает `gamma>0`.

```python
calc = BulkServiceMultiserverCalc(a=2, b=4, c=3, gamma=0.3)
calc.set_sources(1.0)
calc.set_servers(0.5)
p_abandon = calc.get_abandonment_prob()   # точная вероятность ухода до начала батча
w_given_served = calc.get_w(num=1)[0]     # E[W | дождался]
```

### Auto-dispatch (не считать CV вручную)

**Описание:** `fit_bulk_service_calc(a, b, moments, family="auto")`
(`most_queue.theory.batch.bulk_service_general`) сам выбирает между двумя калькуляторами выше по
CV переданных моментов — `cv ≤ 1` → `BulkServiceErlangCalc`, `cv > 1` → `BulkServiceH2Calc` — по
аналогии с конвенцией `theory.utils.sla.fit_from_moments(family="auto")`. Возвращает калькулятор
с уже применённым `set_servers()` по моментам; вызывающий код всё ещё должен вызвать
`set_sources()`, затем `run()`. Явные `family="erlang"`/`"h2"` проверяют CV-совместимость и кидают
`ValueError` вместо того, чтобы молча вернуть неверную подгонку.

```python
from most_queue.theory.batch.bulk_service_general import fit_bulk_service_calc

calc = fit_bulk_service_calc(a=1, b=4, moments=[2.0, 4.5])        # cv < 1 -> Erlang
calc = fit_bulk_service_calc(a=1, b=4, moments=[2.0, 12.0, 100.0])  # cv > 1 -> H2 (нужно 3 момента)
calc.set_sources(1.0)
res = calc.run()
```

**См. также:** [SLA / вероятность нарушения дедлайна](sla.ru.md) — превратить эти моменты в вероятность нарушения дедлайна или SLO-квантиль.
