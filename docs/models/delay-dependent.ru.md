# Интенсивность обслуживания, зависящая от испытанного ожидания

[🇬🇧 English version](delay-dependent.md) · [← Каталог моделей](../models.ru.md)

**Своими словами:** классическая теория очередей предполагает, что длительность обслуживания
никак не связана с тем, сколько заявка перед этим прождала. Измерения говорят обратное. В
клинике пациент, принятый с задержкой, лежит дольше («slowdown»); в рознице покупатель,
простоявший в очереди дольше, покупает больше; оператор при заторе может как ускоряться, так и
затягивать. В этой модели интенсивность обслуживания зависит от **собственного** испытанного
ожидания заявки — не от длины очереди, не от текущей загрузки и не от уже отработанного времени
обслуживания (эти зависимости в библиотеке уже есть).

Практическое следствие резкое: если планировать ёмкость по обычной M/M/c, а эффект замедления
присутствует, задержка будет занижена, причём ошибка растёт ровно там, где она опаснее всего. В
первоисточнике показано, что `E[W]` теряет даже **выпуклость** по `λ` — чего обычная M/M/c
принципиально не может, — поэтому экстраполировать подогнанную классическую модель здесь нельзя.

### M/M/c с порогом по ожиданию — точное решение

**Описание:** пуассоновский вход интенсивности `λ`, `c` одинаковых приборов, дисциплина FCFS,
неограниченный накопитель. Заявка, чьё ожидание не превысило порог `k`, обслуживается с
интенсивностью `μ₁`; заявка, прождавшая дольше, — с интенсивностью `μ₂`. Случай `μ₂ < μ₁` —
замедление, `μ₂ > μ₁` — ускорение, `μ₁ = μ₂` — обычная M/M/c.

Условие стационарности определяется **только** `μ₂`: `λ < c·μ₂`. Как бы ни была велика `μ₁`,
достаточно длинная очередь выводит за порог каждую заявку, поэтому `μ₁` не спасает перегруженную
систему.

```python
from most_queue.theory.delay_dependent import MMcDelayDependentServiceCalc

calc = MMcDelayDependentServiceCalc(c=3, k=5.0)   # порог по испытанному ожиданию
calc.set_sources(l=2.0)
calc.set_servers(mu1=0.8, mu2=0.7)                # замедление: ожидание удлиняет обслуживание

calc.get_w()[0]            # точное E[W]
calc.get_p0_wait()         # P(W = 0) — застала свободный прибор
calc.get_cdf(3.0)          # точное P(W <= 3)
calc.get_tail(10.0)        # точное P(W > 10) — вероятность нарушения дедлайна
calc.get_pdf(3.0)          # точная плотность
calc.get_class1_prob()     # P(W <= k): доля заявок, обслуженных с интенсивностью mu1
calc.get_v()[0]            # E[V] = E[W] + E[S]
calc.get_server_state_probs()   # pi(i, j): состояния нулевого ожидания по составу приборов
```

**Метод.** Реализация работы D'Auria B., Adan I.J.B.F., Bekker R., Kulkarni V., *An M/M/c queue
with queueing-time dependent service rates*, European Journal of Operational Research
299(2):566–579, 2022,
[doi:10.1016/j.ejor.2021.12.023](https://doi.org/10.1016/j.ejor.2021.12.023) (препринт
[arXiv:2107.04557](https://arxiv.org/abs/2107.04557)). **Модель и её решение принадлежат
авторам**; вклад библиотеки — реализация, написанная по статье. Авторы опубликовали и свой код,
он не использовался.

Состояние — **виртуальное время ожидания** `W(t)` (заявка, пришедшая в момент `t`, начинает
обслуживаться в `t + W(t)`) вместе с **состоянием приборов** `S(t) = (S₁, S₂)` — сколько приборов
будет занято заявками класса 1 и класса 2 в момент начала нового обслуживания. Именно вторая
компонента делает процесс марковским: сам по себе `W` таковым не является, поскольку скорость его
убывания зависит от того, заявки каких классов обслуживаются. Пока `W(t) > 0`, заняты все приборы,
поэтому `S₁ + S₂ = c-1` и остаётся ровно `c` фаз.

Уравнения равновесия дают интегро-дифференциальные уравнения, которые приводятся к двум системам
линейных ОДУ второго порядка с постоянными коэффициентами — одна ниже порога, другая выше, —
связанным условиями непрерывности в точке `k`. Их решение — **смесь матричных экспонент**, а все
неизвестные постоянные сворачиваются рекурсией по граничным состояниям к одной скалярной
величине, которая определяется условием нормировки.

**Два вычислительных момента, которые стоит знать** (оба обнаружены при реализации, в статье не
оговорены):

- Одна из матриц, интеграл от которой нужен для среднего, **всегда** вырождена: в спектре
  неизбежно есть `min(0, λ - c·μ₁)` в одной группе и `max(0, λ - c·μ₁)` в другой, так что при
  `λ ≠ c·μ₁` нулевое собственное значение попадает в одну из них. Сам интеграл конечен; вырождена
  только его факторизованная запись. Здесь он считается через экспоненту расширенной матрицы, без
  обращения.
- На поверхности `μ₂ = μ₁ + λ/c` частное решение выше порога входит в резонанс с однородной модой
  и всё представление вырождается. Замечание 2 статьи перечисляет несколько вырожденных случаев,
  но этого среди них нет, хотя он виден в их же формуле для `c = 1`, где `μ₂ - μ₁ - λ` стоит в
  знаменателе. Калькулятор распознаёт этот случай и сообщает о нём; достаточно немного изменить
  одну из интенсивностей — **сама модель** там ведёт себя совершенно нормально, не работает лишь
  данное её представление.

**Проверка.** Три аналитических эталона, ни под один из которых реализацию нельзя было подогнать:
вырождение к формуле Эрланга-C при `μ₁ = μ₂` (совпадение до `1e-16` при `c = 1…5`), замкнутая
форма самой статьи для `c = 1` (плотность до `3e-16`) и опубликованный в статье пример при
`c = 2`, воспроизведённый до каждого напечатанного знака `π(0,0)`, `π(0,1)`, `π(1,0)`. Плюс
независимая имитационная модель для случаев ускорения, замедления и одноканального
([`MMcDelayDependentServiceSim`](../../most_queue/sim/delay_dependent.py)).

| Сверка с имитацией (12 прогонов) | отклонение `E[W]` |
|---|---|
| `c=2`, собственный пример статьи (ускорение) | +0.10σ |
| `c=3`, сильное ускорение `μ₁=0.3, μ₂=0.8` | −0.44σ |
| `c=1`, замедление | +0.11σ |

Полные цифры, включая контрольный опыт, объясняющий, почему самый тяжёлый случай (`ρ = 0.95`)
проверяется по распределению, а не по среднему, — в
[EPIC-076](../epics/EPIC-076-mmc-delay-dependent-service.md).

### Во что обходится игнорирование этой зависимости

Подгоняем обычную M/M/c под **то же реализованное среднее время обслуживания** (самое
благоприятное, что может сделать практик) и сравниваем с точным ответом; `c = 3`, `k = 5`,
`μ₁ = 0.8`, `μ₂ = 0.7`:

| λ | точное `E[W]` | классическая подгонка | отношение | точное `P(W>20)` | классическое `P(W>20)` |
|---|---|---|---|---|---|
| 1.0 | 0.111 | 0.111 | 1.00 | 0.00000 | 0.00000 |
| 1.8 | 1.134 | 0.986 | 1.15 | 0.00050 | 0.00000 |
| 2.0 | 4.796 | 2.421 | **1.98** | 0.05835 | 0.00147 |
| 2.05 | 12.355 | 4.209 | **2.94** | 0.22037 | 0.01566 (**в 14 раз меньше**) |

При малой загрузке ошибка незаметна, а взрывается ровно там, где принимаются решения о ёмкости.
Хуже обстоит дело именно с вероятностью нарушения дедлайна — а против неё обычно и пишется SLO.

Кроме того, при малой `μ₁` величина `E[W]` перестаёт быть выпуклой по `λ`: вторые разности `E[W]`
на сетке `λ = 0.8…2.0` отрицательны при `μ₁ = 0.3` и положительны при `μ₁ = 0.9`. Любая процедура
подбора ёмкости, опирающаяся на выпуклость (а таких большинство), в этом режиме неприменима.

### Смежные модели библиотеки

- [SLA / вероятность нарушения дедлайна](sla.ru.md) — `P(W > D)` по моментам, для любой модели.
  Здесь хвост точный, подгонка не нужна.
- [Admission control по дедлайну](admission-control.ru.md) — **другой** механизм: отклонение при
  приходе вместо изменения интенсивности обслуживания.
- [Occupancy-зависимый continuous batching](continuous-batching.ru.md) — интенсивность зависит от
  текущей занятости, а не от собственного ожидания заявки.
- [Системы с нетерпеливыми заявками](impatience.ru.md) — ожидание заставляет заявку **уйти**, а не
  меняет длительность её обслуживания.
