# Multiserver-job системы (MSJ)

[🇬🇧 English version](msj.md) · [← Каталог моделей](../models.ru.md)

![Схема multiserver-job](../figures/msj.ru.png)

**Простыми словами:** в современных ЦОД и GPU-кластерах одна заявка часто занимает **несколько
серверов одновременно** (ядра, GPU) на всё время работы — в отличие от классического M/M/c, где
заявка занимает один сервер. Заявка ждёт, пока освободится достаточно серверов сразу. Модель
«multiserver-job» позволяет исследовать совместное влияние длительности, фрагментации
ресурсов и дисциплины на задержки.

### FCFS MSJ — точное время отклика (малые системы)

**Описание:** k серверов; у каждого класса — **потребность в серверах** (сколько занимает
одновременно) и экспоненциальная интенсивность. FCFS с блокировкой головы очереди: старшие заявки
жадно заполняют серверы, первая не влезающая останавливает просмотр. Точное среднее время отклика
(общее и по классам) через CTMC над последовательностью заявок по порядку прихода — для малых k /
немногих классов / умеренной загрузки.

**Класс расчета:** `MsjExactCalc` (`most_queue.theory.msj`) ·
**Симулятор:** `MsjSim` (`most_queue.sim.msj`)

```python
from most_queue.theory.msj import MsjExactCalc, MsjClass

calc = MsjExactCalc(k=2, classes=[MsjClass(0.4, 1, 1.0), MsjClass(0.2, 2, 1.0)])
r = calc.run()          # r.v[0] общее среднее пребывание; r.v_per_class по классам
```

### Saturated MSJ — пропускная способность и порог устойчивости

**Описание:** Область устойчивости MSJ-системы характеризуется её *насыщенной* (всегда с бэклогом)
версией. `MsjSaturatedCalc` точно решает насыщенную CTMC и возвращает пропускную способность
`X_sat` — **максимальную суммарную интенсивность входа**, которую открытая система выдерживает: она
устойчива тогда и только тогда, когда Λ < X_sat. Воспроизводит product-form результаты устойчивости
Grosof, Harchol-Balter, Scheller-Wolf.

**Класс расчета:** `MsjSaturatedCalc` (`most_queue.theory.msj`)

```python
from most_queue.theory.msj import MsjSaturatedCalc, MsjClass

sat = MsjSaturatedCalc(k=2, classes=[MsjClass(1.0, 1, 1.0), MsjClass(1.0, 2, 1.0)])
x_sat = sat.run()       # макс. суммарная интенсивность входа (микс классов — из соотношения rates)
```

### PH-обслуживание: FCFS в малых системах

**Простыми словами:** длительность заявки может состоять из нескольких стадий или
быть смесью коротких и длинных работ. На протяжении обслуживания она удерживает все
нужные серверы. Голова очереди блокирует следующие заявки, пока сама не поместится.

```python
from most_queue.random.map_ph import PHDistribution
from most_queue.random.utils.params import Cox2Params, ErlangParams
from most_queue.theory.msj import MsjPHCalc

services = [
    PHDistribution.from_erlang(ErlangParams(r=2, mu=2.0)),
    PHDistribution.from_cox(Cox2Params(mu1=2.0, mu2=1.5, p1=0.75)),
]
calc = MsjPHCalc(k=2, truncation=10, max_states=50000)
calc.set_sources([0.25, 0.15])
calc.set_servers([1, 2], services)
r = calc.run()
print(r.w_per_class, r.v_per_class, r.boundary_mass, r.stability_threshold)
```

`truncation` ограничивает общее число заявок; на границе вход блокируется. Решение
точно для этой конечной модели, а не бесконечной очереди. Закон Литтла использует
принятую интенсивность. Увеличивайте усечение и сравнивайте результаты: граничная
масса сама по себе не является границей ошибки. `w`/`v` содержат только среднее.
`max_states` ограничивает размер обеих CTMC. PH должна быть действительной и
транзиентной; комплексные подгонки и автоматическая замена произвольного G не поддержаны.

`saturated_throughput()` рассчитывает насыщенный порог для данного FCFS-микса;
`run()` отклоняет вход выше/на пороге. Условия загрузки ресурсов ниже 100% недостаточно.
Порог FCFS не переносится на EASY. Старые MSJ-классы и их API сохранены.

### Общее обслуживание, одинаковые трассы и backfilling

**Простыми словами:** EASY допускает опережение короткими/помещающимися работами,
если это не сдвигает прогнозный старт первой ожидающей заявки. Резервируется только
голова, а не все заявки. Прерываний нет.

```python
from most_queue.sim.msj_general import MsjGeneralSim

source = MsjGeneralSim(2, seed=47)
source.set_sources([0.25, 0.15])
source.set_servers([1, 2], [(service, "PH") for service in services])
trace = source.make_trace(11000, estimates="oracle")
for policy in ("fcfs", "easy", "conservative"):
    sim = MsjGeneralSim(2, policy)
    sim.set_servers([1, 2])
    r = sim.run_trace(trace, warmup_jobs=1000)
    print(policy, r.v[0], r.v_quantiles[0.99], r.reservation_violations)
```

Генераторы — пары `(params, notation)` библиотеки либо функции `sampler(rng)`;
для replay достаточно потребностей в серверах. `estimates` — явный `"oracle"`,
список прогнозов по классам или `None` для FCFS. Для произвольных прогнозов/трасс
используйте `MsjTraceJob(arrival, cls, service, estimate)`.
Планировщик не читает будущую фактическую длительность. При превышении оценки работа
не уничтожается; новые backfill временно запрещены. Нарушения обещанного старта
считаются отдельно. При заниженных прогнозах гарантии резервирования нет.

`discipline="conservative"` резервирует старт каждой ожидающей заявки, а не только
головы. Новые заявки не сдвигают старые резервирования. При раннем завершении
календарь сжимается по одной заявке, сохраняя остальные резервирования; для стартов
предусмотрены отдельные события. Превышение прогноза делает календарь недействительным:
временно используется FCFS без нового backfill, после завершения просроченных работ
календарь строится заново. История лучших обещаний сохраняется.
`reserved_start_times` — словарь `индекс заявки в трассе → лучшее обещанное время`,
включая warm-up; это не полная история изменений календаря. `reservation_violations`
считает опоздания к этим обещаниям. Статические oracle и верхние оценки сервиса сохраняют
обещания, но не гарантируют меньший p99 относительно другой дисциплины.
Повторные обходы календаря дороги при больших очередях; это эталонный симулятор,
не оптимизированный промышленный планировщик. Порог FCFS не является порогом conservative.

`run(N)` измеряет N приходов после дополнительного warm-up; `run_trace` дожидается
завершения всей измеряемой когорты. Моменты и p95/p99 относятся к этой когорте, а
загрузка и простой при непустой очереди — к интервалу между первым измеряемым и
последним приходом, без финального дренирования. Для отсутствующего класса — NaN;
при нулевом временном интервале временные метрики — `None`. Счётчики backfill и
резервирований включают warm-up. Конечный прогон не доказывает стационарность или SLO.

Подробности: [методика EN](../msj_ph_methods.md),
[эксперимент](../../examples/msj_backfilling_experiment.py),
[EPIC-047](../epics/EPIC-047-msj-ph-backfilling.md).
Сравнение FCFS/EASY/conservative при одинаковой ресурсной нагрузке:
[пример](../../examples/msj_conservative_experiment.py),
[результаты EPIC-048](../research/msj-conservative-results-2026-10.md).

### Прогноз длительности по признакам

`LogLinearRuntimePredictor` из `most_queue.sim.utils.runtime_prediction` обучает
log-linear baseline на завершённых исторических работах: `fit(X, S)`.
`calibrate(X_cal, S_cal, coverage=0.95)` по отдельной выборке задаёт
односторонний split-conformal прогноз, `predict(X, upper=True)` возвращает его
без доступа к фактическому S будущей работы. Результат передаётся в
`MsjTraceJob.estimate`; EASY/conservative не изменены.

Признаки должны быть доступны до запуска, train/calibration/test — разделены.
Калибровка даёт marginal coverage при обменности наблюдений, а не гарантию каждой
заявки, каждого класса или p99 очереди. При недостатке calibration API сообщает
об отсутствии конечной границы, а не обрезает её. Возрастные прогнозы добавлены
отдельно в EPIC-051. Реальные трассы и сравнение expanding/recent истории
добавлены в EPIC-055–056; online drift-адаптация остаётся будущим этапом.
[Методика и пример EN](../msj_runtime_prediction.md),
[результаты EPIC-049](../research/msj-runtime-prediction-results-2026-10.md).

EPIC-050 добавляет `calibrate_by_group(X_cal, S_cal, groups)` и
`predict(X, upper=True, groups=groups)`: общая регрессия, отдельный порог для
каждого ресурсного класса, известного при поступлении. `group_calibrations`
показывает число наблюдений и доступность конечной границы. Для недостаточно
представленного или неизвестного класса прогноз явно отвергается, без подмены
общей оценкой. Покрытие по классу не гарантирует всех резервирований и теряет
основание при сдвиге закона внутри класса.
[API и ограничения EN](../msj_runtime_prediction.md#calibration-by-resource-group),
[результаты EPIC-050](../research/msj-group-calibration-results-2026-10.md).

### Остаток по возрасту и незавершённая история

`KaplanMeierRuntimeEstimator` из `most_queue.sim.utils.residual_runtime` принимает
`fit(min(S,C), completed)` с булевым индикатором завершения. При независимом
цензурировании внутри класса оценивает survival и остаток при условии S>a:
`remaining_quantile(age, probability=0.9)`, `remaining_mean(age, horizon=None)`.
Неидентифицированный хвост возвращает `None`, без экстраполяции или удаления работ.
Ограниченное среднее требует абсолютного горизонта H>a и отличается от полного.
Это plug-in прогноз, не conformal-гарантия покрытия.

`run_trace(..., remaining_predictor=callback)` и `run(..., remaining_predictor=callback)`
обновляют прогнозы активных работ EASY/conservative только по `(class, service_age)`
на существующих событиях. Удлинение прогноза сбрасывает текущий календарь,
но не прежние обещания; неизвестный остаток запрещает новый backfill, сохраняя
FCFS и дренирование. Начальные оценки ожидающих работ остаются обязательными.
Сброс календаря при расширении может нарушить старое обещание даже для верхней
оценки; гарантия статического резервирования на эту opt-in политику не переносится.
Счётчики `runtime_updates`, `unavailable_runtime_updates`, `forecast_calendar_resets`
включают warm-up; недоступность также включает остаток меньше точности timestamp.
[Пример и контракт EN](../msj_age_runtime.md),
[результаты и ограничения EPIC-051](../research/msj-age-runtime-results-2026-10.md).

### Упаковка без прогнозов и явное прерывание

FirstFit пропускает блокирующую голову ради помещающихся работ; MSF сначала
пробует широкие заявки. Quickswap временно закрывает допуск, чтобы освободить
серверы для широких работ. ServerFilling перепаковывает короткий FCFS-префикс,
прерывая и затем продолжая часть работ: это другой операционный режим.

`MsjGeneralSim(k, discipline=...)` принимает `first_fit`, `msf`, `msfq`,
`adaptive_quickswap`, `server_filling` без оценок длительности. Для MSFQ нужны
K∈{1,k}; keyword-only `msfq_threshold=0` задаёт ell, при нуле получается MSF.
ServerFilling поддерживает только степени двойки для k и K, preemptive-resume
с нулевой ценой прерывания. Это не restart и не ServerFilling-SRPT. Несовместимые
размеры отвергаются, а не округляются.

Для ServerFilling W включает все паузы, `start_times` остаётся первым стартом.
`service_segments` — интервалы `(id, start, end)`, `preemptions` и
`preemptions_per_job` — число прерываний всей трассы. У непрерывающих политик
новые массивы пустые. Packing не обещает резервирований и не принимает
`remaining_predictor`; прежние backfilling API и defaults сохранены.
[Точные правила и исполняемый пример EN](../msj_packing.md),
[эксперимент](../../examples/msj_packing_experiment.py),
[результаты и компромиссы EPIC-052](../research/msj-packing-results-2026-10.md).

### Цена checkpoint и resume

`MsjCheckpointSim(k, checkpoint_time=c, resume_time=r)` из
`most_queue.sim.msj_checkpoint` — отдельное расширение SF для степеней двойки.
Во время детерминированных checkpoint/resume работа удерживает K серверов, но
не продвигается; полезный прогресс сохраняется. Первый старт не платит r.
Пока активен хотя бы один overhead, новые прерывания не начинаются; выбранные
ожидающие работы всё же могут стартовать на свободных ресурсах. Это явное
модельное соглашение, не исходный SF и не эмуляция Slurm. При c=r=0 и нулевой защите используется
точно прежний zero-cost replay.

Доступны прежние `set_servers`, `set_sources`, `run`, `run_trace`.
`MsjCheckpointResults` раскладывает W на очередь/checkpoint/resume и первый
старт/последующие паузы, хранит три интервальных журнала и различает выделенную
и полезную загрузку. Дренирование конечной трассы не доказывает устойчивость.
[Пример, правила событий и метрик EN](../msj_checkpoint.md),
[эксперимент](../../examples/msj_checkpoint_experiment.py),
[результаты EPIC-053](../research/msj-checkpoint-results-2026-10.md).

### Минимальный полезный интервал между вытеснениями

Смысл дисциплины: дать запущенной или восстановленной работе выполнить хотя
бы q единиц полезного сервиса до следующего вытеснения. Это может уменьшить
overhead, но задержать другую работу, которой нужны те же серверы. Короткая
работа может закончиться раньше q; истечение защиты не требует переключения.

`MsjCheckpointSim(..., min_service_time=q)` принимает keyword-only
неотрицательную длительность. Часы защиты запускаются после окончания resume;
overhead и прошлые полезные интервалы не учитываются. Пересмотр по истечении
защиты происходит и без новых приходов. Прежние prefix/gate сохраняются,
q=0 точно оставляет модель EPIC-053. `protected_preemptions` — отклонённые
попытки «работа × событие», не число сэкономленных прерываний;
`protection_expirations` — сработавшие пересмотры. Метрики W/ресурсов прежние.

Эксперимент выбирает q=h(c+r) на независимых завершённых исторических трассах
и фиксирует h до тестовой выборки. Сохраняются все кандидаты; лучший training
score не выдаётся за гарантию улучшения. [Пример и контракт EN](../msj_protected_service.md),
[эксперимент](../../examples/msj_protected_service_experiment.py),
[результаты EPIC-054](../research/msj-protected-service-results-2026-10.md).

### Калибровка по исторической трассе

`parse_swf` из `most_queue.sim.utils.workload_trace` выделяет и аудирует
подвыборку завершённых жёстких заявок. `chronological_split` допускает в обучение
лишь исходы, известные до временной границы. `ServiceCalibration` предоставляет
эмпирический, Exp, PH и moment-lognormal варианты обслуживания.

Простыми словами: оценить длительности по прошлым завершённым работам и проверить,
сохраняются ли задержки и выбор дисциплины на последующих приходах. Arrival и
точные K общие; истинное S недоступно прогнозу. Историческое ожидание не задаёт
очередь симулятора. Отбор status=1 и отсутствие исходного backlog ограничивают
выводы об эксплуатации кластера. Нового планировщика или гарантии устойчивости нет.

См. [контракт и воспроизведение EN](../real_trace_calibration.md),
[эксперимент](../../examples/real_trace_calibration_experiment.py),
[результаты EPIC-055](../research/real-trace-calibration-results-2026-10.md).

### Давность истории и зависимое обслуживание

`ConditionalEmpirical` из `most_queue.random.trace_resampling` строит ECDF
точного K или грубой группы с явным fallback и условные midrank с учётом ties.
`circular_block_indices` переносит блоки рангов, но не исторические arrival/K.
Сравнение зависимого генератора — с rank-iid той же смеси рангов, не с uniform-iid.
Это инструменты генерации нагрузки, не новые дисциплины.

Простыми словами: в нескольких точках истории проверить, помогают ли более
свежие наблюдения, точные ресурсные классы и серии длинных/коротких работ
предсказать будущие задержки. Arrival/K и исторический прогноз одинаковы для
всех вариантов; тестовые S не участвуют в обучении или нормировке нагрузки.

1368 прогонов показали преимущество recent-coarse в агрегате, не в каждом периоде.
Уточнение K и более близкая автокорреляция не гарантируют лучших задержек или
p99-решений. Начальная очередь и отмены по-прежнему вне этого эксперимента.
[Методика EN](../real_trace_temporal.md),
[эксперимент](../../examples/real_trace_temporal_experiment.py),
[результаты EPIC-056](../research/real-trace-temporal-results-2026-10.md).

### Начальное состояние и отдельный учёт исходов

`MsjLifecycleSim.run_lifecycle` — отдельный opt-in API с прежними шестью
непрерывающими дисциплинами. `MsjCarryIn` задаёт уже работающие заявки и возраст;
начальные ожидающие сохраняют заданный порядок. `MsjLifecycleJob` различает
completed/cancelled и необязательный runtime limit от старта исполнения.
Обычный `MsjGeneralSim.run_trace` не изменён.

Простыми словами: запустить очередь с уже занятыми ресурсами, учесть конкуренцию
отменённых работ и различать, завершилась цель или была остановлена. Короткое
время до прекращения по лимиту не равно хорошему успешному обслуживанию.
Для начальных running в баланс входит лишь занятое время после границы replay.

Эксперимент использует частичный ретроспективный snapshot и наблюдаемое занятие
до отмены. Скрытый полный S, таймер отмены в очереди, приоритеты и память исходного
планировщика не восстанавливаются. Истинный остаток не передаётся прогнозу.
[Контракт и исполняемый пример EN](../real_trace_lifecycle.md),
[эксперимент](../../examples/real_trace_lifecycle_experiment.py),

### Аудит и калибровка современной GPU-нагрузки

`parse_acme_kalos` / `AcmeTrace` проверяют timezone-aware timestamps, сохраняют
целочисленный GPU request и аудит исключений. Исполнение — end-start, а не
поле duration, включающее ожидание. `acme_snapshot` задаёт частичное начальное
состояние. `MsjLifecycleJob` также сохраняет failed/node_failed и записанный
timed_out; последний не означает известного runtime budget.

Простыми словами: проверять длительности работ разработки LLM, не смешивая
успешное исполнение с временем до отмены/отказа. Неизвестные окончания и лимиты
не придумываются; запрос GPU не выдаётся за измеренную аппаратную загрузку.

В 1224 прогонах Kalos ошибки моделей велики, но при номинальной ёмкости пула
в контроле нет ожидания целей. Все шесть дисциплин равны: нулевой regret ничего
не доказывает об их ранжировании. Для этого нужны данные о квотах, размещении
и эффективной ёмкости. [Методика/API](../modern_gpu_trace.md),
[эксперимент](../../examples/modern_gpu_trace_experiment.py),
[результаты](../research/modern-gpu-trace-results-2026-10.md).

### Условное эмпирическое обслуживание

Простыми словами: приходы, запрос ресурса и признаки работы сохраняются.
Длительность берётся из завершённой истории с похожими K/type или requested time;
при редкой группе используется более широкая история. Отношение S/request
сохраняет связь длительности с бюджетом цели без обрезания превышений.
Меняется генератор нагрузки, не диспетчер; схема rigid jobs выше остаётся прежней.

`FeatureConditionalEmpirical` даёт exact/coarse context ECDF, аудит fallback и CRPS.
EPIC-059 выбирает модель по раннему validation до позднего replay. SDSC ratio
улучшает CRPS и timeout, но может ухудшить очередь и p99 policy choice;
type Kalos не переносится на поздний блок. Доступность type online не установлена.
[Методика/API](../feature_service.md), [эксперимент](../../examples/feature_service_experiment.py),
[результаты](../research/feature-service-results-2026-10.md).

### Общий GPU пул и эксклюзивные узлы

Простыми словами: работа резервирует либо requested GPU из общего пула, либо
все запрошенные узлы целиком. Те же приходы и длительности проверяются при
заданных размерах пула. Если работа или initial running set не помещаются,
вся ячейка невыполнима — работы не уменьшаются и не исключаются.

`ResourceRequest`, `assess_envelope`, `observed_occupancy` разделяют проекцию
ресурса, выполнимость replay и совместимость записанных execution-интервалов.
Схема rigid jobs выше не меняется, меняются scalar demand/capacity. Requested
GPU work учитывается отдельно от reserved GPU-equivalent work. Это sensitivity,
не оценка квот или восстановленного размещения на физических узлах.

[эксперимент](../../examples/gpu_resource_envelope_experiment.py),

### Выбор генератора по ошибкам очереди

Простыми словами: ранние исторические работы проигрываются с несколькими
генераторами длительности. Выбирается тот, чьи mean/p99 T ближе к контролю
с записанным S; тип модели замораживается и проверяется на поздних периодах.
Схема rigid jobs выше, диспетчер и capacity не меняются.

`queue_log_error` и `select_queue_model` используют положительные validation
метрики с равными весами, строгими shapes и заданным порядком exact ties.
EPIC-061 сравнивает этот выбор с CRPS и fixed coarse. Ошибки очереди, покрытие
классов, успешность и policy regret могут давать разные выводы; временное
разделение ретроспективного эксперимента не является online-гарантией.

### Совместные приходы и ресурсные признаки

Простыми словами: генерируются время прихода вместе с потребностью в ресурсе
и набором признаков, затем длительность из общей эмпирической K-группы.
Дальше работа проходит прежнюю схему rigid jobs; диспетчер не меняется.

`ArrivalMark` и `MarkedArrivalBootstrap` сохраняют соседние нулевые/положительные
интервалы, поддерживают iid/circular blocks и закреплённые перестановки для
согласованных контролей. EPIC-062 сохраняет fixed-arrival coarse baseline и
пустое начало всех сценариев, не копируя исторический carry-in на synthetic time.
Context/request — диагностические marks, не входы S или runtime caps.
Устарелость completed-prefix, смена состава и горизонта явно аудируются;
устойчивый выигрыш joint-генератора и production-валидация policies не заявляются.

### Availability-aware история приходов

Простыми словами: не ждать завершения job'а, чтобы использовать его время
прихода, потребность и контекст для истории, по которой подгоняются будущие
приходы, — эти признаки уже были известны в момент подачи заявки. Подгонка
длительности обслуживания не меняется: она по-прежнему требует завершения.

EPIC-065 заменяет completed-prefix donor-историю (которая обрывалась на
первом незавершённом к cutoff задании, лаг до 8.2 дня) на `availability_prefix`
поверх уже распарсенной популяции completed+cancelled /
completed+cancelled+failed+timeout+node_failed, отфильтрованной только по
submit<cutoff. Lag падает до минут/часов, donor-пул примерно удваивается на
каждом origin, но это не равномерное улучшение точности: ошибка очереди Q
заметно ухудшается на SDSC и заметно улучшается на Kalos .70, а выбор
дисциплины по mean T не меняется нигде.

[эксперимент](../../examples/availability_aware_arrivals_experiment.py),
[результаты](../research/availability-aware-arrivals-results-2026-10.md).

### Календарь меняющейся ёмкости

Простыми словами: позволить самому пулу ресурсов менять размер по заранее
закреплённому расписанию, вместо постоянной ёмкости на весь реплей. Схема
rigid jobs и диспетчеры выше не меняются; новой дисциплины не добавляется.

`MsjLifecycleSim.run_capacity_calendar(trace, calendar)` принимает opt-in
`CapacityCalendar` (кусочно-постоянный, явный домен, без forward/backfill) и
реплеит до более раннего из полного дренажа и собственного горизонта
календаря. Активные задания никогда не вытесняются при падении ёмкости
(grandfathering); задание, чья потребность превышает максимум календаря,
исключается из диспетчеризации как `infeasible`, а не блокирует FCFS
навсегда; падение ёмкости, делающее существующую Conservative-резервацию
невозможной, перехватывается как явный, помеченный временем mismatch, а не
переинтерпретируется молча. EPIC-064 фиксирует это 23 юнит-тестами и
прогоняет три предписанных, не подогнанных сценария (фиксированный общий
пул, дневной общий пул, изолированный VC) на одном предписанном окне Helios
Venus; в этом окне общий пул оказался постоянным, поэтому shrink/growth-
механика проверена синтетическими тестами, а не этим конкретным прогоном
на реальных данных.
[Методика](../msj_capacity_calendar.md),
[эксперимент](../../examples/msj_capacity_calendar_experiment.py),
[результаты](../research/msj-capacity-calendar-results-2026-10.md).
