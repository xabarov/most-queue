# Multiserver-job системы (MSJ)

[🇬🇧 English version](msj.md) · [← Каталог моделей](../models.ru.md)

![Схема multiserver-job](../figures/msj.ru.png)

**Простыми словами:** в современных ЦОД и GPU-кластерах одна заявка часто занимает **несколько
серверов одновременно** (ядра, GPU) на всё время работы — в отличие от классического M/M/c, где
заявка занимает один сервер. Заявка ждёт, пока освободится достаточно серверов сразу. Модель
«multiserver-job» позволяет исследовать совместное влияние длительности, фрагментации
ресурсов и дисциплины на задержки.

### FCFS MSJ — точное время отклика (малые системы)

**Описание:** k серверов; у каждого класса — **потребность в серверах** (сколько занимает
одновременно) и экспоненциальная интенсивность. FCFS с блокировкой головы очереди: старшие заявки
жадно заполняют серверы, первая не влезающая останавливает просмотр. Точное среднее время отклика
(общее и по классам) через CTMC над последовательностью заявок по порядку прихода — для малых k /
немногих классов / умеренной загрузки.

**Класс расчета:** `MsjExactCalc` (`most_queue.theory.msj`) ·
**Симулятор:** `MsjSim` (`most_queue.sim.msj`)

```python
from most_queue.theory.msj import MsjExactCalc, MsjClass

calc = MsjExactCalc(k=2, classes=[MsjClass(0.4, 1, 1.0), MsjClass(0.2, 2, 1.0)])
r = calc.run()          # r.v[0] общее среднее пребывание; r.v_per_class по классам
```

### Saturated MSJ — пропускная способность и порог устойчивости

**Описание:** Область устойчивости MSJ-системы характеризуется её *насыщенной* (всегда с бэклогом)
версией. `MsjSaturatedCalc` точно решает насыщенную CTMC и возвращает пропускную способность
`X_sat` — **максимальную суммарную интенсивность входа**, которую открытая система выдерживает: она
устойчива тогда и только тогда, когда Λ < X_sat. Воспроизводит product-form результаты устойчивости
Grosof, Harchol-Balter, Scheller-Wolf.

**Класс расчета:** `MsjSaturatedCalc` (`most_queue.theory.msj`)

```python
from most_queue.theory.msj import MsjSaturatedCalc, MsjClass

sat = MsjSaturatedCalc(k=2, classes=[MsjClass(1.0, 1, 1.0), MsjClass(1.0, 2, 1.0)])
x_sat = sat.run()       # макс. суммарная интенсивность входа (микс классов — из соотношения rates)
```

### PH-обслуживание: FCFS в малых системах

**Простыми словами:** длительность заявки может состоять из нескольких стадий или
быть смесью коротких и длинных работ. На протяжении обслуживания она удерживает все
нужные серверы. Голова очереди блокирует следующие заявки, пока сама не поместится.

```python
from most_queue.random.map_ph import PHDistribution
from most_queue.random.utils.params import Cox2Params, ErlangParams
from most_queue.theory.msj import MsjPHCalc

services = [
    PHDistribution.from_erlang(ErlangParams(r=2, mu=2.0)),
    PHDistribution.from_cox(Cox2Params(mu1=2.0, mu2=1.5, p1=0.75)),
]
calc = MsjPHCalc(k=2, truncation=10, max_states=50000)
calc.set_sources([0.25, 0.15])
calc.set_servers([1, 2], services)
r = calc.run()
print(r.w_per_class, r.v_per_class, r.boundary_mass, r.stability_threshold)
```

`truncation` ограничивает общее число заявок; на границе вход блокируется. Решение
точно для этой конечной модели, а не бесконечной очереди. Закон Литтла использует
принятую интенсивность. Увеличивайте усечение и сравнивайте результаты: граничная
масса сама по себе не является границей ошибки. `w`/`v` содержат только среднее.
`max_states` ограничивает размер обеих CTMC. PH должна быть действительной и
транзиентной; комплексные подгонки и автоматическая замена произвольного G не поддержаны.

`saturated_throughput()` рассчитывает насыщенный порог для данного FCFS-микса;
`run()` отклоняет вход выше/на пороге. Условия загрузки ресурсов ниже 100% недостаточно.
Порог FCFS не переносится на EASY. Старые MSJ-классы и их API сохранены.

### Общее обслуживание, одинаковые трассы и backfilling

**Простыми словами:** EASY допускает опережение короткими/помещающимися работами,
если это не сдвигает прогнозный старт первой ожидающей заявки. Резервируется только
голова, а не все заявки. Прерываний нет.

```python
from most_queue.sim.msj_general import MsjGeneralSim

source = MsjGeneralSim(2, seed=47)
source.set_sources([0.25, 0.15])
source.set_servers([1, 2], [(service, "PH") for service in services])
trace = source.make_trace(11000, estimates="oracle")
for policy in ("fcfs", "easy", "conservative"):
    sim = MsjGeneralSim(2, policy)
    sim.set_servers([1, 2])
    r = sim.run_trace(trace, warmup_jobs=1000)
    print(policy, r.v[0], r.v_quantiles[0.99], r.reservation_violations)
```

Генераторы — пары `(params, notation)` библиотеки либо функции `sampler(rng)`;
для replay достаточно потребностей в серверах. `estimates` — явный `"oracle"`,
список прогнозов по классам или `None` для FCFS. Для произвольных прогнозов/трасс
используйте `MsjTraceJob(arrival, cls, service, estimate)`.
Планировщик не читает будущую фактическую длительность. При превышении оценки работа
не уничтожается; новые backfill временно запрещены. Нарушения обещанного старта
считаются отдельно. При заниженных прогнозах гарантии резервирования нет.

`discipline="conservative"` резервирует старт каждой ожидающей заявки, а не только
головы. Новые заявки не сдвигают старые резервирования. При раннем завершении
календарь сжимается по одной заявке, сохраняя остальные резервирования; для стартов
предусмотрены отдельные события. Превышение прогноза делает календарь недействительным:
временно используется FCFS без нового backfill, после завершения просроченных работ
календарь строится заново. История лучших обещаний сохраняется.
`reserved_start_times` — словарь `индекс заявки в трассе → лучшее обещанное время`,
включая warm-up; это не полная история изменений календаря. `reservation_violations`
считает опоздания к этим обещаниям. Oracle и верхние оценки сервиса сохраняют
обещания, но не гарантируют меньший p99 относительно другой дисциплины.
Повторные обходы календаря дороги при больших очередях; это эталонный симулятор,
не оптимизированный промышленный планировщик. Порог FCFS не является порогом conservative.

`run(N)` измеряет N приходов после дополнительного warm-up; `run_trace` дожидается
завершения всей измеряемой когорты. Моменты и p95/p99 относятся к этой когорте, а
загрузка и простой при непустой очереди — к интервалу между первым измеряемым и
последним приходом, без финального дренирования. Для отсутствующего класса — NaN;
при нулевом временном интервале временные метрики — `None`. Счётчики backfill и
резервирований включают warm-up. Конечный прогон не доказывает стационарность или SLO.

### Прогноз длительности по признакам

`LogLinearRuntimePredictor` из `most_queue.sim.utils.runtime_prediction` обучает
log-linear baseline на завершённых исторических работах: `fit(X, S)`.
`calibrate(X_cal, S_cal, coverage=0.95)` по отдельной выборке задаёт
односторонний split-conformal прогноз, `predict(X, upper=True)` возвращает его
без доступа к фактическому S будущей работы. Результат передаётся в
`MsjTraceJob.estimate`; EASY/conservative не изменены.

Признаки должны быть доступны до запуска, train/calibration/test — разделены.
Калибровка даёт marginal coverage при обменности наблюдений, а не гарантию каждой
заявки, каждого класса или p99 очереди. При недостатке calibration API сообщает
об отсутствии конечной границы, а не обрезает её. Возрастные прогнозы, drift-адаптация
и реальные трассы остаются отдельными этапами.
[Методика и пример EN](../msj_runtime_prediction.md),
[результаты EPIC-049](../research/msj-runtime-prediction-results-2026-10.md).

EPIC-050 добавляет `calibrate_by_group(X_cal, S_cal, groups)` и
`predict(X, upper=True, groups=groups)`: общая регрессия, отдельный порог для
каждого ресурсного класса, известного при поступлении. `group_calibrations`
показывает число наблюдений и доступность конечной границы. Для недостаточно
представленного или неизвестного класса прогноз явно отвергается, без подмены
общей оценкой. Покрытие по классу не гарантирует всех резервирований и теряет
основание при сдвиге закона внутри класса.
[API и ограничения EN](../msj_runtime_prediction.md#calibration-by-resource-group),
[результаты EPIC-050](../research/msj-group-calibration-results-2026-10.md).
