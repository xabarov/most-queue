# Roadmap: точные моменты ожидания для bulk-service (batch-size-dependent)

> Источники и численная проверка гипотезы — `docs/research/bulk-service-waiting-moments-2026.md`.
> База: EPIC-012 (`most_queue/theory/batch/bulk_service.py::BulkServiceMM1Calc`).

## 1. Моменты N (число в системе) — тривиально, из уже решённого pi

CTMC над `(i,j)` (i — размер обслуживаемого батча, j — число ожидающих) уже решается точно
(`spsolve`). Моменты `N=i+j`:

```
E[N^k] = Σ_{(i,j)} pi(i,j) · (i+j)^k
```

Никакой новой математики — просто больше сумм по уже вычисленному `pi`.

## 2. Точные моменты W (время ожидания) — при a=1

По PASTA приходящий клиент застаёт стационарное `(i,j)`. При `i>=1` (сервер занят) ожидание =
(оставшееся время текущего батча, `Exp(mu(i))`, по памяти-less) + время на `j // b` ПОЛНЫХ батчей
размера `b` впереди (каждый `Exp(mu(b))`, независимо) — гипоэкспоненциальное распределение,
моменты — через `conv_moments` (свёртка моментов независимых экспонент, уже есть в библиотеке).

**Почему это точно ТОЛЬКО при `a=1`:** вывод предполагает, что батч размера `min(b, остаток)`
формируется СРАЗУ, как только предыдущий освобождается. При `a>1`, если остаток после полных
батчей `<a`, сервер уходит в простой и ждёт ДОПОЛНИТЕЛЬНЫХ приходов до порога `a` — та же
«накопительная» подзадача, что и для самого первого батча, но теперь рекурсивно вложенная. Это
ломает чистую гипоэкспоненциальную декомпозицию. Численно проверено: при `a=1` формула совпадает с
Monte Carlo (<0.5% на 4 моментах); при `a=2` расхождение на среднем ~18% — поймано ДО написания
финального кода, не документационная тонкость.

```python
def exp_moments(rate, num=4):
    return [math.factorial(k) / rate**k for k in range(1, num + 1)]

def erlang_moments(n_terms, rate, num=4):
    if n_terms == 0:
        return [0.0] * num
    acc = exp_moments(rate, num)
    for _ in range(n_terms - 1):
        acc = conv_moments(acc, exp_moments(rate, num), num)
    return acc

# per state (i,j), i>=1:
full_ahead = j // b
wm = exp_moments(mu(i), num)
if full_ahead > 0:
    wm = conv_moments(wm, erlang_moments(full_ahead, mu(b), num), num)

# per state (0,j) [idle, accumulating toward a=1 -- j is always 0]:
# wm = [0]*num (tagged's own arrival immediately hits a=1, batch starts at once)

w_moments = Σ_{(i,j)} pi(i,j) · wm(i,j)
```

Для общего `a` (idle-состояния `(0,j)`, `0<=j<a-1`) формула для приходящего в idle:
`need = a - j - 1`; если `need<=0` — `wm=[0]*num`; иначе `wm = erlang_moments(need, lam, num)`
(нужно `need` дополнительных приходов, каждый `Exp(lam)`, до старта батча) — это ЧАСТЬ вывода,
которая остаётся точной и при `a>1` (проблема только в состояниях `i>=1` с недостаточным остатком
после полных батчей). В коде: при `a>1` метод точных моментов `get_w()` кидает понятную ошибку,
не пытаясь дать неверный ответ молча.

## 3. Что НЕ делаем в этом эпике (резерв)

- Точные моменты `W` при `a>1` — требует augmented absorbing-CTMC (отслеживание «сколько клиентов
  ещё осталось впереди помеченного» через под-фазы idle-refill) — решаемо, но существенно больше
  работы.
- Точные моменты `V` (пребывание) даже при `a=1` — собственный итоговый размер батча помеченного
  клиента зависит от приходов ВО ВРЕМЯ его ожидания, коррелирован с `W` — `V ≠ conv(W, S)` простой
  свёрткой, нужен совместный вывод. `E[V]` через закон Литтла (`E[N]/λ`) остаётся точным и
  используется как раньше.

## 4. API

```python
class BulkServiceMM1Calc(BaseQueue):
    def get_n_moments(self, num: int = 4) -> list[float]:
        """Exact raw moments of N (number in system), any a, b."""

    def get_w(self, num: int = 4) -> list[float]:
        """Exact raw moments of W (waiting time). Requires a == 1
        (ValueError otherwise -- see docs/research/bulk-service-waiting-moments-2026.md)."""
```

`run()` при `a==1` использует `get_w()` для `res.w` (заменяет старую приближённую оценку через
`mean_batch_service`); при `a>1` поведение не меняется (среднее через приближение, как раньше, с
явной пометкой в докстринге, что это приближение).
