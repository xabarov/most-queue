# Roadmap: многоканальный queueing-inventory (M/M/c, (s,S), backorder/lost-sales)

> База — `(0,S)`: `docs/roadmaps/queueing_inventory_roadmap.md`; lost-sales:
> `queueing_inventory_lost_sales_roadmap.md`; общая `(s,S)`: `queueing_inventory_general_sS_roadmap.md`.
> Источники — `docs/research/queueing-inventory-multiserver-2026.md`.

## 1. Идея: складываем c граничных уровней в один суперблок

В `M/M/1`-модели уровень QBD = число клиентов `n` (неограничено), граница — только `n=0`.
В `M/M/c` число **занятых серверов** = `min(n, c)` — детерминированная функция `n`, отдельный бит
состояния не нужен. Но скорость обслуживания зависит от `n` при `n = 0,...,c-1` (ставка `n·μ`,
не все серверы заняты) и становится не зависящей от `n` (`c·μ`) только при `n ≥ c`.

Значит границы QBD — это **`c` уровней** (`n=0,...,c-1`), а не один. `QBDSolver` поддерживает
граничный блок произвольной размерности `m0`, лишь бы он был один — поэтому "складываем" все `c`
граничных подуровней в один суперблок размерности `m0 = c·(S+1)` (фаза `i` вложена внутрь подуровня
`n`), а однородная (повторяющаяся) часть QBD начинается с `n = c` (размерность `m = S+1`, как и в
`M/M/1`-модели). При `c=1` суперблок вырождается в единственный подуровень `n=0` — точная редукция
к уже реализованной модели (EPIC-024/026/027).

## 2. Локальные операторы (одинаковы во всех моделях, различается только `n`-зависимость)

Пусть `m = S+1`, фаза `i = 0,...,S`. Для произвольного числа клиентов `n` определим:

- **Приход** `U(i)`: ставка `λ`, фаза не меняется; `U(0) = 0`, если `policy="lost_sales"`
  (приход при пустом складе не является переходом состояния — как в EPIC-026).
- **Обслуживание** `Dn(n, i)`: ставка `min(n,c)·μ`, переход `i → i-1`, только при `i ≥ 1`
  (обслуживание блокировано при `i=0`, порог не совпадает с `s`).
- **Пополнение** `R(i)`: ставка `θ`, переход `i → S`, при `i ≤ s` (общая `(s,S)`, EPIC-027).

## 3. Граничный суперблок (n = 0,...,c-1)

`B00` (`m0×m0`, блоки `c×c`, каждый блок `m×m`):

```
B00[n, n]   = diag(-(U_out(i) + Dn_out(n,i) + R_out(i)))  +  R(i)-переходы (i<=s -> S)
B00[n, n+1] = U(i)·I   (диагональная по i матрица), n = 0,...,c-2
B00[n, n-1] = Dn(n, i)  (i, i-1)-поддиагональ,        n = 1,...,c-1
```

где `U_out(i) = λ` (или `0` при `i=0` и lost-sales), `Dn_out(n,i) = n·μ` при `i≥1` иначе `0`,
`R_out(i) = θ` при `i≤s` иначе `0`. При `n=0`: `Dn_out(0,i) ≡ 0` для всех `i` (нет клиентов —
нечего обслуживать), поэтому диагональ блока `n=0` **совпадает** с `B00` уже реализованной
`M/M/1`-модели — прямая проверка на согласованность вывода.

`B01` (`m0×m`, из границы в первый повторяющийся уровень `n=c`): только последний подуровень
(`n=c-1`) отдаёт переход — `B01`-блок `[c-1] = U(i)·I` (приход при `n=c-1` выталкивает систему в
`n=c`), остальные подблоки нулевые.

`B10` (`m×m0`, из `n=c` обратно в `n=c-1`): единственный ненулевой подблок — колонка `n=c-1`,
равна `A2` (см. ниже) — уход с `n=c` (все `c` серверов заняты, ставка `c·μ`) приземляется на
`n=c-1`.

## 4. Однородная часть (n ≥ c) — совпадает с M/M/1-моделью при замене `μ → c·μ`

```
A0[i,i] = λ                          (A0[0,0]=0 при lost_sales)
A2[i,i-1] = c·μ                       для i = 1,...,S   (A2[0,:]=0 — блокировка при i=0)
A1[i, S] = θ                          для i = 0,...,s
A1[0,0]  = -θ (lost) / -(λ+θ) (backorder)
A1[i,i]  = -(λ + c·μ + θ)             для i = 1,...,s
A1[i,i]  = -(λ + c·μ)                 для i = s+1,...,S
```

Ровно формулы `queueing_inventory_general_sS_roadmap.md` §2 с `μ → c·μ` — ожидаемо, поскольку при
`n≥c` все `c` серверов заняты одновременно, что структурно эквивалентно одному "суперсерверу" со
ставкой `c·μ`.

**Проверка на c=1:** суперблок `B00` вырождается в один подуровень (`n=0`), формулы `A0/A1/A2`
совпадают с `M/M/1`-моделью буквально (`c·μ = μ`) — точная регрессия.

## 5. Производные метрики (нужна доработка, не просто перенос формул)

- **`get_p(num_levels)`**: `P(N=n)` для `n=0,...,c-1` — сумма по `i` соответствующего подблока
  `pi0` (переформатировать `pi0` в `(c, m)`); для `n≥c` — `solver.level_probs` начиная с `pi1`
  (индекс QBD-уровня `j` соответствует `N = c-1+j`).
- **`_phase_marginal()`** (распределение запаса, суммарно по всем `N`): сумма всех `c` подблоков
  `pi0` (поэлементно по `i`) `+ pi1 @ (I-R)^{-1}` — то же самое `(I-R)^{-1}`-суммирование, что и в
  `M/M/1`-модели, только `pi0` теперь сумма `c` кусков вместо одного вектора.
- **`_mean_in_system()`**: `E[N] = Σ_{n=0}^{c-1} n·P(n) + (c-1)·pi1(I-R)^{-1}·1 + pi1(I-R)^{-2}·1`
  — первое слагаемое считается прямо по подблокам `pi0`, второе и третье — стандартная
  matrix-geometric формула среднего со сдвигом на `(c-1)` (при `c=1` сдвиг обнуляется — снова
  точная редукция).
- **`get_w()`**: `V = W + 1/μ` остаётся точным без изменений (среднее время обслуживания одного
  клиента не зависит от `c`).
- **`_effective_arrival_rate()`**: без изменений (EPIC-026 логика: `λ` для backorder, `λ·(1 −
  stockout_prob)` для lost-sales — `stockout_prob` теперь агрегирован по всем `N`, как в
  `_phase_marginal()`).

## 6. API

```python
class MMcQueueingInventoryCalc(BaseQueue):
    def __init__(self, c: int, s_max: int, s: int = 0, policy: Policy = "backorder",
                 calc_params: CalcParams | None = None):
        """:param c: число одинаковых серверов, c >= 1."""
```

Валидация: `c >= 1`, `s_max >= 1`, `0 <= s < s_max`, `policy in ("backorder","lost_sales")`.
Условие устойчивости: `rho = λ/(c·μ) < 1`.

Отдельный класс (не параметр на `MM1QueueingInventoryCalc`), т.к. размерность граничного блока
меняется (`m0 = c·(S+1)` вместо `S+1`) — качественно другая конструкция солвера, а не изменение
одной формулы (в отличие от `s`/`policy` в EPIC-026/027).

## 7. Sim

`MMcQueueingInventorySim`: состояние `(n, i)`, ставка обслуживания `min(n,c)·μ` вместо `μ`
(единственное отличие событийного цикла от `MM1QueueingInventorySim`), пополнение при `i<=s`,
lost-sales — приход при `i=0` не входит в очередь.
