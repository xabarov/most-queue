## Направление 1. Асимптотика хвоста по t → ∞ (при фиксированном `b_max`)

**Статус: переоценено, сложнее, чем казалось изначально — см. «Находка» ниже.**

### Исходная гипотеза (оказалась нерелевантной практике)

Наивная идея: показать, что `η(b_max) := lim_{t→∞} -log P(W>t) / t` имеет точную замкнутую форму —
`rate(b_max)` для $E_k$-случая, `min(mu1(b_max), mu2(b_max))` для H2-случая — поскольку
доминирующая (самая длинная, у границы усечения очереди `N`) цепь фаз имеет для Erlang-случая ВСЕ
фазы с одинаковой ставкой `rate(b_max)`, а собственные значения такой цепи не зависят от числа фаз
`m`, только полиномиальный множитель перед экспонентой зависит от `m`.

### Находка при проверке (2026-10-06)

Численная проверка (`get_tail(t)` при `t=40,60`, для `b_max=2..64`) дала эмпirическую скорость
затухания **на порядок меньше** предсказанной (0.21 против 4.60 для `b_max=2`). Причина —
методологическая ошибка в самой гипотезе, не баг в коде:

- Цепь у границы усечения `N=400` имеет `m=⌊N/b_max⌋·k` фаз (например, 2000 фаз при `b_max=2`,
  `k=10`), то есть представляет собой **Erlang(m, rate(b_max))**, чьё **среднее** равно `m/rate ≈
  435` при `b_max=2`. На `t=40` мы меряем не хвост, а тело распределения со средним 435 —
  асимптотика `t→∞` там физически не наблюдаема.
- При этом состояние с таким `j≈N` имеет пренебрежимо малую стационарную вероятность `π(j)`,
  поскольку `ρ=λα≈0.115` — система сильно недогружена. Доминирующий вклад в `P(W>t)` при
  практически интересных `D=5,10,20` дают состояния с **малым** `j` (короткая цепь из нескольких
  фаз текущего батча), а не состояние у границы усечения.
- Следовательно, истинная асимптотика `t→∞` для ВСЕЙ смеси `Σ_j π(j)·f_j(t)` — это не просто
  собственное значение одной «худшей» цепи, а классическая задача типа Крамера–Лундберга
  (седловая точка, балансирующая геометрическое затухание `π(j)` по `j` против фазового затухания
  `f_j(t)` по `t`), специфичная для данной batch-size-зависимой ограниченной модели. Это
  содержательный самостоятельный результат уровня отдельного эпика/раздела статьи, а не
  тривиальное добавление поверх уже построенных подгенераторов.

### Пересмотренные варианты продолжения

- **(1a) Честная `t→∞` асимптотика с явной границей применимости.** Доказать `η(b_max)` как
  предложено выше (это математически верно — собственные значения однородной Erlang-цепи
  действительно не зависят от `m`), но явно охарактеризовать **длину «плеча»** (crossover point,
  `t_c ~ m/rate`) до которого асимптотика не действует, и честно показать, что для реалистичных
  SLA-дедлайнов (`D` того же порядка, что среднее время ожидания) эта асимптотика нерелевантна.
  Ценность — скорее методологическая (предостережение), чем практическая.
- **(1b) Седловая точка / доминантный член смеси в практически релевантном диапазоне `t`.**
  Честно воспроизвести Крамера–Лундберг-type анализ для ИМЕННО этой batch-size-зависимой
  ограниченной модели: найти, какой `j` (и, значит, какая конфигурация фаз) доминирует сумму при
  заданном `t`, и получить приближённо-асимптотическую формулу, объясняющую уже наблюдаемую в
  статье форму кривых (Рисунок 2). Это куда более ценный и куда более трудоёмкий результат —
  по сложности сопоставим с отдельным эпиком, не с вечерней правкой статьи.
- **(1c) Отказаться от асимптотики, усилить новизну через точную количественную характеризацию
  уже полученного результата** — например, доказать монотонность `E[W](b_max)` по `b_max`
  (уже видно численно на Рисунке 1, но не доказано) через стохастическое доминирование/coupling
  аргумент между вложенными цепями Маркова для разных `b_max`. Дешевле 1b, даёт строгую теорему,
  которой сейчас в статье нет.

**Рекомендация:** (1c) — начать с монотонности `E[W](b_max)`, она просится по уже посчитанным
данным, доказательство coupling-аргументом вероятно займёт один присест, и это полноценная теорема
для статьи. (1a)/(1b) — отложить, обсудить отдельно, если потребуется более глубокий результат.

## Направление 2. Снятие ограничения `a=1` → общий порог запуска `a>1` («idle-refill»)

Уже зафиксировано как явное ограничение статьи. Нужна новая CTMC с дополнительным «накопительным»
состоянием перед запуском пакета (сервер простаивает, пока не накопится `a` заявок). Техника
построения подгенератора и PASTA-разложения переносится без изменений; меняется только блок
«сервер простаивает» (сейчас `i=0 → W=0` мгновенно, при `a>1` нужно ждать накопления). Сопоставимо
по сложности с EPIC-040/041 (новый тип «пороговых» состояний в уже знакомой конструкции).

**Оценка:** средняя сложность, 1 новый эпик, затрагивает `most_queue/theory/batch/bulk_service*.py`
и соответствующие симуляторы для DES-кросс-валидации.

## Направление 3. Обобщение на `c>1` серверов (несколько GPU с независимым батчингом)

Прямое практическое попадание в реальную multi-GPU LLM-serving архитектуру (пул реплик, балансировка
нагрузки). По шаблону EPIC-033/038/041 (state-splitting + QBD для гетерогенных серверов), но здесь
серверы не гетерогенные, а идентичные независимые batch-service инстансы с общей очередью —
ближе по структуре к M/G/c, но с пакетным, а не поштучным обслуживанием на каждом сервере.

**Оценка:** высокая сложность, отдельный полноценный эпик, наибольший практический вес, наибольший
риск (новая конструкция state space, не прямое переиспользование существующей).

## Направление 1, подпункт (1c): промежуточный итог (2026-10-06)

Попытка прямого coupling-доказательства монотонности `E[W](b_max)` наткнулась на реальную
трудность: простое поэлементное (pathwise) сравнение двух систем с разными `b_max` по одному и
тому же потоку заявок **не обязано** быть монотонным в каждый момент времени (система с большим
`b_max` иногда формирует один большой и медленный пакет и временно отстаёт по числу завершённых
заявок от системы с меньшим `b_max`, которая чаще завершает меньшие пакеты) — полное pathwise
доминирование, по-видимому, неверно в общем случае; утверждение верно только в терминах
долгосрочных средних, что требует другой техники доказательства (не прямого coupling).

**Получен и строго доказан более скромный, но точный результат** — лемма баланса потоков:
в любой стабильной эргодической batch-service системе с `E[время пакета | размер s] = α·s + τ0`
(верно по построению и для $E_k$-, и для H2-калькуляторов) коэффициент загрузки сервера
удовлетворяет точному тождеству

```
ρ = λα + λτ0 / S̄,      где S̄ = E[размер пакета] (усреднение по пакетам, не по заявкам)
```

(доказательство — renewal-reward, 4–5 строк, не требует независимости между размером пакета и его
длительностью). Следствие: монотонность `E[W](b_max)` сводится к монотонности `S̄(b_max)` — что
скромнее исходной цели, но полностью строго.

Численная проверка тождества на уже построенных калькуляторах (через `run().utilization`, по
скрытой формуле `S̄ = λτ0/(ρ-λα)`) подтвердила его точно и показала `S̄(b_max)` монотонно
растущей, `ρ(b_max)` монотонно убывающей, для обоих вариантов изменчивости:

| b_max | ρ (E_k) | S̄ (E_k) | ρ (H2) | S̄ (H2) |
|---|---|---|---|---|
| 2  | 0,958 | 1,79 | 0,939 | 1,83 |
| 4  | 0,899 | 1,93 | 0,817 | 2,15 |
| 8  | 0,895 | 1,94 | 0,780 | 2,27 |
| 16 | 0,895 | 1,94 | 0,769 | 2,31 |
| 32 | 0,895 | 1,94 | 0,766 | 2,32 |

Для $E_k$ (низкая изменчивость) `S̄`/`ρ` стабилизируются уже к `b_max≈8`; для H2 (высокая
изменчивость) сходимость заметно медленнее — пакет иногда "подрастает" из-за редких долгих
обслуживаний, что само по себе интересное наблюдение для статьи. Полное доказательство
монотонности `S̄(b_max)` остаётся открытым, зафиксировано как conjecture с сильной численной
поддержкой.

## Приоритет (обновлено 2026-10-06)

Рекомендация по убыванию отношения ценность/трудоёмкость, с учётом уже найденных рисков:

1. **B1** (оптимальный `b_max`) — почти бесплатно, без риска, явно прикладная ценность, использует уже
   готовый код как есть.
2. **E1** (количественный бейзлайн против Claeys 2013) — усиливает центральный novelty-довод статьи

3. **D1** (калибровка на Bench360) — наибольший скачок достоверности, но зависит от того, насколько
   чисто датасет конвертируется в нужную параметризацию; нужно сначала прочитать источник.
4. **A1** (idle-refill, `a>1`) — закрывает явное ограничение, шаблон техники уже есть, но это
   полноценный новый эпик most-queue, не правка статьи.
5. **A4** (нетерпеливые заявки) — концептуально сильно подходит мотивации (SLA = заявки, которые

6. **A3** (MAP-вход) / **C3** (седловая точка) — самые рискованные и дорогие, но с наибольшим

7. **A2** (`c>1` серверов) — наибольшая практическая значимость, но отдельный полноценный эпик,

## Реализация B1 + E1 (2026-10-06)

Выполнены по решению пользователя («1 и 2 сейчас, потом 3»). Оба — в статью
(`docs/статьи/batch-service-sla/latex/main.tex`, новый раздел «Практические следствия: выбор
`b_max` и предел приближений»), оба воспроизводимы новыми скриптами в `examples/`.

**B1 (`examples/batch_service_optimal_bmax.py`)** — минимальный `b_max` под целевую SLA, прямым
перебором по уже точному `get_tail` как чёрному ящику. Побочная находка: на расширенной сетке
дедлайнов (добавлены `D=30,50` сверх исходных `5,10,20`) точный хвост оказался **немонотонен** по
`b_max` при `D=50` — `P(W>50)` при `b_max=32` на 7 порядков хуже, чем при `b_max=8..16`
(устойчиво к удвоению усечения очереди `N`, не артефакт). Это прямое проявление направления 1/C1
(асимптотика `t→∞`, `η(b_max)=rate(b_max)` убывает с ростом `b_max`) — при достаточно глубоком `D`
убывающая асимптotическая скорость в итоге перевешивает выигрыш от более редких партий. На
практике эффект не меняет ответ ни при одном из испытанных `ε` (провал на много порядков ниже
разумных целей), но является строгим контрпримером к гипотезе о всеобщей монотонности —
зафиксировано в статье как открытый вопрос, не как теорема.

**E1 (`examples/batch_service_dominant_pole_baseline.py`)** — точную batch-size-зависимую формулу
Claeys et al. (2013) получить не удалось (платный доступ); вместо этого честно реализована та же
ОБЩАЯ техника (единственная доминирующая особенность/полюс производящей функции — по открытому
precursor-препринту 2012 года с biblio.ugent.be, который реально прочитан) для нашей модели:
`P_approx(W>t)=ρ·exp(-η(b_max)·t)`. Результат — расхождение с точным значением от $10^{14}$ до
$10^{19}$ в зависимости от `b_max`/режима, причём в РАЗНЫЕ стороны (занижение при малом `b_max` —
асимптотика ещё не наступила; завышение при большом `b_max` — номинальная ставка `rate(b_max)`
почти никогда не реализуется). Количественно подтверждает центральный novelty-довод статьи: даже
честная реализация ближайшего прежнего метода катастрофически неточна именно в практически
интересном диапазоне.

Дополнительно доказана (не только численно, строго) **лемма баланса потоков**
`ρ = λα + λτ0/S̄` (renewal-reward, 4-5 строк) — общая для любой batch-size-зависимой системы с
линейным по размеру средним временем пакета, независимо от распределения. Сводит монотонность
`E[W](b_max)` к монотонности `S̄(b_max)`, даёт независимую численную сверку корректности построения
CTMC (обратное восстановление `S̄` из `run().utilization` совпадает точно).

**Следующий шаг:** направление 3 (D1, калибровка на Bench360, arXiv:2511.16682).

## Реализация D1 (2026-10-06)

Прочитан полный текст Bench360 (arXiv:2511.16682, открытый PDF). Подходящий источник —
таблица 4 (offline-batch throughput, tokens/s, по `batch_size∈{16,32,64,128}`, по движкам
vLLM/SGLang/LMDeploy/TGI, по GPU L4/A10/A30). Взят SGLang на L4 (рекомендованный авторами
"победитель" на mid-tier GPU) как единственная комбинация, годная для вывода $g(s)=\alpha
s+\tau_0$ без дополнительных вендорских допущений.

Пересчёт: время обработки батча размера $B$ = $B\cdot N_t/\text{TPS}(B)$, где $N_t=64$ —
`max_new_tokens` для MMLU/SQuAD/Spider в Bench360 (Приложение E.1 источника). МНК по 4 точкам
даёт $\alpha\approx0{,}076$~с, $\tau_0\approx6{,}30$~с — на порядок больший фиксированный
оверхед на партию, чем у \cite{inoue2021} (ResNet-50, $\tau_0=1{,}887$), что содержательно
объяснимо разницей между декодирующим циклом LLM и свёрточной сетью.

Пересчёт $E[W](b_{\max})$ на этих параметрах ($\lambda=0{,}25$, 80\% от пропускной способности
при $b_{\max}=2$) даёт то же качественное поведение, что и на синтетических параметрах Inoue:
$E[W]=10{,}24$ при $b_{\max}=2$ превышает соответствующую Inoue-границу (9,72), быстро сходится
к $\approx3{,}11$ уже при $b_{\max}=8$. Добавлено в статью одним компактным абзацем в
"Численные эксперименты" + ссылка `bench360_2026` в общий `library.bib`, не отдельным разделом —
результат подтверждающий, не открывающий новую линию анализа.

**Честно зафиксированное ограничение:** Bench360 даёt только throughput (среднее), не
изменчивость времени обслуживания батча — коэффициент вариации в обеих калибровках (Inoue и
Bench360) остаётся синтетическим допущением; снято явно в разделе "Ограничения" статьи.

**Статус направления 2 (расширенный список, 2026-10-06): все три исходных пункта плана (B1, E1,
D1) выполнены.** Резерв на будущее — направления A1-A4, A2-A3, C3 из расширенного списка
(idle-refill, нетерпеливые заявки, `c>1` серверов, MAP-вход, седловая точка) остаются как
кандидаты на отдельные будущие эпики most-queue, не как доработки текущей статьи.
