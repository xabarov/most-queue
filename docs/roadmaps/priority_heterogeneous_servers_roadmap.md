# Roadmap: M/M/2 с приоритетами и гетерогенными серверами

> Первоисточник постановки: *Analysis of a Pre-Emptive Two-Priority Queuing System with Impatient
> Customers and Heterogeneous Servers*, Mathematics, 2023, doi:10.3390/math11183878 (без
> нетерпения в этой волне). Техника расщепления состояния: Krishnamoorthi B., *On Poisson Queue
> with Two Heterogeneous Servers*, Operations Research, 1963, doi:10.1287/opre.11.3.321 (уже
> применена в EPIC-023). Полный список источников — `docs/research/priority-heterogeneous-servers-2026.md`.

## 1. Постановка

2 сервера, скорости `mu_a ≥ mu_b` (после нормализации внутри `set_servers`). 2 класса заявок,
пуассоновские потоки `l0` (класс 0, высший приоритет) и `l1` (класс 1). Preemptive-приоритет:
класс 0 может вытеснить обслуживаемую заявку класса 1 (память экспоненциального обслуживания не
нужна — restart = resume для M/M). Дисциплина назначения серверов:

1. **Простаивающий сервер приоритетнее вытеснения.** Новая заявка сначала пытается занять
   простаивающий сервер (быстрый первым); вытесняет чужой (низкоприоритетный) сервер только если
   свободных нет.
2. **Sticky: заявка в обслуживании не мигрирует между серверами**, даже если освобождается более
   быстрый сервер — начатое обслуживание продолжается на том же приборе до конца или вытеснения.

## 2. Состояние и построение цепи (программно, не вручную)

При экспоненциальном обслуживании `(n_0, n_1)` — число заявок каждого класса в системе — почти
марковское состояние, как и в уже существующем `MMkPriorityExact` (гомогенный случай). Не хватает
одного бита: при `n_0=1` (или `n_0=0, n_1=1`) неизвестно, **какой** сервер занят — а от этого
зависит ставка. Полное состояние: `(n_0, n_1, config)`, где `config` содержит эту информацию
только в неоднозначных случаях (`n_0=1` — какой сервер у класса 0; `n_0=0, n_1=1` — какой сервер
у класса 1), иначе `config=None` (канонический случай: `n_0≥2` — оба сервера класс 0; `n_0=0,
n_1≥2` — оба сервера класс 1; `n_0=n_1=0` — оба простаивают).

Чтобы не выводить вручную каждый переход (риск ошибки транскрипции при таком ветвлении — уже
проявился в разборе на этапе исследования), цепь строится **механически** через четыре чистые
функции над «сырым» представлением `(n_0, n_1, a_class, b_class)` (`a_class`/`b_class` ∈
`{0, 1, None}` — что сейчас реально обслуживает каждый сервер):

```python
def canonicalize(n0, n1, a_class, b_class):
    """Заполняет простаивающие слоты из очереди (класс 0 первым), выводит config."""
    backlog0 = n0 - (a_class == 0) - (b_class == 0)
    backlog1 = n1 - (a_class == 1) - (b_class == 1)
    for slot in ("a", "b"):
        cur = a_class if slot == "a" else b_class
        if cur is None:
            if backlog0 > 0:
                new_val, backlog0 = 0, backlog0 - 1
            elif backlog1 > 0:
                new_val, backlog1 = 1, backlog1 - 1
            else:
                continue
            if slot == "a": a_class = new_val
            else: b_class = new_val
    # config: см. §1 текста выше — читается напрямую из (n0, n1, a_class, b_class)
    ...


def class0_arrival(n0, n1, a_class, b_class):
    n0 += 1
    if a_class is None: a_class = 0
    elif b_class is None: b_class = 0
    elif a_class == 1: a_class = 0     # вытесняем класс 1 на A (быстрый — предпочтителен для класса 0)
    elif b_class == 1: b_class = 0     # иначе вытесняем на B
    # else: оба уже класс 0 -- просто растёт очередь класса 0
    return canonicalize(n0, n1, a_class, b_class)


def class1_arrival(n0, n1, a_class, b_class):
    n1 += 1
    if a_class is None: a_class = 1
    elif b_class is None: b_class = 1
    # класс 1 никогда не вытесняет -- иначе просто растёт очередь
    return canonicalize(n0, n1, a_class, b_class)


def departure(n0, n1, a_class, b_class, server):
    served = a_class if server == "a" else b_class
    if server == "a": a_class = None
    else: b_class = None
    if served == 0: n0 -= 1
    else: n1 -= 1
    return canonicalize(n0, n1, a_class, b_class)
```

Обход состояний: для каждого достижимого `(n0, n1, config)` (в пределах усечения) восстановить
`(a_class, b_class)` (однозначно по определению `config`), применить `class0_arrival` (ставка
`l0`), `class1_arrival` (ставка `l1`), `departure("a")` (если `a_class` занят, ставка `mu_a`),
`departure("b")` (если `b_class` занят, ставка `mu_b`) — получить 4 (или меньше) исходящих
перехода. Собрать полный список `(from, to, rate)`, решить через
`theory/reliability/utils.py::ctmc_stationary` (переиспользуем инструмент EPIC-023).

## 3. Проверка корректности построения (до сдачи, не тест)

Перед тем как писать формальные тесты — прогнать `canonicalize`/`class0_arrival`/
`class1_arrival`/`departure` на малых случаях вручную (`n0≤2, n1≤2`) и свериться со сценариями,
разобранными в research-доке (например: `(n0=0,n1=1,config=B)` + приход класса 0 → класс 0
занимает простаивающий A → `(n0=1,n1=1,config=A)`). Это не подменяет тесты, но ловит грубые
ошибки в примитивах до того, как они растворятся в большой цепи.

## 4. Редукция-регрессия

При `mu_a = mu_b = mu` результат обязан **точно** воспроизвести `MMkPriorityExact(n=2)` с теми же
`l0, l1, mu` (тот же usable truncation) — сильнейшая проверка: если расщепление состояния
построено некорректно, эта редукция, скорее всего, не сойдётся точно (в отличие от более слабых
приближённых проверок).

## 5. API

```python
class MM2PriorityHeterogeneousCalc(BaseQueue):
    def __init__(self, truncation: int | None = None): ...
    def set_sources(self, l: list[float]): ...      # [l0, l1]
    def set_servers(self, mu_a: float, mu_b: float): ...  # любой порядок
    def run(self) -> PriorityResults: ...             # per-class v/w (первые моменты)
```

Возвращаемые моменты — по образцу `MMkPriorityExact`: как минимум средние `v[k][0]`, `w[k][0]`
per class; старшие моменты — опционально, в резерве (см. `MMkPriorityExact`'s `with_variance`
как образец для будущего расширения).

## 6. Sim

DES-симулятор переиспользует **те же четыре примитива** (`class0_arrival`/`class1_arrival`/
`departure`/`canonicalize`), импортированные из теоретического модуля, а не дублирует логику —
гарантирует, что тестируемая теория и симулятор согласованы по построению, а не только по
результату.

## 8. Резерв

- **Нетерпение (impatience)** — добавляет ещё одно измерение состояния (кто из ожидающих может
  уйти); первоисточник 2023 года его покрывает, но не в этой волне.
- **Accumulating priority + гетерогенные серверы** (EJOR 2016) — другая техника (накопление
  кредита, не CTMC-расщепление состояния сервера), отдельная задача.
- **k > 2 гетерогенных сервера** — комбинаторный взрыв конфигураций (как и в EPIC-023).
