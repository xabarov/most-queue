# Roadmap: queueing-inventory lost-sales вариант

> Первоисточник: Saffari M., Haji R., Hassanzadeh F., *The M/M/1 queue with inventory, lost sale,
> and general lead times*, Queueing Systems, 2013, doi:10.1007/s11134-012-9337-3. Базовая модель
> (backorder) и полный вывод QBD-блоков — `docs/roadmaps/queueing_inventory_roadmap.md`. Полный
> список источников — `docs/research/queueing-inventory-lost-sales-2026.md`.

## 1. Разница с backorder (EPIC-024)

Единственное отличие: приход заявки при `i=0` (склад пуст). В backorder — заявка встаёт в
очередь (`n→n+1`, уровень вверх). В lost-sales — заявка **теряется**: событие не меняет состояние
системы вовсе (это не «переход с равными состояниями», а полное отсутствие перехода — потерянные
события не входят в генератор CTMC).

## 2. Изменение QBD-блоков

Из `queueing_inventory_roadmap.md` §2, базовые блоки (`m = S+1` фаз, `i = 0..S`):

```
backorder:  A0 = λ · I_m                    B01 = λ · I_m
lost_sales: A0 = λ · diag(0, 1, 1, ..., 1)   B01 = λ · diag(0, 1, 1, ..., 1)   (строка фазы 0 обнулена)
```

Диагональ `A1`/`B00` теряет слагаемое `λ` в строке `i=0` (поскольку туда больше не ведёт исходящий
переход по приходу):

```
backorder:  A1[0,0] = -(λ+θ)     B00[0,0] = -(λ+θ)
lost_sales: A1[0,0] = -θ         B00[0,0] = -θ
```

Всё остальное (`A2` — обслуживание, `A1[0,S]`/`B00[0,S]` — пополнение, `B10` — вниз с уровня 1)
**не меняется**.

## 3. API

Не новый класс — параметр на существующем:

```python
class MM1QueueingInventoryCalc(BaseQueue):
    def __init__(self, s_max: int, policy: Literal["backorder", "lost_sales"] = "backorder",
                 calc_params: CalcParams | None = None): ...
```

`_build_solver()` строит `A0`/`B01` по формуле выше в зависимости от `self.policy`; остальной код
(`A2`, `A1` диагональ для `i≥1`, `B00` для `i≥1`, `B10`, метрики через `QBDSolver`) — без
изменений, переиспользуется как есть.

**Новая метрика:** `loss_prob` в `QueueingInventoryResults` — вероятность, что случайно пришедшая
заявка потеряна. В этой модели (весь приход при `i=0` теряется, весь приход при `i≥1` принимается)
по PASTA это **в точности** `stockout_prob` (маргинальная `P(i=0)`, уже вычисляемая для
backorder-варианта) — для `policy="lost_sales"` просто переиспользовать то же поле под новым
именем/алиасом, не отдельный расчёт.

## 4. Sim

`MM1QueueingInventorySim` получает тот же `policy` параметр: при `lost_sales` и `i==0` на событии
прихода — просто не увеличивать `failed`/`n` (эффективно «холостой» тик по времени, но состояние
не меняется; статистика площадей всё равно корректно накапливается за время до следующего
события).

## 6. Резерв

- Общая `(s,S)`-политика, многоканальный случай, композиция с negative-customers/приоритетами —
  как и в EPIC-024, остаются в резерве (независимо от backorder/lost-sales).
