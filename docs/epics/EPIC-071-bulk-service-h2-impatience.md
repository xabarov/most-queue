# EPIC-071: Нетерпеливые заявки для H2-обслуживания (EPIC-036/042 × EPIC-068)

- **Статус:** done
- **Создан:** 2026-10-07
- **Завершён:** 2026-10-07
- **Roadmap:** резерв EPIC-068 («Что НЕ сделано»: `BulkServiceH2Calc.get_abandonment_prob()`)

## Цель

Добавить марковское нетерпение (ставка `gamma`) к `BulkServiceH2Calc` — вторая из
трёх резервных комбинаций, отмеченных в «Ограничениях» статьи batch-service-sla.

## Почему это средний (не низкий) риск

В отличие от EPIC-070 (почти чистое переиспользование), здесь H2 — не
последовательная цепь фаз, а ВЕТВЛЕНИЕ: каждый полноразмерный батч впереди
помеченной заявки заново независимо выбирает свою ветвь (`p1`/`mu1` или `p2`/`mu2`).
`abandonment_chain` (EPIC-068) в текущем виде предполагает последовательные фазы —
перенос потребовал бы скрещивать `(R, K)` с ВЕТВЬЮ каждого слоя впереди, а не
только последнего (как уже делает `BulkServiceH2Calc.get_tail` при `gamma=0`,
см. `_tagged_wait_tail_with_refill`).

**Однако есть готовый шаблон для переноса.** `_tagged_wait_tail_with_refill` уже
решает ОЧЕНЬ похожую задачу: пересекает ветвление КАЖДОГО слоя впереди со счётчиком
новых приходов (`K`) для гонки при `a>1`. Расширение до `(R, K)` с добавлением
конкурирующего выхода `gamma` на каждой фазе — структурно то же самое упражнение,
просто с ещё одним измерением состояния (`R`, убывающее через нетерпение `R*gamma`
и через исключающие batches размера ровно `b`, та же логика, что в EPIC-068).

## Что получилось на деле (проще предварительной оценки)

Опасение при планировании — что потребуется «скрещивать ветвление каждого слоя
впереди помеченной заявки с `(R, K)`», то есть что число ветвящихся слоёв будет
расти с числом полных батчей впереди (как в `_tagged_wait_tail_with_refill`).
На практике это не потребовалось: в отличие от Erlang (где «сколько ещё батчей
впереди» определяет число ПОСЛЕДОВАТЕЛЬНЫХ фазовых слотов, `n_first + k_ahead`),
H2 не накапливает слои — каждый новый батч впереди заново выбирает одну из ровно
двух веток и тут же «забывает» прошлые ветки (марковость/безпамятность). Поэтому
вместо растущего по числу слоёв пространства состояний достаточно ровно 3
«сегментов» на каждую пару `(R, K)`: `first` (уже наблюдаемый батч, его фаза уже
известна по PASTA — ветвления там нет) и `ahead`-ветка-0 / `ahead`-ветка-1 (каждая
зацикливается сама на себя при переходе к следующему батчу впереди). Итоговая
конструкция (`_h2_abandonment_chain` в `bulk_service_h2.py`) структурно проще
`abandonment_chain` (EPIC-068) для Erlang при `k>1`, а не сложнее её — оценка риска
как «среднего» была осторожной, но объём реализации оказался ближе к низкому.

## Задачи

      ветвятся по `(p1_b, 1-p1_b)`, переходы внутри сегмента (R-нетерпение,

## Результаты

Предварительная оценка «средний риск» подтвердилась по объёму нового понимания
(нужна была новая конструкция, не чистое переиспользование, как в EPIC-070), но
не по сложности реализации: благодаря безпамятности H2 на границе батчей каждый
новый батч впереди начинает жизнь заново, так что не нужно накапливать слои —
достаточно 3 статичных сегментов на `(R, K)`. Независимый DES подтвердил точность
при настоящем ветвлении (`p1=0,3`, `mu1≠mu2`) на двух конфигурациях `(a,b)`,
включая вырожденный случай `a=1`. Точная регрессия к `BulkServiceMM1Calc` при
`p1=1` и `gamma>0` совпала до `float64`-точности. Закрывает вторую из трёх
резервных комбинаций, отмеченных в «Ограничениях» Статьи 1
(`docs/статьи/batch-service-sla-single/`); остаётся EPIC-072 (несколько каналов +
фазовое/batch-size-зависимое обслуживание, Статья 2).
