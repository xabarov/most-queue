# EPIC-025: M/M/2 с приоритетами и гетерогенными серверами

- **Статус:** done (2026-09-29)
- **Создан:** 2026-09-29
- **Roadmap:** [../roadmaps/priority_heterogeneous_servers_roadmap.md](../roadmaps/priority_heterogeneous_servers_roadmap.md)

## Цель

Точный (усечённая CTMC, не приближение) калькулятор для M/M/2 с **двумя приоритетными классами**
(preemptive, класс 0 — высший) и **гетерогенными серверами** (`mu_a ≠ mu_b`) — соединение техники
расщепления состояния из EPIC-023 (Krishnamoorthi) с уже существующим приоритетным стеком
(`MMkPriorityExact` как гомогенный эталон для редукции).

## Контекст

Обзор литературы: [../research/priority-heterogeneous-servers-2026.md](../research/priority-heterogeneous-servers-2026.md).
Направление выбрано как альтернатива queueing-inventory при выборе EPIC-024, отложено и
реализуется сейчас. Прямой первоисточник: *Analysis of a Pre-Emptive Two-Priority Queuing System
with Impatient Customers and Heterogeneous Servers*, Mathematics, 2023, doi:10.3390/math11183878.

Ключевая сложность: при экспоненциальном обслуживании состояние `(n_0, n_1)` (число заявок
каждого класса) почти достаточно — как в уже существующем `MMkPriorityExact` — но не совсем: при
`n_0∈{0,1}` неоднозначно, **какой именно** сервер (быстрый A или медленный B) занят, а от этого
зависит скорость перехода. Решение — программное построение цепи через примитивы
`canonicalize`/`class0_arrival`/`class1_arrival`/`departure` (см. roadmap §2), а не ручной вывод
каждого перехода — резко снижает риск ошибки при таком ветвлении по сравнению с ручной матрицей.

## Задачи

### Ядро: усечённая CTMC

      `MM2PriorityHeterogeneousCalc(truncation=...)`, `set_sources(l=[l0,l1])`,

      PriorityResults` (per-class `v`/`w`; `w = v - E[S_i]`, где `E[S_i]` получен через закон

## Критерии готовности (DoD эпика)

Общий DoD — [../DOD.md](../DOD.md). Специфично:

1. При `mu_a = mu_b` результат точно совпадает с `MMkPriorityExact(n=2, ...)` (не просто близко —
   до точности усечения обеих моделей).
2. Инвариант потокового баланса выполняется с ошибкой < 1e-9.
3. Против DES — в пределах стандартного допуска репозитория.
4. Документация (EN+RU) на месте.

## Результаты

Реализовано по плану ([roadmap](../roadmaps/priority_heterogeneous_servers_roadmap.md)). Кратко:

- **Ядро:** `MM2PriorityHeterogeneousCalc` (`theory/priority/preemptive/mm2_heterogeneous.py`) —
  усечённая CTMC, построенная механически через четыре примитива (`_canonicalize`,
  `_class0_arrival`, `_class1_arrival`, `_departure`) вместо ручного вывода каждого перехода —
  решение, принятое именно из-за высокого ветвления состояний (см. research-доку). Решается через
  `ctmc_stationary` (переиспользование EPIC-023). `E[S_i]` для декомпозиции `V=W+S` получен через
  закон Литтла на «заявках класса i в обслуживании», не через допущение о единой ставке на класс.
- **Проверка:** точная редукция к `MMkPriorityExact(n=2,...)` при `mu_a=mu_b` (совпадение до
  ~1e-10 на трёх наборах параметров); инвариант потокового баланса (~1e-15); малые ручные
  сценарии из roadmap §3 как юнит-тесты примитивов — все совпали с первой попытки, подтверждая,
  что механическое построение избежало ошибок, ради которых оно было выбрано.
- **Sim + кросс-валидация:** `MM2PriorityHeterogeneousSim`
  (`most_queue/sim/priority_heterogeneous.py`) — напрямую переиспользует те же четыре примитива
  (импорт, не копирование), гарантируя согласованность теории и симуляции по построению.
- **Документация:** новая секция в `docs/models/priority-dynamic.md`+`.ru.md`, README/README.ru.md,
  `docs/models.md`/`.ru.md`.
- **Тесты:** полный прогон `tests/` — **540 passed, 0 failed** (951s), регрессий нет.
- **Резерв на будущее:** нетерпение (impatience), accumulating priority + гетерогенные серверы,
  k>2 гетерогенных сервера — не реализовано.
