# EPIC-069: Bulk-service с `c>1` независимыми серверами

- **Статус:** done
- **Создан:** 2026-10-06
- **Завершён:** 2026-10-06
- **Roadmap:** [../roadmaps/batch_service_sla_exact_tail_part2_roadmap.md](../roadmaps/batch_service_sla_exact_tail_part2_roadmap.md) (направление A2, закрыто)

## Цель

Обобщить `BulkServiceMM1Calc` (сейчас — ровно один сервер) на `c>1` ИДЕНТИЧНЫХ независимых
серверов с ОБЩЕЙ очередью — прямое попадание в реальную multi-GPU LLM-serving архитектуру (пул
реплик, у каждой свой continuous-batching движок, общий роутер запросов перед пулом).

## Решённые открытые вопросы конструкции

1. **Правило диспетчеризации.** Зафиксировано: когда хотя бы один сервер свободен, батч
   стартует МГНОВЕННО, как только очередь достигает `a` — той же конвенцией, что и `i=0`-состояние
   `BulkServiceMM1Calc`. Поскольку заявки приходят по одной, idle-dispatch batch всегда РОВНО
   размера `a` (переполнить порог одной заявкой за раз нельзя). Отсюда встроенный инвариант
   состояния: `idle_count >= 1 ⟹ j < a` — несколько серверов МОГУТ одновременно простаивать,
   ожидая, пока общая очередь дотянет до `a`.
2. **Представление состояния.** Вектор занятости `(n_1,...,n_b)` — сколько серверов заняты
   батчем размера `s`, для `s=1..b` (`idle_count = c - Σn_s`), скрещенный с `j` (ожидающие в общей
   очереди). Перечисление векторов занятости (`_enumerate_occupancy`) — `compositions(≤c, b
   частей)`, управляемо для практических `c,b` (≤6-8).
3. **Масштаб первой версии — подтверждено.** Реализован чисто экспоненциальный случай
   (`mu` может зависеть от размера батча ТОЛЬКО для `_solve_pi()`/`get_n_moments()` — точные
   `get_w()`/`get_tail()` требуют `mu` батч-размер-НЕЗАВИСИМОЙ, см. ниже).

## Ключевая находка при выводе `get_w()`/`get_tail()`

Первоначальная оценка roadmap'а («гонка среди потенциально многих конкурентных экспоненциальных
часов, каждый сервер со своим размером батча») оказалась ИЗБЫТОЧНО пессимистичной для
батч-размер-НЕЗАВИСИМОГО `mu`: поскольку все `c` серверов — экспоненциальные (безpамятные),
АГРЕГИРОВАННАЯ ставка «следующее освобождение» среди всех `c` занятых серверов всегда РОВНО
`c·mu`, НЕЗАВИСИМО от того, какие конкретно размеры батчей они сейчас обслуживают (пока
`idle_count` остаётся 0, т.е. свободный сервер тут же забирает новый батч). Это означает: ожидание
помеченного клиента (при всех `c` занятых) требует ВООБЩЕ не отслеживать вектор занятости — число
клиентов впереди (`R`) убывает на `b` при каждом событии-с-исключением со ставкой `c·mu`, что
ТОЧНО совпадает с «ahead»-сегментом `most_queue.theory.batch._idle_refill.abandonment_chain`
(EPIC-068) при `gamma=0` (без нетерпения) и ОДНОЙ ставкой на всём протяжении (нет различия
«первый сегмент vs последующие», поскольку нет понятия «застигнутый батч» — любой из `c`
одинаковых безpамятных серверов может освободиться следующим). Конструкция ПЕРЕИСПОЛЬЗОВАНА
как есть, без переписывания. Для батч-размер-ЗАВИСИМОГО `mu` агрегированная ставка ДЕЙСТВИТЕЛЬНО
зависит от полного вектора занятости — настоящий взрыв размерности, вынесено в резерв
(`_require_constant_mu`, `NotImplementedError` с объяснением).

## Найденная и исправленная ошибка (в существующем, не новом коде)

`abandonment_chain` (из EPIC-068) никогда не вызывался с `gamma=0.0` НАПРЯМУЮ — все вызовы в
EPIC-068 замыкались раньше (`if gamma<=0: return 0.0`). Этот эпик — первый вызывающий код,
реально передающий `gamma=0.0` в конструкцию. При `gamma=0` некоторые idle-состояния цепи
(`total = r_val+1+k_val >= a`, недостижимые при данном `a`, например ВСЕ idle-состояния при
`a=1`) получают нулевую строку в разреженной матрице (нет ни исходящих переходов, ни
диагонали — универсальный `out_rate[s]+=gamma` при `gamma>0` маскировал эту проблему), что
делает `(-A)` точно вырожденной для формулы моментов (`spla.spsolve` в цикле). Хвост
(`expm_multiply`) переносил вырожденность без ошибки — что и спрятало проблему до этого эпика.
**Исправлено** в `_idle_refill.py`: недостижимые (доказуемо изолированные — ни входов, ни
выходов) строки с нулевым `out_rate` получают произвольную позитивную диагональ (`out_rate[s]=1`)
— не меняет результат ни для одного достижимого состояния, подтверждено полным повторным
прогоном тестов EPIC-068 (19/19 прошли без изменений).

## Валидация

- `get_n_moments()`: DES (`a,b,c` варьируются) — совпадает в пределах 0.3-4%, включая
  батч-размер-зависимый `mu`.
- `c=1` регрессия: `get_n_moments`/`get_w`/`get_tail` — точное совпадение (`rtol=1e-9`) с
  `BulkServiceMM1Calc`.
- `get_w()`/`get_tail()` при `c>1`: независимый DES (запись времени ДИСПЕТЧЕРИЗАЦИИ, не
  завершения батча — тот же урок про wait-vs-sojourn, что и в EPIC-068/043) — совпадает в
  пределах 5% по моментам, `diff/SE < 2.3` по хвосту на нескольких `t`.

## Что НЕ сделано (осознанный резерв)

- `get_w()`/`get_tail()` для батч-размер-ЗАВИСИМОГО `mu(size)` — требует отслеживать полный
  вектор занятости внутри поглощающей цепи (настоящий, а не кажущийся, взрыв размерности).
  `get_w`/`get_tail` явно кидают `NotImplementedError` с объяснением, а не дают молча неверный
  ответ.
- Erlang/H2-подогнанное время обслуживания батча для `c>1` — не начато, отдельный потенциальный
  под-эпик, если оправдано практикой.
- Включение результата в текст статьи (`docs/статьи/batch-service-sla/`) — не выполнено,
  numerical experiment не проводился; калькулятор доступен как готовый инструмент.

## Критерии готовности (DoD эпика)

Общий [DoD](../DOD.md). Выполнено: `c=1` точная регрессия; независимая DES-валидация `E[N]`,
`W`-моментов и хвоста для `c>1`, несколько `(a,b,c)`; полный набор тестов проходит;
pylint/black/isort чисты.
