# EPIC-043: Точные моменты (не только среднее) для фазово-расширенных CTMC

- **Статус:** done
- **Создан:** 2026-09-30

## Цель

`BulkServiceErlangCalc`/`BulkServiceH2Calc` (EPIC-035/036), `MMcQueueingInventoryHeterogeneousCalc`
(EPIC-038), `MMcQueueingInventoryHeterogeneousH2Calc` (EPIC-039) сейчас дают только среднее
`E[V]`/`E[W]`. Нужны точные вторые (и выше) моменты — по аналогии с тем, как EPIC-032 добавил
точные моменты поверх исходного (экспоненциального) `BulkServiceMM1Calc`.

## Контекст

Кандидат №4 из очереди 2026-09-30. Скоуп сознательно сужен до ОДНОЙ, самой простой модели —
`BulkServiceErlangCalc` при `a=1` — вместо попытки покрыть все фазово-расширенные калькуляторы
сразу. PASTA-аргумент EPIC-032 переносится почти механически: прибывающий видит стационарное
`(i, фаза p, j)`; если сервер занят, его ожидание — ОСТАВШЕЕСЯ обслуживание текущего батча
(`Erlang(k-p, rate)`, k-p ещё не пройденных фаз) плюс `j//b` полных батчей впереди (каждый всегда
размера ровно `b`, т.к. батчи обслуживаются FCFS порциями по `b`, пока остаётся меньше `b`),
каждый `Erlang(k, rate(b))`, свёрнутые через `conv_moments`.

## Результаты

`BulkServiceErlangCalc` (`most_queue/theory/batch/bulk_service_erlang.py`) теперь даёт ТОЧНЫЕ
моменты `W` при `a=1` через новый метод `get_w(num=4)`, по аналогии с `BulkServiceMM1Calc.get_w()`
(EPIC-032). Рефакторинг: `run()` разделён на `_solve_pi()` (кэшируемое решение CTMC) + `run()`
(вызывает `get_w()` при `a=1`, иначе — старое приближённое среднее при `a>1`) — тот же паттерн,
что и в `BulkServiceMM1Calc`.

**Найдена и исправлена ошибка ПРИ ВАЛИДАЦИИ (не в финальном коде, но стоит зафиксировать урок):**
первая попытка сверки с независимой DES сравнивала теоретические моменты `W` (время ожидания,
до старта СВОЕГО батча) с DES-выборкой времени от прихода до ЗАВЕРШЕНИЯ батча (то есть с
sojourn time `V`, не `W`) — выглядело как грубая ошибка теории (среднее разошлось в разы), пока
не обнаружилось, что DES записывал не то время. После исправления DES (фиксировать момент старта
батча, а не его завершения) всё сошлось. Урок: при валидации через DES всегда явно проверять, ЧТО
именно измеряет симуляция, а не только что теория «не сходится».

**Валидация:** `k=1` (Erlang→Exponential) даёт ТОЧНОЕ (до `1e-9`) совпадение со всеми 4 моментами
`BulkServiceMM1Calc.get_w()` — сильнейшая возможная регрессионная проверка (не просто среднее, а
все моменты сразу); `k=2,3` сверены с независимой DES по первым трём моментам — совпало в
пределах Monte Carlo допуска.

**Тесты:** 4 новых теста (точная регрессия к `BulkServiceMM1Calc`, DES cross-validation при k=2,3,
отклонение `a>1`). Полный набор тестов (вместе с EPIC-040/041/042): 769 passed, 0 failed (410s,
`pytest tests/ -n auto`).

**Резерв (не в этом эпике):** перенос той же техники на `BulkServiceH2Calc` (H2 не имеет
«оставшихся фаз» в том же смысле — ветвь фиксирована с начала обслуживания, потребует немного
другого аргумента: «оставшееся время текущей ветви» — Exp, memoryless, проще, чем Erlang!
вероятно даже легче перенести, чем казалось); `MMcQueueingInventoryHeterogeneousCalc`/
`MMcQueueingInventoryHeterogeneousH2Calc` (queueing-inventory) — не пробовалось вовсе, другая
структура состояния (busy-subset, а не просто фаза текущего батча); batch-size-зависимые
параметры (EPIC-042) в сочетании с точными моментами — совместимость не проверялась.
