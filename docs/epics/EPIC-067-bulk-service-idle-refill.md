# EPIC-067: Idle-refill — точные W-моменты и хвост bulk-service при `a > 1`

- **Статус:** done
- **Создан:** 2026-10-06
- **Roadmap:** [../roadmaps/batch_service_sla_exact_tail_part2_roadmap.md](../roadmaps/batch_service_sla_exact_tail_part2_roadmap.md) (направление A1)

## Цель

Снять единственное явно обозначенное ограничение EPIC-032/035/036/043/066: точные
`get_w()`/`get_tail()` для batch-service очередей (`BulkServiceMM1Calc`,
`BulkServiceErlangCalc`, `BulkServiceH2Calc`) были доказаны и реализованы только для
`a=1` (нет нижнего порога запуска пакета). Реальная general bulk-service rule
допускает `a>1` (сервер ждёт накопления минимум `a` заявок перед стартом батча) — уже
поддержано в построении стационарного распределения `pi` всех трёх калькуляторов, но
не в PASTA-разложении времени ожидания.

## Контекст

Прошлая попытка (до EPIC-032, зафиксировано в его docstring и в
`docs/research/bulk-service-waiting-moments-2026.md`) уже пробовала наивное решение:
считать, что после полных батчей впереди остаток либо сразу формирует батч тагнутого
клиента, либо ждёт `need = a - remainder - 1` ДОПОЛНИТЕЛЬНЫХ приходов строго ПОСЛЕ
того, как батчи впереди отработают — т.е. трактовать это как ещё одну
последовательную Erlang-фазу. Эта версия подтверждена численно НЕВЕРНОЙ (~18% ошибка
на среднем при `a=2`) и поэтому `get_w()`/`get_tail()` явно кидали `ValueError` при
`a>1`.

## Находка: почему наивная версия неверна

Наивная версия предполагает, что НИКАКИЕ новые приходы не случаются, пока батчи
впереди ещё обслуживаются — но это неверно: заявки продолжают приходить (и
учитываются к порогу `a`) ПОКА идёт обслуживание текущего/впередиидущих батчей.
Истинная динамика — это ГОНКА между «обслуживание впередиидущей части завершается»
(ставка `mu`) и «пришла ещё одна заявка» (ставка `lambda`), а не чистая
последовательная композиция. Подробная рефутация — численная трассировка по
состояниям `(i,j)` против независимого симулятора: наивная формула давала ошибку
17–30% именно в состояниях, где нужен рефилл, и точное совпадение (<1%) там, где
рефилл не нужен (`docs/roadmaps/...` roadmap, раздел «Находка»).

## Корректная конструкция

2-мерная поглощающая CTMC, пересекающая «какая фаза обслуживания идёт сейчас» (для
MM1/Erlang — позиция в последовательности `rate(i)`, затем `rate(b)` повторено
`full_ahead` раз; для H2 — то же самое, но с ветвлением на каждом батче впереди) с
«сколько из нужных `need` дополнительных приходов уже случилось» (0..need, с
насыщением — приходы сверх `need` ничего не меняют). ВАЖНО: счётчик приходов
пересекается со ВСЕМИ фазами обслуживания (включая самую первую, текущую), не только
с последней — первая реализация для H2 ошибочно считала приходы только во время
последнего (ветвящегося) слоя и подтверждена неверной (~20% ошибка) тем же методом
трассировки по состояниям, что и исходная наивная версия, до того как тест её поймал.

Из последней фазы: если счётчик уже достиг `need` — поглощение сразу по завершении
фазы (по безпамятности экспоненты, остаток уже не важен). Если нет — переход в
чистый Erlang(`need - count`, `lambda`) рефилл-хвост.

Общая конструкция вынесена в `most_queue/theory/batch/_idle_refill.py::race_subgen`
(последовательный случай, переиспользуется MM1 и Erlang — Erlang просто передаёт
полную последовательность фазовых ставок `[rate(i)]*(k-p) + [rate(b)]*(k*full_ahead)`
вместо «одна ставка + ставка». H2 использует отдельную (ветвящуюся) версию
`BulkServiceH2Calc._tagged_wait_tail_with_refill`, не обобщённую в `_idle_refill.py`.

Моменты (`get_w`) считаются общей формулой фазового распределения
`E[T^n] = n! * alpha @ (-A)^-n @ 1` (через `scipy.sparse.linalg.spsolve`, итеративно),
хвост (`get_tail`) — тем же `expm_multiply` на разреженном подгенераторе, что и
остальной EPIC-066-стек.

## Результаты

Реализовано и провалидировано:

- **Лемма**: `get_w()`/`get_tail()` теперь точны для ЛЮБОГО `1<=a<=b` на всех трёх
  калькуляторах (`BulkServiceMM1Calc`, `BulkServiceErlangCalc`, `BulkServiceH2Calc.get_tail`).
- **Общий инструмент**: `most_queue/theory/batch/_idle_refill.py::race_subgen` —
  переиспользуемая race-aware конструкция подгенератора для последовательного
  (неветвящегося) случая, используется MM1 и Erlang.
- **Две реальные ошибки пойманы ДО релиза, обе через независимую DES-валидацию по
  состояниям, не просто агрегированную**:
  1. Наивная «последовательный рефилл» гипотеза (сама цель эпика) — 17–30% ошибка,
     найдена ДО написания race-aware кода (документировано выше).
  2. Первая реализация race-aware конструкции для H2 ошибочно пересекала счётчик
     приходов только с ПОСЛЕДНИМ (ветвящимся) слоем обслуживания, а не со всеми —
     молча теряя приходы, случившиеся во время более ранних фаз. Ошибка ~20% на
     конкретном состоянии (`a=2,b=2`), найдена той же техникой трассировки по
     состояниям против независимого симулятора, исправлена до того как тест,
     видевший только агрегированные моменты, успел бы её пропустить на менее
     чувствительном наборе параметров.
- `run()` всех трёх калькуляторов больше не содержит приближённую mean-only ветку для
  `a>1` (MM1, Erlang) — везде точный `get_w()`.
- Новые тесты: `test_a_gt_1_w_vs_sim` (против официального `BulkServiceSim`),
  `test_get_w_matches_independent_monte_carlo_at_a_gt_1`,
  `test_get_tail_matches_independent_monte_carlo_at_a_gt_1` (MM1, Erlang, H2 —
  параметризованы по нескольким `(a,b[,k])`), заменили прежние
  `test_*_rejects_a_greater_than_one`.
- Полный `pytest tests/ -m "not slow" -n auto` — 1841 passed. pylint 10.00/10 на всех
  изменённых модулях (`bulk_service.py`, `bulk_service_erlang.py`, `bulk_service_h2.py`,
  `_idle_refill.py`). black/isort чисты.

**Следующий шаг:** нет открытых хвостов по этому эпику. Резерв на будущее (не часть
этого эпика) — `get_w` (точные моменты, не только хвост) для H2 остаётся
нереализованным (как и при `a=1`, EPIC-035/043 не покрывали H2); обобщение
`_idle_refill.race_subgen` до поддержки ветвящихся цепей (объединив с H2's отдельной
реализацией) — чисто рефакторинговый резерв, не меняет корректность.
