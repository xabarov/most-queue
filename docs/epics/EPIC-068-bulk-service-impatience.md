# EPIC-068: Нетерпеливые заявки (impatience/reneging) в batch-service

- **Статус:** proposed
- **Создан:** 2026-10-06
- **Roadmap:** [../roadmaps/batch_service_sla_exact_tail_part2_roadmap.md](../roadmaps/batch_service_sla_exact_tail_part2_roadmap.md) (направление A4)

## Цель

Добавить нетерпеливые заявки (экспоненциальное время терпения, по конвенции уже
существующего `most_queue.theory.impatience.mm1.MM1Impatience` — параметр `gamma`,
марковское/безpамятное abandonment) к `BulkServiceMM1Calc`/`BulkServiceErlangCalc`/
`BulkServiceH2Calc`. Мотивация для статьи: в реальном GPU/LLM-serving запрос, не
дождавшийся своего дедлайна, обычно не ждёт бесконечно — его отменяют или
перенаправляют. Текущая статья считает `P(W>D)`, но не что происходит с запросом
дальше; добавление ухода по терпению даёт более реалистичную модель и новую,
практически значимую величину: точную вероятность того, что запрос будет ОТМЕНЁН до
начала обслуживания, не только что он будет ждать дольше `D`.

## Почему это следующий кандидат (а не A2/A3)

Из резерва после EPIC-067 (idle-refill) оставались: A2 (`c>1` серверов), A3
(MAP-вход), A4 (нетерпеливые заявки), C3 (седловая точка). A2 — отдельный полноценный
эпик уровня EPIC-033/038/041 вместе взятых (новая state-space конструкция под
несколько независимых серверов), слишком большой для доработки текущей статьи. A3
ломает PASTA и требует принципиально другой техники (кандидат на ОТДЕЛЬНУЮ будущую
статью, не текущую). C3 — уровень отдельного исследования (Крамер-Лундберг для новой
модели). A4 — единственный кандидат, который:

1. **Низкий риск для стационарного распределения.** Уход по терпению добавляется как
   ОДНА новая транзиция `(i,...,j) -> (i,...,j-1)` со ставкой `j*gamma` (каждый из `j`
   ожидающих независимо теряет терпение) — механически идентично уже существующей
   конвенции `MM1Impatience`/`theory/impatience/mmn.py`, не требует новой размерности
   состояния.
2. **Прямое переиспользование конструкции EPIC-067.** Вероятность того, что
   ПОМЕЧЕННЫЙ клиент уйдёт по терпению до начала своего батча, — это та же самая
   phase-type/race цепь (idle-refill подгенератор `_idle_refill.race_subgen` и
   ветвящаяся H2-версия), но с ДОПОЛНИТЕЛЬНЫМ конкурирующим выходом по ставке `gamma`
   из КАЖДОГО состояния цепи (тагнутый клиент прерывается, если его личные часы
   терпения сработают раньше поглощения). Площадка для ошибок та же, что уже один раз
   поймана в EPIC-067 (нельзя забыть учесть `gamma`-выход на ВСЕХ фазах, не только на
   последней) — явный чеклист на этапе реализации.
3. **Новая, нетривиальная для статьи величина**, не покрытая ни одной из цитируемых
   работ (ни Inoue 2021, ни линия Banerjee/Gupta, ни Claeys et al. 2013 не
   рассматривают уход по терпению вместе с batch-size-зависимым обслуживанием).

## Предварительный набросок конструкции

- `_solve_pi()` во всех трёх калькуляторах: добавить `if j>=1: add(s, <j-1>, j*gamma)`
  в состояниях busy и idle (ожидающие теряют терпение независимо от того, идёт
  обслуживание или нет).
- `get_w()`/`get_tail()`: не меняются по смыслу (всё ещё точное `W` для тех, кто
  ДОЖДАЛСЯ) — НО стационарное `pi`, по которому они усредняют, теперь уже учитывает
  отток по терпению, так что оценка автоматически становится point estimate условно
  на «не ушёл».
- Новая величина `get_abandonment_prob()` (или `get_reneging_prob()`): вероятность,
  что ПОМЕЧЕННЫЙ клиент уходит по терпению до начала своего батча — та же
  subgenerator-конструкция EPIC-067, но с добавленным конкурирующим `gamma`-выходом
  из каждого состояния; считается как `1 - P(поглощение по батчу)` через тот же
  `(-A)^-1`/`expm_multiply` аппарат.

Общий [DoD](../DOD.md) + контракт выше. Обязательно: регрессия `gamma=0` точно
совпадает с EPIC-067; DES-валидация `gamma>0` для всех трёх калькуляторов.
