# EPIC-068: Нетерпеливые заявки (impatience/reneging) в batch-service

- **Статус:** done (MM1/Erlang — полная поддержка; H2 — только уровень `pi`, см. «Что НЕ сделано»)
- **Создан:** 2026-10-06
- **Завершён:** 2026-10-06
- **Roadmap:** [../roadmaps/batch_service_sla_exact_tail_part2_roadmap.md](../roadmaps/batch_service_sla_exact_tail_part2_roadmap.md) (направление A4, закрыто)

## Цель

Добавить нетерпеливые заявки (экспоненциальное время терпения, по конвенции уже
существующего `most_queue.theory.impatience.mm1.MM1Impatience` — параметр `gamma`,
марковское/безpамятное abandonment) к `BulkServiceMM1Calc`/`BulkServiceErlangCalc`/
`BulkServiceH2Calc`. Мотивация для статьи: в реальном GPU/LLM-serving запрос, не
дождавшийся своего дедлайна, обычно не ждёт бесконечно — его отменяют или
перенаправляют. Новая величина `get_abandonment_prob()` даёт точную вероятность того,
что запрос будет ОТМЕНЁН до начала обслуживания своего батча.

## Почему первоначальный набросок оказался неверным

Предварительный набросок (см. ниже «Задачи») предполагал, что достаточно взять
RACE-цепь EPIC-067 и добавить ОДИН конкурирующий выход по ставке `gamma` из каждого
состояния. Это оказалось **неверной гипотезой**, подтверждённой независимой
симуляцией: количество клиентов, стоящих ПЕРЕД помеченным (`R`, у EPIC-067 это был
детерминированный остаток `j`), при наличии abandonment само становится процессом
СМЕРТИ (каждый из `R` выживших впереди независимо теряет терпение), идущим
ОДНОВРЕМЕННО с формированием батчей — а не фиксированной величиной. Простая
гипотеза («race-цепь EPIC-067 + отдельный конкурирующий gamma-выход») давала ошибку
17–38% на разных состояниях против независимой симуляции одного помеченного клиента.

**Ключевой структурный факт (доказан, не просто проверен численно):** если батч
формируется БЕЗ помеченного клиента, его размер всегда РОВНО `b` (доказательство от
противного: если `total = R+1+K <= b`, то `take = total >= R+1`, то есть батч
обязательно включает помеченного; значит исключение возможно только при `total > b`,
и тогда `take = b`). Это держит конструкцию трактуемой: нужны только ДВЕ ставки
(`rate_first` — оставшиеся фазы наблюдаемого батча, `rate_ahead = rate_fn(b)` — все
последующие полноразмерные батчи впереди), в точности как в EPIC-067, плюс
дополнительная размерность состояния `(R, K)`: `R` — выжившие впереди (0..j, убывает
через abandonment и через полные batch-takes), `K` — новые приходы ПОЗАДИ помеченного
(0..a-1, захват выше `a-1` не нужен — доказано, что исход уже не зависит от `K` после
этого порога, см. `most_queue.theory.batch._idle_refill.abandonment_chain`).

## Реализация

- **`most_queue/theory/batch/_idle_refill.py`**: новая функция `abandonment_chain(...)`
  — race-aware поглощающая цепь `(segment, phase, R, K)`, с универсальным
  конкурирующим выходом `gamma` (личные часы терпения помеченного) на каждой фазе.
  Возвращает `(subgen, m, start, serve_rate)`: `serve_rate` — вектор ставок перехода
  в «обслужен», нужен для условных моментов `W`.
- **`BulkServiceMM1Calc`/`BulkServiceErlangCalc`**: `gamma` в `__init__` (валидация
  `>= 0`); `_solve_pi()` — добавлен отток `j*gamma` в busy/idle состояниях; новый
  `get_abandonment_prob()`; `get_w()`/`get_tail()` при `gamma>0` делегируют в
  `_get_w_with_abandonment`/`_get_tail_with_abandonment` — точные моменты/хвост `W`
  УСЛОВНО на «дождался» (нормировка на `1 - get_abandonment_prob()`).
- **`BulkServiceH2Calc`**: только `gamma`-отток в `_solve_pi()` — см. «Что НЕ сделано».

## Найденная и исправленная ошибка (до поставки)

Формула момента фазового типа с отдельным «serve_rate»-вектором награды требует
`n+1` применений `(-A)^-1` для `n`-го момента (`E[W^n; served] = n! * alpha @
(-A)^-(n+1) @ serve_rate`), а не `n` (как для безусловной формулы `n! * alpha @
(-A)^-n @ 1` при `gamma=0`, где нет отдельного вектора награды). Первая версия
`_get_w_with_abandonment` ошибочно делала только `n` применений — из-за этого
`numerator` в первом (`n=1`) моменте численно совпадал с `p_served_state`, и
`get_w()` оказывался в ~2 раза БОЛЬШЕ истинного значения (поймано full-system
DES-тестом при `a=1`: теория 0.296 vs DES 0.156). Исправлено добавлением одного
`spla.spsolve` ПЕРЕД циклом в обоих калькуляторах (MM1 и Erlang — одна и та же
ошибка была скопирована в обоих файлах).

Также при ad-hoc отладке (не в финальном коде библиотеки) был переоткрыт тот же
класс ошибки, что уже встречался в EPIC-067: «протухшие часы терпения» — при
исключающем батче (`take=b`) нужно убрать ровно `take` записей из списка ожидающих
с СОХРАНЕНИЕМ порядка очереди (FCFS), а не отсортировав их по времени abandonment
(иначе систематически выбирается смещённое подмножество выживших). Это была ошибка
отладочного скрипта, не библиотеки, но подтверждает: эта площадка для ошибок
регулярно всплывает заново и должна быть в чеклисте для будущих похожих эпиков.

## Валидация

- **MM1** (`tests/units/test_bulk_service_abandonment.py`): regression `gamma=0`;
  full-system DES (arrival-indexed, без censoring) для `get_abandonment_prob()`,
  `get_w()`, `get_tail()` при нескольких `(a,b)`; монотонность по `gamma`.
- **Erlang** (`tests/units/test_bulk_service_erlang_abandonment.py`): САМАЯ сильная
  проверка — `k=1` должно ТОЧНО (`rtol=1e-9`) совпадать с `BulkServiceMM1Calc` для
  `get_abandonment_prob`/`get_w`/`get_tail` (общая конструкция
  `abandonment_chain`, но разные call sites — без MC-шума). Для `k>1` —
  full-system DES с ЗАМЕТНО более широкими допусками, чем у MM1: агрегированная
  длинная симуляция страдает от сериальной корреляции между последовательными
  клиентами (эффективный размер выборки намного меньше номинального), что
  подтверждено отдельной ИЗОЛИРОВАННОЙ Monte-Carlo проверкой одного помеченного
  клиента (без автокорреляции), которая совпадала с точной формулой почти без
  погрешности при тех же параметрах, где агрегированный DES показывал устойчивое
  расхождение 1–6%.
- **H2** (`tests/units/test_bulk_service_h2.py`): regression `gamma=0`; E[N] против
  независимого DES с abandonment на уровне `pi` (то, что реализовано).

## Что НЕ сделано (осознанный вынос из объёма эпика)

- **`BulkServiceH2Calc.get_abandonment_prob()`/gamma-aware `get_w()`/`get_tail()`** —
  НЕ реализованы. H2 — не последовательная цепь фаз, а ВЕТВЛЕНИЕ (каждый
  полноразмерный батч впереди заново выбирает свою ветвь p1/p2); `abandonment_chain`
  в текущем виде предполагает последовательные фазы. Перенос потребовал бы
  скрещивать (R, K) с ВЕТВЬЮ каждого слоя впереди, а не только последнего (как уже
  делает `get_tail` при `gamma=0`) — заметно более сложное пространство состояний.
  Зафиксировано как резерв в docstring `bulk_service_h2.py`.
- Точные моменты V (sojourn, не только W) — не входили в объём ни одного из эпиков
  batch-service серии.
- Экспериментальная часть для статьи (численный пример влияния `gamma` на
  эффективный SLA-success) — не выполнялась; `get_abandonment_prob()`/`get_w()`
  доступны как готовый инструмент, если статья решит включить этот пример позже.
