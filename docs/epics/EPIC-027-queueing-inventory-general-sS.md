# EPIC-027: Queueing-inventory, общая политика (s,S)

- **Статус:** done
- **Создан:** 2026-09-29
- **Roadmap:** [../roadmaps/queueing_inventory_general_sS_roadmap.md](../roadmaps/queueing_inventory_general_sS_roadmap.md)

## Цель

Обобщить `MM1QueueingInventoryCalc` (EPIC-024/026) с политики `(0,S)` на **общую `(s,S)`**:
пополнение запаса триггерится при падении до произвольного порога `0 ≤ s < S`, а не только до
нуля.

## Контекст

Обзор литературы: [../research/queueing-inventory-general-sS-2026.md](../research/queueing-inventory-general-sS-2026.md).
Прямое продолжение EPIC-024/026, ранее помеченное в резерве как требующее «дополнительный бит
состояния — заказ уже размещён». При детальном выводе это оказалось избыточным: при
экспоненциальном (без памяти) времени поставки состояние «заказ в пути» полностью определяется
условием `i ≤ s`, так же как в `(0,S)` оно определялось `i = 0`. Единственное изменение — условие
срабатывания пополнения в матрицах `A1`/`B00` (`i==0` → `i≤s`); блокировка обслуживания и триггер
lost-sales остаются завязаны на `i=0` (другой порог, не совпадает с `s`). При `s=0` — точная
редукция к уже реализованной модели.

## Задачи

### Ядро

- [x] `most_queue/theory/inventory/mm1_inventory.py`: `MM1QueueingInventoryCalc.__init__(s_max,
      s: int = 0, policy=..., ...)` — параметр `s` (реордер-точка, по умолчанию 0 — сохраняет
      текущее поведение). В `_build_solver()`: пополнение (`θ`, переход в `S`) активно для всех
      `i ∈ {0,...,s}`, а не только `i=0`; диагональ `A1`/`B00` для `i ∈ {1,...,s}` получает
      слагаемое `θ` в дополнение к уже имеющимся `λ`/`μ` (обслуживание не блокировано при `i≥1`).
      Валидация `0 ≤ s < s_max`.
- [x] Юнит-тесты: **точная редукция** при `s=0` к текущему поведению (regression, а не
      приближённое совпадение); при увеличении `s` (больше safety stock) — `stockout_prob` и
      `E[W]` не растут (интуитивно должны падать или оставаться на месте); `residual()` QBD мал.

## Результаты

Реализовано по плану ([roadmap](../roadmaps/queueing_inventory_general_sS_roadmap.md)). Кратко:

- **Ядро:** `MM1QueueingInventoryCalc`/`MM1QueueingInventorySim` получили параметр `s` (реордер-точка,
  `0 ≤ s < s_max`, по умолчанию `0`). Оказалось, что общая `(s,S)` политика **не требует** новой
  размерности состояния — вопреки резервной заметке из EPIC-024/026: при экспоненциальном времени
  поставки «заказ в пути» полностью определяется условием `i ≤ s`, точно так же, как `i = 0`
  определяло это в частном случае `(0,S)`. Фазовое пространство QBD осталось `i ∈ {0,...,S}`,
  изменился только диапазон активности перехода пополнения в `A1`/`B00` (`i≤s` вместо `i==0`).
  Блокировка обслуживания и триггер потерь в lost-sales остались завязаны на `i=0` (независимый
  порог, не совпадает с `s`).
- **Проверка:** точная редукция при `s=0` к EPIC-024/026 поведению (residual ~1e-16); монотонность
  — больший `s` не увеличивает `stockout_prob`/`E[W]`; малый residual QBD-солвера; кросс-валидация
  против DES-симуляции (s=2, s_max=4).
- **Тесты:** `tests/units/test_mm1_queueing_inventory.py` — 18 passed; `tests/test_inventory.py` —
  3 passed. Полный прогон `tests/` — **553 passed, 1 failed** (883s); упавший тест
  (`test_mgn_with_h2_delay_cold_warm.py::test_mgn_h2_delay_cold_warm`) воспроизводится и на коммите
  до EPIC-027 (проверено через `git stash`) — предсуществующая нестабильность DES-допуска, не
  регрессия этого эпика.
- **Документация:** новые секции «Общая политика (s,S)» в `docs/models/inventory.md`/`.ru.md`
  (EN+RU), таблицы в `docs/models.md`/`.ru.md` обновлены (`(0,S)` → `(s,S)`).
- **Резерв на будущее:** многоканальный queueing-inventory (`c > 1` серверов) остаётся
  нереализованным — см. `docs/research/queueing-inventory-2026.md`. Та же memoryless-lead-time
  логика, вероятно, упрощает и его пространство состояний — стоит проверить перед тем, как
  закладывать дополнительные биты состояния.
