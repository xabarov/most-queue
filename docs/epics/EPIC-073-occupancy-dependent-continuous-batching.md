# EPIC-073: Occupancy-dependent обслуживание с потолком занятости (ядро continuous batching)

- **Статус:** done
- **Создан:** 2026-10-09
- **Завершён:** 2026-10-09
- **Roadmap:** `docs/диссертация/план-моделей.md`, M1 (первый пункт реестра
  частных моделей для направления LLM-serving/document-intelligence)

## Цель

Дать ТОЧНОЕ (не приближённое) распределение времени ожидания для очереди с
occupancy-зависимой (state-dependent) интенсивностью обслуживания и жёстким
потолком одновременной занятости `k` — марковское ядро, которым на практике
является «continuous batching» современных LLM-инференс-движков (vLLM/
SGLang-стиль): до `k` заявок одновременно «активны» (батчатся вместе на одной
итерации декодирования), интенсивность обслуживания КАЖДОЙ зависит от текущей
занятости (разделяемый вычислитель/пропускная способность памяти), потолок `k`
задаётся доступной памятью (KV-cache).

## Обзор литературы и обоснование новизны

Проверено по трём направлениям (ТМО-классика через `.claude/skills/lit-search/`,
классическая литература по computer systems multiprogramming, и современные
2024-2026 работы по LLM-serving queueing — через WebSearch, поскольку они слабо
индексируются arXiv/OpenAlex/Crossref-инструментом).

- **Классическая ТМО:** state-dependent birth-death СМО — известны с 1970-х
  (`Mn/Mn/-/- systems`, Gross & Harris/Kleinrock-линия); сама по себе
  конструкция НЕ нова.
- **Ближайший точный классический результат:** Morrison, J.A. «Sojourn and
  waiting times in a single-server system with state-dependent mean service
  rate» (Queueing Systems, 1989) — точные моменты времени ожидания для
  ОДНОСЕРВЕРНОЙ системы с ДВУХУРОВНЕВОЙ (пороговой) ставкой, плюс отдельная
  работа того же автора для ДВУХсерверного случая. Не обобщено (по нашему
  обзору) на произвольное число серверов/произвольный профиль `mu(occupancy)`.
- **Современная LLM-serving литература (2024-2026):** активная область, но
  везде, где действительно строится СМО-модель occupancy-зависимого
  continuous batching, результат либо приближённый, либо ограничен средним:
  - Ramani & Tantawi, *«An Approximate Queueing Model of LLM Inference
    Serving for SLO-Driven Autoscaling»* (arXiv:2609.20957, 2026) — строит ТУ
    ЖЕ «state-dependent Markov chain for batch occupancy», но явно
    ПРИБЛИЖЁННО (mean-value analysis), даёт только СРЕДНИЕ TTFT/ITL (валидация
    против реальных замеров — 5-16% ошибка).
  - Yang, Xu, Jiao, *«A Queueing Theoretic Perspective on Low-Latency LLM
    Inference with Variable Token Length»* (arXiv:2407.05347, 2024) — M/G/1 +
    bulk queue, среднее время ожидания для трёх стратегий батчинга; batch-size-
    зависимое время обслуживания (ближе к уже имеющемуся в most-queue
    bulk-service, не к occupancy-зависимой ставке).
  - Nie, Si, Zhou, *«A Queueing-Theoretic Framework for Stability Analysis of
    LLM Inference with KV Cache Memory Constraints»* (arXiv:2605.04595, ICML
    2026) — условия устойчивости/неустойчивости, не стационарное
    распределение времени ожидания.
  - Ao, Dong, Luo, Simchi-Levi, *«Service-Induced Congestion in
    Memory-Constrained LLM Serving»* (arXiv:2606.15555, 2026) — ДЕТЕРМИНИРО-
    ВАННАЯ (не стохастическая) динамическая система, предельные циклы и потеря
    throughput при вытеснении KV-cache; другой математический аппарат
    (fluid/dynamical systems, не CTMC), другой вопрос (устойчивость
    вытеснения, не распределение времени ожидания).

**Вывод по новизне:** ни одна найденная работа не даёт ТОЧНОГО (не
приближённого, не только среднего) распределения времени ожидания для
occupancy-зависимой СМО с потолком занятости при произвольном `k` и
произвольном профиле `mu(occupancy)`. Это и есть зазор, который закрывает
данный эпик — точное обобщение однo-/двухсерверного результата Morrison (1989)
на произвольное `k`, с точными моментами И точным хвостом (не только
моментами), тем же PASTA-аппаратом, что уже многократно применён в
`most_queue.theory.batch`.

## Ключевая аналитическая находка

Цепь по полному числу в системе `j` — обычный (хоть и occupancy-зависимый по
ставке) процесс гибели-размножения: detailed balance выполняется ВСЕГДА для
процессов гибели-размножения, независимо от зависимости ставок от состояния —
поэтому стационарное распределение `pi_j` имеет явную (не итеративную)
произведенную форму. Нетривиальная часть — не это, а то, что занятость ЖЁСТКО
зафиксирована на уровне `k` в любом состоянии `j>=k` (любое завершение
обслуживания немедленно восполняется из очереди, пока она не пуста) — то есть
интенсивность, которую видит помеченная заявка, заставшая `j>=k`, КОНСТАНТНА
(`k*mu(k)`) независимо от профиля `mu` ниже потолка. Отсюда — условное (на
`j>=k`) время ожидания есть ТОЧНЫЙ `Erlang(j-k+1, k*mu(k))`, и безусловное
распределение `W` — явная (вычислимая без усечённого разреженного решения)
смесь эрлангов, взвешенная occupancy-зависимым `pi_j`.

## Задачи

- [x] Точная конструкция: `OccupancyDependentQueueCalc`
      (`most_queue/theory/continuous_batching/occupancy_dependent.py`) —
      `_solve_pi()` (замкнутая форма в лог-пространстве, устойчиво для
      больших `N`), `get_w()`/`get_tail()`/`get_cdf()` (смесь эрлангов),
      `get_n_moments()`, `get_p_wait()`.
  - [x] Регрессия: константный `mu` → точное совпадение (`rtol~1e-9`) с
        классическим `most_queue.theory.fifo.mmnr.MMnrCalc` (M/M/k/N).
  - [x] Регрессия: `k=1` → классический M/M/1/N (та же `MMnrCalc` при `n=1`).
  - [x] Внутренняя согласованность: `∫P(W>t)dt == E[W]` (числ. интегрирование
        хвоста совпадает с моментной формулой с точностью ~1e-4 отн.).
  - [x] Независимая DES-проверка (с нуля, не переиспользующая most_queue) на
        генуинно occupancy-зависимом `mu(occ)=2/(0.5+0.3*occ)`: средняя и
        второй момент времени ожидания совпали в пределах 5%/12% (большой
        объём выборки, 500k заявок).
  - [x] Численная устойчивость: защита от `OverflowError` в
        `math.factorial`/`math.pow` для глубоко усечённых состояний с
        пренебрежимо малой вероятностью (`_NEGLIGIBLE_PROB` cutoff).
  - [x] Тесты (`tests/units/test_occupancy_dependent_queue.py`, 8 тестов).
  - [x] pylint 10/10, black/isort чисты.

## Что сознательно не входит в объём (резерв для M2-M4)

- **Фазовое (не экспоненциальное) время обслуживания** — остаточная длина
  генерации токенов не экспоненциальна в реальности; перенос PASTA+фазового
  аппарата batch-service (EPIC-035/036) на occupancy-зависимую ставку — M2
  в `план-моделей.md`.
- **Растущий во времени ресурсный след заявки** (реальный KV-cache: каждая
  резидентная заявка занимает РАСТУЩИЙ, а не фиксированный объём памяти) —
  здесь `k` зафиксировано и экзогенно; обобщение — M3 (ближайшая существующая
  структура — `most_queue.theory.msj`, multiserver-job).
  Двухфазное prefill/decode обслуживание — M4.
- Нетерпение заявок (`gamma`) — не рассмотрено в этом эпике; естественное
  следующее расширение по аналогии с EPIC-068, отдельный резерв.

## Критерии готовности (DoD эпика)

Общий [DoD](../DOD.md). Обязательно для этого эпика: точная регрессия к
`MMnrCalc` (константный `mu` и `k=1`); независимая DES-валидация на генуинно
occupancy-зависимом `mu`; внутренняя согласованность хвоста и моментов;
обзор литературы с явной фиксацией ближайших конкурирующих результатов
(Morrison 1989; Ramani & Tantawi 2026) и того, чем данный результат точно
отличается (exact vs approximate/mean-only).

## Результаты

Закрыт первый пункт (M1) реестра `докторская/план-моделей.md`. Получено точное
(замкнутая смесь эрлангов, не приближение по методу среднего значения, как в
единственной найденной близкой работе 2026 года) распределение времени
ожидания occupancy-зависимой, ограниченной по занятости СМО — марковского ядра
continuous batching современных LLM-инференс-движков. Результат сводится точно
к классическому `M/M/k/N` при постоянной ставке и к `M/M/1/N` при `k=1`;
подтверждён независимым DES на генуинно occupancy-зависимой ставке. Следующий
шаг по плану — M6 (допуск/расписание с убывающей ценностью, независимая ветка)
и/или M2 (фазовое обобщение этого результата).
