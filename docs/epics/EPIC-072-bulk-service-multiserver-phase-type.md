# EPIC-072: Многоканальный bulk-service с batch-size-зависимым обслуживанием

- **Статус:** done
- **Создан:** 2026-10-07
- **Завершён:** 2026-10-07
- **Roadmap:** резерв EPIC-069 («Что НЕ сделано»: batch-size-зависимое `mu(size)` для
  `c>1`; Erlang/H2-обслуживание для `c>1`)

## Цель

Снять ограничение `BulkServiceMultiserverCalc.get_w()`/`get_tail()` на
batch-size-НЕЗАВИСИМое экспоненциальное `mu(size)` при `n>1` каналах — третья из
трёх резервных комбинаций, отмеченных в «Ограничениях» статьи batch-service-sla.
Erlang/H2-обслуживание при `n>1` сознательно оставлено за рамками (см.
«Что по-прежнему не входит»), как и было предложено в разделе «Предлагаемый
масштаб первой версии» этого же документа.

## Почему это был объявлен высокий риск

EPIC-069 нашёл ключевое упрощение: при batch-size-НЕЗАВИСИМОМ `mu` агрегированная
ставка «следующее освобождение» равна ровно `n*mu` независимо от состава занятости
каналов, поэтому тегированному ожиданию не нужно отслеживать вектор занятости вовсе.
Это упрощение исчезает, как только `mu` зависит от размера батча: агрегированная
ставка генуинно зависит от того, какие именно размеры сейчас обслуживаются каждым
из `n` каналов.

## Что получилось на деле (риск оказался тоньше предполагавшегося)

Опасение при планировании — что понадобится отслеживать ПОЛНЫЙ вектор занятости
внутри поглощающей цепи НА ПРОТЯЖЕНИИ ВСЕГО ожидания, а значит пространство
состояний растёт как «число векторов занятости × R × K» без ограничений сверху,
кроме усечения очереди `N`. На практике нашлось дополнительное структурное
упрощение, не предполагавшееся заранее: отслеживание вектора занятости нужно
ТОЛЬКО пока ВСЕ `n` каналов заняты. В момент, когда освободившийся канал не
может сразу забрать новый батч (накопленного `R+1+K` не хватает до порога `a`),
этот канал простаивает — и с этого момента ДАЛЬНЕЙШИЕ завершения остальных ещё
занятых каналов уже не могут изменить содержимое очереди (канал, завершающий
обслуживание при неизменном числе ожидающих, просто создаёт ЕЩЁ ОДИН простаивающий
канал, а не диспетчеризацию). Поэтому с этого момента действует уже существующая,
не зависящая от занятости гонка ожидания накопления
(`most_queue.theory.batch._idle_refill.abandonment_chain`'s idle-подцепь,
переиспользована без изменений, `gamma` зафиксирована в 0). Это ограничивает
отслеживаемое пространство векторов занятости ТОЛЬКО векторами с суммой РОВНО
`c` (а не `<=c`, как для полного `_solve_pi()`) — заметно меньшее множество,
не зависящее от усечения очереди `N`.

Независимая проверка подтвердила конструкцию на двух конфигурациях `(a,b,c)` при
генуинно batch-size-зависимом `mu(size)=1/(0.3+0.25·size)`: `E[W]` и `P(W>t)`
совпали с независимым DES в пределах статистической погрешности. Регрессия на
КОНСТАНТНОЙ callable `mu` (не `_is_constant_mu`, но возвращающей одно и то же
значение) совпала с результатом EPIC-069 до полной `float64`-точности —
независимое подтверждение, что новая и старая конструкции описывают одну и ту же
систему.

## Задачи

- [x] Зафиксировать точную конструкцию (batch-size-зависимый `mu`,
      экспоненциальный): `_occupancy_busy_chain` на `(occ, R, K)` для `sum(occ)=c`,
      плюс переиспользование существующей occupancy-независимой idle-подцепи.
- [x] Оценить размер пространства состояний: для реалистичных `n` (2-4), `b` (2-4)
      — десятки векторов занятости × `(j+1)·a` — на порядки меньше первоначальной
      оценки «число векторов занятости (`<=c`) × R × K»; дополнительное усечение
      не потребовалось.
- [x] Независимая DES-валидация (`E[W]`, `P(W>t)`) на `(a,b,c) ∈ {(2,4,2), (1,3,3)}`.
- [x] Регрессия: константная callable `mu(size)=const` → точное совпадение
      (`rtol=1e-9`) с уже провалидированным EPIC-069 (скалярный `mu`).
- [x] `get_n_moments()` не затронут (был точен для любого `mu` ещё до EPIC-072).
- [x] Явный `NotImplementedError` для оставшейся нереализованной комбинации
      (batch-size-зависимый `mu` + `gamma>0`), с понятным сообщением.
- [x] Тесты (`tests/units/test_bulk_service_multiserver_dependent_mu.py`, 8 тестов),
      обновлён устаревший тест в `test_bulk_service_multiserver.py` (раньше
      проверял, что зависимый `mu` ОТВЕРГАЕТСЯ — теперь проверяет, что он
      ПОДДЕРЖИВАЕТСЯ при `gamma=0` и по-прежнему отвергается при `gamma>0`).
- [x] pylint 10/10, black/isort чисты; полный набор тестов проходит.
- [x] Документация: docstring модуля, `docs/models/batch.{md,ru.md}`.

## Что по-прежнему не входит в объём

- Erlang-обслуживание при `n>1` — добавляет фазовое измерение к каждому занятому
  каналу; по духу похоже на то, как EPIC-035 добавил фазу к `BulkServiceMM1Calc`,
  но не исследовано здесь. Решение о запуске — отдельный эпик (EPIC-073+), по
  аналогии с тем, как EPIC-071 потребовался отдельно от EPIC-070.
- H2-обслуживание при `n>1` — ветвящаяся структура поверх вектора занятости,
  вероятно комбинация сложностей EPIC-036 и этого эпика; дальнейший резерв.
- Нетерпение (`gamma>0`) в сочетании с batch-size-зависимым `mu` — `_occupancy_
  busy_chain` не несёт переходов по уходу заявок впереди (`R*gamma`); явный
  резерв, не входивший в предложенный масштаб.

## Критерии готовности (DoD эпика)

Общий [DoD](../DOD.md). Обязательно: регрессия к константной callable `mu`
(точное совпадение с EPIC-069); независимая DES-валидация на генуинно
зависимом `mu`; полный набор тестов проходит; pylint/black/isort чисты.

## Результаты

Предварительная оценка «высокий риск, настоящий взрыв размерности состояния»
подтвердилась лишь частично: отслеживание вектора занятости действительно
необходимо (в отличие от EPIC-070/071, где старые конструкции переиспользовались
почти без изменений) — но только на ПОДМНОЖЕСТВЕ режима ожидания (пока все `c`
каналов заняты), а не на всём протяжении, как предполагалось при планировании.
Эта находка — та же закономерность, что уже встречалась в EPIC-070/071 этой
серии: первоначальная оценка риска по размышлению регулярно оказывается
осторожнее фактической сложности реализации. Закрывает третью и последнюю из
трёх резервных комбинаций, отмеченных в «Ограничениях» статьи batch-service-sla
(Статья 2, `docs/статьи/batch-service-sla-multi/`); Erlang/H2 при `n>1` остаются
открытым резервом для возможных будущих эпиков.
