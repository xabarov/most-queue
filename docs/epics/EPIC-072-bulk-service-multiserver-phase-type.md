# EPIC-072: Многоканальный bulk-service с фазовым/batch-size-зависимым обслуживанием

- **Статус:** proposed
- **Создан:** 2026-10-07
- **Roadmap:** резерв EPIC-069 («Что НЕ сделано»: batch-size-зависимое `mu(size)` для
  `c>1`; Erlang/H2-обслуживание для `c>1`)

## Цель

Снять оба оставшихся ограничения `BulkServiceMultiserverCalc.get_w()`/`get_tail()`:
(1) batch-size-ЗАВИСИМое экспоненциальное `mu(size)` при `n>1` каналах; (2)
фазовое (Erlang/H2) обслуживание при `n>1` каналах. Третья из трёх резервных
комбинаций, отмеченных в «Ограничениях» статьи batch-service-sla — и, в отличие от
EPIC-070/071, единственная из трёх, требующая НАСТОЯЩЕГО (не кажущегося) взрыва
размерности состояния.

## Почему это высокий риск

EPIC-069 нашёл ключевое упрощение: при batch-size-НЕЗАВИСИМОМ `mu` агрегированная
ставка «следующее освобождение» равна ровно `n*mu` независимо от состава занятости
каналов, поэтому тегированному ожиданию не нужно отслеживать вектор занятости вовсе.
Это упрощение ИСЧЕЗАЕТ, как только `mu` зависит от размера батча (или от фазы): тогда
агрегированная ставка ГЕНУИННО зависит от того, какие именно размеры/фазы сейчас
обслуживаются каждым из `n` каналов — тегированное ожидание должно отслеживать полный
вектор занятости `(n_1,...,n_b)` (или `(n_1,\varphi_1,...,n_b,\varphi_b)` для фазового
случая) ВНУТРИ самой поглощающей цепи, а не только снаружи (как уже делает
`_solve_pi()`). Это НАСТОЯЩИЙ комбинаторный взрыв: число состояний поглощающей цепи
растёт как (число векторов занятости) × (R) × (K), и этот объект нужно строить заново
для каждого наблюдаемого стационарного состояния `(occ, j)` с ненулевой `pi`.

Структурный аналог в библиотеке: EPIC-038 (queueing-inventory с общим числом `c`
гетерогенных серверов) решал похожую по духу задачу (подмножества серверов,
отслеживание состава) через технику расщепления на подмножества — хороший шаблон
для ОЦЕНКИ подхода, но там заявки обслуживаются поштучно, а здесь — батчами
переменного размера, так что прямого переноса кода не будет, только идеи.

## Предлагаемый масштаб первой версии (сузить риск)

Не пытаться решить сразу оба случая (batch-size-зависимый `mu` и фазовое
обслуживание) — начать с МЕНЬШЕГО из двух:

1. **Сначала**: batch-size-зависимое ЭКСПОНЕНЦИАЛЬНОЕ `mu(size)` при `n>1` (без
   фазы) — вектор занятости `(n_1,...,n_b)` без фазового измерения, ближе по духу к
   уже существующей конструкции `_solve_pi()`, но теперь ВНУТРИ поглощающей цепи.
2. **Потом, если оправдано**: Erlang-обслуживание при `n>1` (добавляет фазовое
   измерение к каждому занятому каналу) — по аналогии с тем, как EPIC-035 добавил
   фазу к уже решённому `BulkServiceMM1Calc`.
3. **H2 при `n>1`** — дальнейший резерв, вероятно отдельный под-эпик (ветвление
   поверх вектора занятости — комбинация сложностей EPIC-036 и этого эпика).

## Задачи (черновой набросок, масштаб уточняется на старте)

- [ ] Зафиксировать точную конструкцию для шага 1 (batch-size-зависимый `mu`,
      экспоненциальный): поглощающая цепь на `(occ, R, K)`.
- [ ] Оценить размер пространства состояний при реалистичных `n` (2-6), `b` (2-8) —
      решить, нужно ли дополнительное усечение/аппроксимация.
- [ ] Независимая DES-валидация ПЕРЕД агрегированной (per-state, по методологии
      EPIC-067/068) — здесь особенно важно, учитывая новизну конструкции.
- [ ] Регрессия: постоянный `mu(size)=const` → точное совпадение с уже
      провалидированным EPIC-069.
- [ ] Решить с пользователем (см. roadmap) — входит ли шаг 2/3 в этот же эпик или
      становится отдельным (EPIC-073+).
