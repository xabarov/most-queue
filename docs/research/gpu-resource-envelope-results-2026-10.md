# Влияние размера GPU пула и эксклюзивных узлов на replay

Дата: 2026-10-02. [Протокол/API](../gpu_resource_envelope.md),
[эпик](../epics/EPIC-060-gpu-resource-envelope.md),
[артефакты](../../works/gpu_resource_envelope/README.md).

Исследуется чувствительность к ресурсу, не реконструкция производственной
capacity. Один и тот же набор jobs проходит через общий GPU-пул или через
эксклюзивное резервирование запрошенных узлов при четырёх заранее заданных
размерах пула. Непомещающиеся jobs не исключаются, а делают ячейку невыполнимой.

**Итог:** меньший пул и эксклюзивные узлы создают ненулевое контрольное ожидание,
но почти не разделяют дисциплины. По observed p99 T все шесть policies равны
во всех 20 допустимых ячейках. Подтверждения выбора production scheduler нет.
Ошибки mean/p99 T с генератором recent-coarse при уменьшении пула могут резко
усиливаться, хотя его service лента между ресурсными сценариями не меняется.

## Наблюдаемость и совместимость записанных интервалов

В Acme/Kalos есть GPU/node requests, но нет per-job node IDs, quota history,
partition membership или ленты available capacity. Число узлов не доказывает
эксклюзивность, а историческое ожидание не определяет единственную capacity.
`queue` — время ожидания, не очередь/квота пользователя.

Для 19 902 пригодных GPU execution-интервалов максимальный отдельный request —
1024 GPU / 128 nodes. Peak одновременных requests — **1536 GPU**, а при
exclusive-node допущении — **268 nodes**. Пики не обязаны приходиться на один
момент. Полный recorded requested work — 5 192 656 394 GPU-seconds;
exclusive reservation — 653 224 227 node-seconds, или 5 225 793 816
GPU-equivalent seconds. Это зарезервированный ресурс, не аппаратная utilization.

| N nodes / GPU inventory | Recorded GPU intervals выше capacity, s | Recorded exclusive-node intervals выше capacity, s |
| --- | ---: | ---: |
| 302 / 2416 | 0 | 0 |
| 226 / 1808 | 0 | 84 |
| 151 / 1208 | 122 | 14064 |
| 113 / 904 | 3443240 | 3443812 |

Совместимость обоих верхних GPU-пулов с записанными интервалами не выбирает
между ними и не восстанавливает квоты. Нижние пулы меняют допустимые старты;
они остаются **контрфактическими** сценариями, а не исправлением исходной трассы.
Пригодные completed имеют historical mean W=281.26 s и p99 W=3960.68 s;
эти величины не использовались как objective настройки и не являются replay reference.

## Зафиксированная матрица

Origins .35/.50/.70 raw submit span. Первые два: 200 warmup+1000 targets;
последний: 100+300. Те же периоды уже использовались ранее; не новый blind test.
Две allocation-модели, N={302,226,151,113}, observed S и один recent-coarse
generator с восемью seeds, шесть неизменённых диспетчеров. Forecast статичен
по expanding history на cutoff, общий для всех вариантов.

Envelope audit дал **20 feasible и четыре infeasible cells**. При .50/.70 N=113
работы с 1024 GPU / 128 nodes не помещаются в 904 GPU / 113 nodes. Нет строк
расписаний для этих ячеек, нет нулевых подставных метрик. Остальные сценарии
сохраняют source IDs, целевые denominators и observed carry-in; S общая внутри
variant/seed/origin. Точная матрица сохранена до replay.

## Результаты очередей

Выполнены **1080 расписаний**: 432/324/324 на трёх origins. Все targets завершились;
новые runtime caps не вводились. В таблице mean W контрольного replay с
записанными S, в секундах. Это не историческое ожидание Kalos.

| Allocation / N nodes | Origin .35 | Origin .50 | Origin .70 |
| --- | ---: | ---: | ---: |
| GPU pool / 302 | 0 | 0 | 0 |
| GPU pool / 226 | 0 | 0 | 0 |
| GPU pool / 151 | 0 | 0.300 | 0–2.757 |
| GPU pool / 113 | 0 | infeasible | infeasible |
| Exclusive nodes / 302 | 0 | 0 | 0 |
| Exclusive nodes / 226 | 0 | 0 | 0 |
| Exclusive nodes / 151 | 0.752 | 30.351 | 0–2.757 |
| Exclusive nodes / 113 | 24.301 | infeasible | infeasible |

Одиночное значение одинаково у всех шести policies; диапазон — min/max по policies.
В .70/N=151 FirstFit и MSF дают W=0, EASY и Conservative — 0.993 s,
FCFS и Adaptive Quickswap — 2.757 s в обеих allocation-моделях. Mean T различает
политики только в этих двух ячейках из 20: соответственно 2342.700, 2343.693
и 2345.457 s.
В остальных 18 ячейках все policies равны по mean T. По p99 T все равны
во всех 20 ячейках. Все **40 решений модели** (20×mean/p99) имеют regret=0,
но 38 из них используют полностью неразличающий reference. Это не свидетельство
точной модели или устойчивого преимущества дисциплины.

### Ошибка обслуживания и чувствительность к ресурсу

Ниже одинаковый срез на каждом origin: nominal GPU, половинный GPU и половинный
exclusive-node пул. Полная сетка, классовые метрики и интервалы есть в JSON.
Ошибка — среднее по шести policies от абсолютной относительной ошибки MC mean
соответствующей метрики против **observed той же ячейки**. Model mean W усреднено
по шести policies и восьми seeds. Origins не объединяются в независимые повторы.

| Origin | Allocation / N | Ошибка mean T, % | Ошибка p99 T, % | Model mean W, s |
| --- | --- | ---: | ---: | ---: |
| .35 | GPU / 302 | 103.37 | 58.28 | 14.62 |
| .35 | GPU / 151 | 1740.04 | 1147.21 | 14043.12 |
| .35 | Nodes / 151 | 1952.42 | 1163.11 | 15878.93 |
| .50 | GPU / 302 | 191.76 | 58.55 | 0.00 |
| .50 | GPU / 151 | 290.76 | 118.86 | 187.27 |
| .50 | Nodes / 151 | 435.47 | 174.12 | 620.66 |
| .70 | GPU / 302 | 377.85 | 570.70 | 8047.39 |
| .70 | GPU / 151 | 2311.62 | 2499.13 | 53388.14 |
| .70 | Nodes / 151 | 2311.63 | 2499.13 | 53388.30 |

Пример парного resource contrast: у FirstFit в .70 переход с nominal GPU/302
на GPU/151 повышает model mean T на **28159.00 s**, условный 95% CI
[17940.38, 38377.61]. В observed replay изменение mean T равно **нулю**.
Это разница ресурсов при одной модели и общих seeds, не CI ошибки относительно
истории и не оценка реальных квот. Пример показывает, что точности S недостаточно
оценивать без последствий для очереди. Уменьшение capacity не исправляет
автоматически чрезмерное ожидание генератора.

Исходный requested GPU work сохраняется между resource cells при одной service
ленте; node reservation учитывается отдельно. Ненулевые reservation violations
EASY/Conservative означают нарушение прогнозных обещаний, а не превышение
физического ограничения данного сценария. Аудит ресурсных интегралов и полное
дренирование проверены отдельно от качества прогнозов.

## Проверки и ограничения

В библиотеку добавлены `ResourceRequest`, `assess_envelope`, `observed_occupancy`.
Симуляторы и диспетчеры не менялись. Offline-тесты проверяют целочисленные
requests, невозможные running sets, atomic end/start, независимые интегралы,
малый аналитический пример exclusive-node ожидания, nominal-regression и
воспроизводимость последовательного/параллельного replay. Никаких данных
скачивать для тестов не требуется.

Первый полный запуск на восьми worker и повтор на шести дали побайтово одинаковые
пять JSON-файлов, включая manifest. Проверены hashes исходника, 16 файлов
реализации и четырёх файлов результатов. Отдельный аудитор заново построил
180 cell-specific service лент, пересчитал все **120 observed расписаний**,
проверил 1080 строк, 1200 модельных интервалов, 720 парных/детерминированных
контрастов, 40 решений и четыре infeasible cells. Он не использует новый runner
или fit helper, но использует те же диспетчеры; это не независимая реализация
планировщика.

Добавлено **55 offline-тестов**. Финальные проверки: полный pytest — **1632 passed**,
быстрый — **1623 passed**, оба с 16 прежними warnings. На предварительном полном
прогоне старый стохастический `test_m_h2_h2warm` дал AssertionError; отдельный
повтор и последующий полный прогон прошли без изменения теста/допусков.
Pylint новых библиотечного модуля и runner — 10/10, всей библиотеки — 9.98/10
с прежними замечаниями; форматирование и pre-commit проходят.
Независимая reader-проверка уточнила протокол единиц и выбора до расчётов,
затем сверила итоговые числа с JSON; в частности, исправлено описание
промежуточных EASY/Conservative в .70/N=151. Финальная проверка пройдена.

Снимок частичен; CPU-only и неизвестные окончания отсутствуют в GPU-популяции.
Предположение неизменного S при смене ресурса не моделирует CPU/memory/I/O
contention. Ресурсные сценарии не идентифицируют production scheduler,
preemption, retries или quotas. Conditional MC CI не оценивает неизвестную
реальную capacity. При tied observed policies zero regret не подтверждает
правильность выбора дисциплины.

## Продолжение

Реальная реконструкция quotas/placement/variable capacity требует новых данных,
а не подгонки N к уже просмотренному W. Следующий эпик калибровки — выбор модели
по раннему replay с отдельной временной проверкой (queue-aware selection), с
обязательными coarse baseline и учётом class coverage. Новая адаптивная дисциплина
не должна выбираться по неразличающему nominal-pool контролю.
