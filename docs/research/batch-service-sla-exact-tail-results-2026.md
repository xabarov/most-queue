# Точная вероятность нарушения SLA для batch-service очередей: результаты

Дата: 2026-10-05. [Эпик](../epics/EPIC-066-batch-service-sla-exact-tail.md),
[обзор литературы](batch-service-sla-exact-tail-2026.md),
[roadmap](../roadmaps/batch_service_sla_exact_tail_roadmap.md),
[артефакты](../../works/batch_service_sla_exact_tail/README.md).

**Итог:** для `M/PH^[a,b]/1` (a=1) получена и проверена точная (не подогнанная,
не оценка сверху) `P(W>D)`/CDF через матрично-экспоненциальное действие на
сужённом phase-type подгенераторе — для Erlang (последовательная цепь) и для
H2 (ветвящаяся цепь, каждый следующий полный батч заново выбирает фазу).
Численное сравнение с (а) закрытой оценкой сверху Inoue (2021) для `E[W]` и
(б) приближением SLA-слоя `fit_from_moments` показывает: ограниченное окно
`[1,b_max]` может сделать истинную `E[W]` ВЫШЕ оценки Inoue (рассчитанной для
неограниченного батча) в разы; приближение по моментам переоценивает
`P(W>D)` в глубоком хвосте на порядки.

## Точность: регрессия и независимая DES-проверка

| Калькулятор | Регрессия (k=1 / p1=1 → BulkServiceMM1Calc) | DES-проверка (batch-size-dependent, CV≠1) |
| --- | --- | --- |
| `BulkServiceMM1Calc.get_tail` | точное совпадение с `mm1_deadline_violation_prob` (разница ~1e-16) | a=1,b=4, batch-size-dependent `mu`: все точки в пределах MC-погрешности (включая глубокий хвост, где DES даёт 0 событий из 3М выборок, а точный результат — 1e-5) |
| `BulkServiceErlangCalc.get_tail` | точное совпадение с `BulkServiceMM1Calc.get_tail` при k=1 | a=1,b=3,k=3: все точки в пределах MC-погрешности |
| `BulkServiceH2Calc.get_tail` | точное совпадение с `BulkServiceMM1Calc.get_tail` при p1=1 (невозможная вторая фаза) | a=1,b=3, ветвящийся H2: все точки в пределах MC-погрешности |

19 новых юнит-тестов (`tests/units/test_bulk_service_tail.py`,
`test_bulk_service_erlang_tail.py`, `test_bulk_service_h2_tail.py`), включая
монотонность хвоста, `get_cdf=1-get_tail`, граничное условие
`get_tail(0)=1-P(простой)` и отказ при `a>1`/отрицательном `t`.

**Инженерная находка:** первая реализация через плотную `scipy.linalg.expm`
оказалась практически непригодной (57 секунд на один вызов при
`queue_truncation=500`); переход на `scipy.sparse.linalg.expm_multiply`
(действие матричной экспоненты на вектор, без явного построения плотной
экспоненты) дал то же самое значение за 0.19 секунды — ускорение ~300×,
решающее для практического использования при реалистичном `queue_truncation`.

## Сравнение с Inoue (2021): во сколько раз ограниченное окно меняет `E[W]`

Общая функция среднего `H^[b]=αb+τ0` (`α=0.1438, τ0=1.8874` — fit Inoue из
Table 1(a)/Fig. 9 для Tesla V100 ResNet50), `λ=0.8` (устойчиво при любом
`b_max≥2`: максимальная пропускная способность при `b_max=2` — `2/(2α+τ0)≈0.92`).
Оценка Inoue (Theorem 2, неограниченный батч, детерминированное время):
**`φ(λ,α,τ0) = 3.353`**.

| `b_max` | Точное `E[W]`, Erlang (CV=0.316, низкая variance) | Точное `E[W]`, H2 (CV=2.0, высокая variance) |
| --- | ---: | ---: |
| 2 | **5.005** | **35.064** |
| 4 | 1.196 | 7.796 |
| 8 | 1.074 | 5.640 |
| 16 | 1.073 | 5.217 |
| 32 | 1.073 | 5.199 |
| 64 | 1.073 | 5.213 |
| 128 | 1.073 | 5.216 |

При малом `b_max` (реалистичном для памяти GPU) истинная `E[W]` **превышает**
оценку сверху Inoue — несмотря на то, что это именно upper bound, выведенный
для идеализированного неограниченного батча: граница просто не покрывает
режим ограниченного окна, для которого она не выводилась. При CV=2 (разумная
изменчивость для смешанных по длине LLM-запросов в батче) расхождение при
`b_max=2` — почти **10×**. При большом `b_max` (сходится к неограниченному
случаю Inoue) точное значение остаётся ниже 3.353 — граница корректна именно
там, где она и была выведена, но не сигнализирует о своей неприменимости при
малом `b_max`.

## Сравнение с приближением SLA-слоя (`fit_from_moments`)

Erlang (CV=0.316), те же `λ,α,τ0`, `b_max` ∈ {2,4,8,...,128}; `D` — порог SLA.

| `b_max` | `D` | Точная `P(W>D)` | Подогнанная (fit, 2 момента) | Относительная ошибка |
| --- | ---: | ---: | ---: | ---: |
| 2 | 5 | 3.7035e-01 | 3.7107e-01 | +0.19% |
| 2 | 10 | 1.3255e-01 | 1.3331e-01 | +0.57% |
| 2 | 20 | 1.6981e-02 | 1.6906e-02 | −0.44% |
| 8 | 5 | 2.7386e-04 | 2.5296e-03 | **+824%** |
| 8 | 10 | 5.6797e-09 | 2.4628e-06 | **+43 261%** |
| 8 | 20 | 3.3642e-18 | 1.6570e-12 | **+4.93×10⁷%** |
| 16 | 5 | 2.4137e-04 | 2.5019e-03 | **+937%** |
| 16 | 10 | 1.0582e-09 | 2.4014e-06 | **+226 833%** |
| 16 | 20 | 5.7739e-19 | 1.5685e-12 | **+2.72×10⁸%** |

При умеренной загрузке у `b_max=2` (где хвост ещё не экстремально глубок
относительно среднего) подгонка по двум моментам работает неплохо (ошибка
<1%). Но при большем `b_max` — там, где `E[W]` мало, а запрошенный дедлайн `D`
уходит в ДЕЙСТВИТЕЛЬНО глубокий хвост (во много раз больше среднего) — подгонка
по моментам **систематически и drastически переоценивает** вероятность
нарушения SLA: на порядки, иногда на много порядков. Это ожидаемо (двумоментная
подгонка не обязана верно воспроизводить форму ДАЛЁКОГО хвоста), но здесь это
впервые количественно показано для batch-size-dependent batch-service очереди
именно в режиме, релевантном GPU/LLM SLA (нечастое, но некритично редкое
нарушение SLA — типичная цель операторов, например `P(TTFT>SLA)<0.1%`).

## Ограничения

Сравнение — контролируемое численное исследование на синтетических
параметрах (из fit Inoue для ResNet50-инференса, не из LLM-трассы
напрямую), не replay реальной LLM-трассы. `a=1` (резерв `a>1` не реализован,
см. roadmap). H2-случай сравнивался с Inoue только по `E[W]` (fit-сравнение
по `P(W>D)` выполнено только для Erlang-случая в этом отчёте). Оценка Inoue
сама по себе явно помечена её автором как upper bound, не точное значение —
наше наблюдение («граница может быть ниже истинного `E[W]` при малом
`b_max`») не противоречит математике Inoue (граница доказана для
`b_max=∞`), а указывает на риск её неверного применения к ограниченному
случаю без дополнительной проверки.
