# Приоритеты с гетерогенными серверами: обзор литературы и gap-анализ (2026-09)

- **Дата:** 2026-09-29
- **Источники:** OpenAlex, Crossref (скилл `lit-search`: priority queue heterogeneous servers
  preemptive two classes, M/M/2 heterogeneous servers priority) + инвентаризация кода
- **Эпик по итогам:** [EPIC-025](../epics/EPIC-025-priority-heterogeneous-servers.md)

Прямое продолжение техники EPIC-023 (расщепление состояния по занятому ремонтнику) в новом
контексте — приоритетная СМО вместо надёжности. Направление всплыло как альтернатива
queueing-inventory при выборе EPIC-024 и было отложено; сейчас реализуется.

## 1. Что есть в most_queue сейчас

Приоритетный стек огромен (`docs/models/priority.md`, `priority-dynamic.md`), но **все**
многоканальные точные/RDR-модели (`MMkPriorityExact`, `RDRAPriorityCalc`, `MPhPhK2Class`,
`RDRAPriorityPH`) предполагают **гомогенные** серверы — состояние описывается только числом
заявок каждого класса `(n_1,...,n_m)`, т.к. при одинаковой скорости обслуживания неважно, какой
именно из k серверов занят. `MachineRepairHeterogeneousCalc` (EPIC-023) впервые ввёл в библиотеку
технику для **разных** скоростей — но без приоритетных классов (там расщепление нужно только
из-за неоднородности ремонтников, а не из-за конкуренции классов заявок).

**Пробел:** приоритетные классы **и** гетерогенные серверы одновременно — нужна техника,
объединяющая оба усложнения.

## 2. Литература

- Kella O., Yechiali U., *On a Preemptive Markovian Queue with Multiple Servers and Two Priority
  Classes*, Mathematics of Operations Research, 1992, doi:10.1287/moor.17.2.365 — 50 цит.,
  базовая работа по многоканальным 2-приоритетным Марковским системам (отправная точка постановки
  задачи, хотя не всегда именно про гетерогенные серверы — проверить в деталях при написании).
- *Analysis of a Pre-Emptive Two-Priority Queuing System with Impatient Customers and
  Heterogeneous Servers*, Mathematics, 2023, doi:10.3390/math11183878 — 11 цит., **прямое
  совпадение постановки**: 2 приоритетных класса, преимущественный (preemptive) приоритет,
  гетерогенные серверы. Ближайший первоисточник для EPIC-025 (без нетерпения в первой волне —
  резерв).
- *Multi-server accumulating priority queues with heterogeneous servers*, European Journal of
  Operational Research, 2016, doi:10.1016/j.ejor.2016.02.010 — 35 цит. — стык с APQ (EPIC-020),
  подтверждает живость темы «гетерогенные серверы + приоритеты» за пределами чистого preemptive.
- *Priority Multi-Server Queueing System with Heterogeneous Customers*, Mathematics, 2020,
  doi:10.3390/math8091501 — 26 цит. (заявки, а не серверы, гетерогенны — смежная, не совпадающая
  постановка, но подтверждает активность семейства тем).
- Krishnamoorthi B., *On Poisson Queue with Two Heterogeneous Servers*, Operations Research, 1963,
  doi:10.1287/opre.11.3.321 — техника расщепления состояния при `n=1`, уже применённая в EPIC-023
  и переиспользуемая здесь в более общем виде.
- *Analysis of MAP/PH₁,PH₂/2 Queueing System with Two Types of Heterogeneous Servers, Standby
  Server*, 2022, doi:10.1504/ijsom.2022.10047837 — подтверждает продолжающийся интерес к парам
  гетерогенных серверов с усложнениями.

## 3. Что реализуемо точно

Ровно 2 сервера (скорости `mu_a >= mu_b`), 2 класса приоритета (класс 0 — высший, preemptive),
экспоненциальное обслуживание. Дисциплина: **preemptive, без миграции уже обслуживаемых заявок**
(«sticky» — заявка в обслуживании не переезжает на другой сервер, даже если освобождается более
быстрый) и **«занимай простаивающий сервер, вытесняй только при необходимости»** (простаивающий
сервер приоритетнее вытеснения уже занятого).

Ключевое наблюдение — при экспоненциальном обслуживании марковское состояние `(n_0, n_1)` **почти**
достаточно (как и для гомогенного случая в `MMkPriorityExact`), но не совсем: при `n_0=1` (или
`n_0=0, n_1=1`) неоднозначно, **какой именно** сервер занят — а от этого зависит скорость
(`mu_a` или `mu_b`). Ровно та же проблема, что у EPIC-023, только точек неоднозначности больше
(не одна, а вся «граница» `n_0∈{0,1}`).

**Решение** — не выводить вручную все переходы (риск ошибки при таком ветвлении), а построить
цепь **программно** через две примитивные операции, к которым сводится любое событие:
- `canonicalize(n_0, n_1, a_class, b_class)` — по «сырому» присвоению серверов (после события,
  возможно, с одним простаивающим слотом) находит канонический `(n_0, n_1, config)`, заполняя
  простаивающий сервер из очереди в порядке приоритета (класс 0 первым).
- `class0_arrival` / `class1_arrival` / `departure(server)` — каждая берёт текущее «сырое»
  присвоение, применяет своё элементарное действие (взять свободный сервер; вытеснить сервер с
  классом 1, если своих свободных нет и класс — 0; освободить сервер) и вызывает `canonicalize`.

Это даёт полный список переходов усечённой (по `n_0`, `n_1`) CTMC механически, без риска
транскрипции. Решается уже готовой `theory/reliability/utils.py::ctmc_stationary` (переиспользуем
инструмент из EPIC-023), либо разреженной степенной итерацией по образцу `MMkPriorityExact` при
больших усечениях.

**Точная редукция-регрессия:** при `mu_a = mu_b` результат обязан **точно** совпасть с уже
существующим `MMkPriorityExact(n=2, ...)` (гомогенный эталон) — сильнейшая проверка корректности
построения цепи.

## 4. Gap-анализ и решение

| Направление | Активность | В most-queue | Реализуемо точно? |
|---|---|---|---|
| M/M/2, 2 приоритетных класса, preemptive, гетерогенные серверы | подтверждена (11–50 цит. на прямых первоисточниках) | нет | да — усечённая CTMC, программное построение переходов, редукция к `MMkPriorityExact` |
| То же + нетерпение (impatience) | подтверждена (прямой первоисточник 2023 её включает) | нет | резерв — добавляет ещё одно измерение состояния (кто ушёл) |
| Accumulating priority + гетерогенные серверы | подтверждена (EJOR 2016, 35 цит.) | нет (EPIC-020 APQ — только гомогенные) | резерв — другая техника (накопление кредита), не CTMC-расщепление |
| k>2 гетерогенных сервера | — | нет | резерв — комбинаторный взрыв конфигураций, как и в EPIC-023 |

**Решение:** реализовать базовый случай (2 сервера, 2 класса, preemptive, без нетерпения) — см.
[EPIC-025](../epics/EPIC-025-priority-heterogeneous-servers.md). Нетерпение, APQ-версия и k>2 —
в резерве.
