# Проверка калибровки на Acme Kalos

В [EPIC-058](../epics/EPIC-058-modern-gpu-trace-validation.md) выполнено
1224 расписания и полный побайтово идентичный повтор. Современная трасса выявила
две разные границы применимости. Derived `duration` содержит ожидание и не может
служить входным S без проверки. А при номинальной ёмкости 2416 GPU контрольный
replay даёт нулевое ожидание целей для всех шести дисциплин: **сравнить качество
их выбора по этим сценариям нельзя**, хотя ошибки моделей длительности велики.

Нулевая ошибка выбора здесь не является успехом предиктора. Уменьшение capacity
или искусственное ускорение приходов после просмотра результатов не выполнялось.
[Методика](../modern_gpu_trace.md), [артефакты](../../works/modern_gpu_trace/README.md),
[manifest](../../works/modern_gpu_trace/manifest.json).

## Источник и проверка значений

Официальный [AcmeTrace](https://github.com/InternLM/AcmeTrace/tree/f9fdf591b4876c2875a9e3d28adb1bda8120dfcb)
Shanghai AI Laboratory, Hu et al., [NSDI 2024](https://www.usenix.org/conference/nsdi24/presentation/hu),
файл Kalos с SHA-256 `7c5a7845da1d66448fa668342e4ecb622fd9a005118080660ec3ad2788d4c9bf`.
[Лицензия CC-BY-4.0](https://github.com/InternLM/AcmeTrace/blob/f9fdf591b4876c2875a9e3d28adb1bda8120dfcb/LICENSE.txt);
исходные строки не переиздаются в репозитории Most-Queue. Изменения данных
ограничены явно описанной селекцией и вычислением end-start для replay.

Измеренное покрытие файла по submit: 17 мая — 16 августа 2023, 62 413 строк.
Это не весь шестимесячный период обоих кластеров из статьи и не 2026 production.
Timestamp с timezone переводятся в секунды UTC. Точный source/schema audit
сохранён в manifest, не заимствован из округлённых чисел публикации.

| Взаимоисключающая категория | Число строк |
| --- | ---: |
| Принятые COMPLETED GPU | 10 762 |
| Принятые CANCELLED GPU | 1240 |
| Принятые FAILED GPU | 7900 |
| CPU-only | 42 506 |
| GPU с нулевым end-start | 2 |
| RUNNING GPU без конечного исхода | 3 |
| Всего | 62 413 |

Из 62 410 закрытых строк у всех `duration = end − submit`, а у 62 409
`duration != end − start`. `queue` согласуется с start-submit во всех 62 413.
Все 19 904 заполненных `gpu_time` закрытых GPU-строк отличаются от
K × (end-start), включая два нулевых интервала. Использование этих derived
полей как ресурса ошибочно добавляло бы ожидание к обслуживанию.

Для 19 902 принятых GPU-интервалов, K × (end-start) составило:

| Исход | GPU-request-seconds | Доля |
| --- | ---: | ---: |
| completed | 1 655 502 814 | 31.88% |
| cancelled | 3 207 237 382 | 61.76% |
| failed | 329 916 198 | 6.35% |

Это занятость **по модели резервирования запроса**, не фактические GPU cycles.
Пик суммы K по историческим [start,end) — 1536. Он не восстанавливает квоты или
доступную ёмкость: постоянные 2416 взяты из
[описания авторов](https://www.usenix.org/publications/loginonline/understanding-workload-characteristics-large-language-model-development)
как номинальное допущение. CPU, память, топология, конкуренция за сеть и
приоритеты не моделируются. Нельзя заключить, что реальный кластер недогружен.

По всем пригодным completed GPU mean S = 893.31 s, p99 S = 5443.62 s,
CV² = 112.73. Это характеристика конечной выбранной выборки; не доказательство
конкретного хвостового закона или стационарности.

## Протокол и временное покрытие

После аудита количества записей, до измерения задержек зафиксированы .35/.45/.50/.55
raw submit span. Прежние .65/.80 не дают 1200 completed GPU jobs. У каждого origin
train содержит только completed с end < cutoff, recent — последние не более
4000 таких работ в submit-порядке. Первые 1200 eligible completed с submit >= cutoff
дают 200 прогрева и 1000 целей. Порядок ties сохраняется из CSV.

| f | Cutoff UTC | Train / recent | Первый выбранный submit UTC | Первый target UTC | Последний target UTC |
| --- | --- | ---: | --- | --- | --- |
| .35 | 06-18 08:54:56.4 | 1500 / 1500 | 06-18 09:33:40 | 06-20 12:10:00 | 06-26 13:30:30 |
| .45 | 06-27 11:44:38.8 | 3060 / 3060 | 06-27 12:47:14 | 06-29 08:52:46 | 06-30 13:19:03 |
| .50 | 07-02 01:09:30 | 4955 / 4000 | 07-02 03:34:10 | 07-03 05:17:26 | 07-04 09:50:52 |
| .55 | 07-06 14:34:21.2 | 8862 / 4000 | 07-07 07:06:54 | 07-12 04:02:08 | 07-18 00:53:10 |

Все даты — 2023 год. Блоки не перекрываются, истории пересекаются. Выборка
покрывает активную часть июня–июля, но не августовский хвост. В первых двух
origin expanding и recent имеют одну историю, поэтому их результаты **точно
совпадают**, а не являются двумя независимыми подтверждениями.

Модель S — iid empirical CDF по K-группам 1/2–8/9–32/>=33, с pooled fallback
при n < 20. Forecast — общий expanding p90. Seeds 58000–58007, одна uniform-лента
для выбранных ID при одинаковом seed/cutoff. Без test-S нормировки, подбора
capacity, нового распределения или нового планировщика.

Сценарии: empty completed; completed с начальным состоянием; все пригодные
terminal competitors с начальным состоянием. В последнем случае:

| f | Running / waiting | Начальный K | Новые cancelled / failed |
| --- | ---: | ---: | ---: |
| .35 | 1 / 0 | 256 | 230 / 1012 |
| .45 | 1 / 0 | 512 | 88 / 3009 |
| .50 | 4 / 0 | 624 | 65 / 862 |
| .55 | 0 / 0 | 0 | 274 / 481 |

В completed-only carry running составили 0/1/1/0 с K 0/512/96/0; начальных
waiting нет. Поэтому данный источник **не проверяет эффект начальной очереди
ожидающих**, хотя API и synthetic-тесты её поддерживают. Initial running
использует исторический остаток, waiting/new terminal — исходное S после нового
старта: явная service-clock чувствительность, не модель времени аварий/отмен.
Budgets отсутствуют; TIMEOUT/NODE_FAIL в этом файле не встречаются.

## Контроль не различает дисциплины

В 72 observed расписаниях (4 × 3 × 6) mean W целей = 0. Mean T и p99 T
совпадают между всеми политиками и сценариями для данного origin:

| f | Mean T, s | p99 T, s | Utilization empty | Utilization carry terminal |
| --- | ---: | ---: | ---: | ---: |
| .35 | 857.138 | 5728.10 | 6.15% | 19.22% |
| .45 | 292.563 | 2559.17 | 16.49% | 41.97% |
| .50 | 187.986 | 2229.15 | 8.15% | 36.89% |
| .55 | 1119.758 | 4967.65 | 11.83% | 41.55% |

Utilization интегрирует модельное резервирование на интервале target-arrivals,
не drain и не аппаратную загрузку. Добавление terminal-нагрузки повышает эту
занятость, но не создаёт очередь целей в контроле. Carry completed не меняет
T/W целей ни у observed, ни у моделей в этих периодах; часть начального ресурса
может влиять на ledger/utilization без влияния на задержку.

В исходном журнале у **всех 4000 target-ID ожидание положительное**; по периодам
его средние равны 768.230 / 19.980 / 30.048 / 544.751 s. Это дополнительная
описательная проверка, не целевая метрика fit. Она подчёркивает разрыв между
журналом и моделью общего пула. Из него нельзя выделить вклад квот, priorities,
CPU/memory или накладных расходов запуска без новых наблюдений.

Все observed policies равноправно лучшие по mean/p99. `reference_best=fcfs` —
только правило разрешения точного равенства. В carry_terminal модели иногда
выбирают FirstFit вместо FCFS, но regret остаётся 0: иной выбор не является
ошибкой при равных контрольных задержках. Счётчик совпавших названий (2/4 либо
3/4) здесь нельзя использовать как accuracy выбора.

## Ошибки эмпирических моделей остаются большими

MAPE ниже — модуль ошибки **MC-среднего** относительно observed того же сценария,
усреднённый по 4 origins × 6 policies. Сценарии и модели между собой не смешаны.

| Сценарий | Модель | MAPE mean T | MAPE p99 T |
| --- | --- | ---: | ---: |
| empty completed | expanding | 158.34% | 38.03% |
| empty completed | recent | 148.69% | 47.93% |
| carry completed | expanding | 158.34% | 38.03% |
| carry completed | recent | 148.69% | 47.93% |
| carry terminal | expanding | 196.77% | 62.26% |
| carry terminal | recent | 187.96% | 74.27% |

Recent немного снижает агрегированную ошибку mean T, но ухудшает p99. Это не
устойчивое преимущество: empty .50 модуль относительной ошибки mean T уменьшается 284.02% → 216.82%,
а .55 увеличивается 57.51% → 86.11%. В двух ранних периодах модели одинаковы.
Нельзя переносить вывод EPIC-056 «recent лучше в агрегате» на все метрики
и периоды нового источника.

У .45 модель иногда создаёт очередь, которой нет в recorded-S контроле.
В carry_terminal FCFS обе модели дают mean T = 1861.15 s, условный 95% t-интервал
[−71.07, 3793.36] s, против observed 292.56 s. Негативная нижняя граница —
свойство симметричного t-интервала по восьми seed, не отрицательное время.
Интервал не обрезается и не выдаётся за точный доверительный интервал
производственного latency. MC mean W этого случая = 906.16 s.

Интервалы описывают только генерацию S при фиксированных source/history/environment.
Неопределённость capacity, quota, lifecycle, выборки и причин остановки не покрыта.
Снижение ошибки отдельной модели после добавления окружения также не означает
улучшения её fit: history и сгенерированные target S не меняются между сценариями.

## Проверки и воспроизводимость

Все четыре origin JSON и manifest совпали побайтно при полном повторе.
Manifest фиксирует Python/NumPy/SciPy, 14 implementation hashes и исходный hash.
Независимый [аудитор](../../works/modern_gpu_trace/audit.py) не вызывает адаптер,
генератор или функции метрик эксперимента. Он повторно разбирает CSV и строит
empirical inverse CDF, проверяет 204 ленты, все 1224 строки, 1296 MC-интервалов,
144 детерминированные разности, 48 решений и все агрегаты.

72 observed replay дополнительно проверены по start/release, отсутствию старта
до arrival, capacity, отдельно интегрированным utilization/idle и ledger исходов.
408 empty-state строк точно совпадают с обычным `MsjGeneralSim.run_trace`.
Аудитор использует те же диспетчеры: это независимая проверка входов, метрик
и интерфейсной совместимости, не вторая реализация scheduling algorithms.

Добавлены 60 offline-тестов; вместе с EPIC-057 — 126 профильных проверок.
Новый adapter/experiment и расширенный lifecycle проходят black/isort/pylint.
Полный pylint пакета сохраняет 43 прежних замечания без новых. Полный pytest:
**1518 passed** (536.69 s), быстрый: **1509 passed** (268.31 s), по 16 прежних
предупреждений. Pre-commit пройден. Независимый читатель подтвердил численности,
таблицы, исторические ожидания, hashes и ограниченную трактовку результатов;
замечания о часовых поясах и модулях ошибок исправлены.

## Что делать дальше

1. Перед новым сравнением дисциплин установить эффективную доступную capacity,
   правила квот/priority и ресурсные ограничения. Без данных допустим только
   отдельно объявленный sensitivity experiment, не подбор «реальной» ёмкости
   по будущим задержкам. Этот результат — проверка границы модели, не повод
   приписать успех FCFS или FirstFit.
2. Следующий запланированный эпик — условная/совместная модель S, K,
   requested_time и доступных признаков приложения с временным holdout.
   Requested_time есть в SDSC, но отсутствует в Kalos: не объединять эти признаки
   как будто они наблюдались в обоих источниках. Для Kalos отдельно проверить
   доступный `type` и неоднородность длительностей по назначению работ.
3. Остановленные работы требуют отдельной модели lifecycle и censoring, а не
   включения времени до отказа в обучение успешного S. Их высокая доля ресурса
   делает completed-only анализ неполным даже при нулевой очереди целей.

Новый современный источник подключён и проверен. Универсальное преимущество
recent history, какого-либо закона обслуживания или дисциплины не установлено.
