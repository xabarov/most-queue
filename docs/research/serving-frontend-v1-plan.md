# План измерения задержек frontend и повторяемости TTFT

Дата: 14.11.2026. Подготовлен новый диагностический цикл на одной A40.
**Платный запуск ожидает отдельного разрешения.** Предыдущие циклы закрыты;
их расходы и журналы сохраняются. Подготовка этого этапа выполняется локально.

## Цель и ожидаемый результат

[Разбор v2](serving-slo-v2-diagnostics.md) показал недооценку внешней добавки
у всех ложных успехов потоковых серий при TTFT 250 мс / TPOT 35 мс. В выбранных
29 случаях медиана недооценки — 24,678 мс; обычное серверное ожидание — 7–25 мкс.
Однако точное место задержки до очереди движка не наблюдалось. Кроме того,
одиночный серверный TTFT 128/32 имел только один повтор, а при большой нагрузке
ошибка ожидания могла накапливаться.

Этот опыт должен дать три результата:

1. Разделить путь до движка на наблюдаемые интервалы и установить, в каких
   интервалах возникает различие между пустым и занятым движком.
2. Получить повторы одинаковых коротких запросов и оценить наблюдаемый разброс
   серверного и клиентского TTFT, включая неудачные исходы у заданных порогов.
3. Проверить влияние инструментовки и сохранить новые потоковые трассы для
   разбора накопления ошибки очереди и времени генерации.

Результатом станет измерительный отчёт с исходными данными и ограничениями.
Калибровка новой модели в этот цикл не входит. Все новые строки имеют
`split=diagnostic`, кроме прогрева; они не являются заранее закрытой
проверочной выборкой модели v3. После использования этих данных для выбора
уточнения потребуется новая проверочная выборка. Исторические результаты v2
продолжают относиться к неизменной модели и её исходному плану. Старый
адаптер v2 не ослабляется для нового `split`: диагностические данные требуют
отдельного анализа с сохранением этой роли.

## Состав выборки

**613 запросов, 108 серий: 4 прогревочных и 609 диагностических.**
Из них 533 запроса с frontend-трассировкой и 80 без неё.

| Семейство | Число запросов | Содержание |
|---|---:|---|
| Прогрев | 4 | Вход/выход 128/32, 1024/32, 4096/32, 1024/512; трассировка включена |
| Пары при пустом движке | 80 | В каждом из двух блоков по 10 пар для входа 128 и 1024, выход 32 |
| Пары на фоне генерации | 60 | 20 фонов по 1024/512 и 40 коротких проб; по 5 пар на длину в каждом блоке |
| Потоковые серии | 469 | Четыре серии по 180 с, вход/выход 1024/128, интенсивности 0,5 и 0,8 |

В каждой паре один запрос идёт с frontend-трассировкой, другой без неё.
Их порядок определяется фиксированным генератором до опыта; пары разных длин
перемешаны. Для каждой входной длины используется один и тот же синтетический
prompt, seed равен `2026111404 + input_tokens`. Между on/off запросами меняется
идентификатор, но token IDs и остальные параметры генерации совпадают.
Prefix caching выключен. Повторяемый prompt здесь нужен для сравнения одинаковой
работы; переносимость результата на разнообразные тексты не заявляется.

Пустая пара — две отдельные последовательные серии; каждая полностью завершается
до следующей. Нагруженная пара — одна серия: фон запускается в момент 0,
две пробы с выходом 32 токена назначены в моменты **1,5 и 5,5 с**.
Сроки не подстраиваются под наблюдения. Для допустимого сравнения фон должен
уже выдать первый токен до клиентского старта каждой пробы и ещё не завершиться
до её входа в очередь; первая проба должна завершить генерацию до старта второй.
Несоблюдение условия записывается как `condition_mismatch`, все строки
сохраняются. Исключать такие пары и выдавать оставшуюся выборку за полную нельзя.

| Блок | Seed приходов | Интенсивность, 1/с | Запросов |
|---|---:|---:|---:|
| a | 75101 | 0,5 | 91 |
| a | 75101 | 0,8 | 143 |
| b | 75102 | 0,8 | 148 |
| b | 75102 | 0,5 | 87 |

Приходы экспоненциальные, их точные смещения определены до опыта. Во втором
блоке порядок интенсивностей обращён. Все серии полностью завершаются перед
следующей. Блоки дают повторение опыта в одном pod, а не независимую выборку
машин. Порядок «пусто, фон, поток» внутри блока фиксирован; разницу между
условиями нельзя полностью отделить от времени работы и состояния оборудования.

## Новые часы и их смысл

[Frontend wrapper](../../tools/runpod_frontend_server.py) добавляет
[ASGI middleware и два наблюдающих hook](../../tools/runpod_frontend_trace.py).
Сохраняются монотонные отметки на том же host:

| Отметка | Наблюдаемое событие |
|---|---|
| `client_started_monotonic_s` | Прежнее начало клиентского TTFT после чтения payload дочерним worker |
| `client_json_ready_ts` | JSON для HTTP-запроса сериализован |
| `http_enter_ts` | Вход в добавленную ASGI middleware |
| `body_received_ts` | Получена последняя часть HTTP body |
| `handler_enter_ts` | Вход в `create_completion` после валидации FastAPI и маршрутизации |
| `render_enter_ts`, `render_exit_ts` | Вход и выход `render_completion_request`, включая его проверки и подготовку |
| `queued_ts` | Прежняя отметка входа запроса в очередь EngineCore |
| `scheduled_ts`, `first_token_ts`, `last_token_ts` | Прежние отметки назначения, первого и последнего токенов движка |
| `client_headers_received_ts` | Клиент получил HTTP response headers |
| `first_response_body_ts` | Отправка первого непустого ASGI body; это транспортное событие |

Клиентский первый токен по-прежнему определяется первым непустым текстом SSE,
TPOT — интервалом от него до DONE, делённым на число последующих токенов.
`first_response_body_ts` не подставляется вместо первого токена: body может
содержать служебное событие. Время запуска дочернего клиента сохраняется
отдельно от TTFT. Получение body не означает завершение разбора JSON;
интервал до `handler_enter_ts` включает разбор, валидацию, зависимости и
маршрутизацию. `render_exit_ts → queued_ts` включает оставшуюся подготовку,
создание генератора и передачу движку; он не измеряет работу GPU.

Девять последовательных интервалов от клиентского старта до первого текста
должны в сумме давать клиентский TTFT с допуском 1e−8 с. Разделение между
процессами предполагает общий монотонный отсчёт на host. Суммарная внешняя
добавка, вычисленная как разность длительностей, сохраняется дополнительно.

Новые логи содержат только синтетический `mqfront-N`, часы, статус и тип ошибки.
Middleware не читает и не копирует body, не меняет возвращаемые объекты и не
пишет на каждый токен. Frontend записывается один раз после HTTP response;
существующий engine trace записывается один раз на завершённый запрос.
Отсутствие заголовка `X-MQ-Trace-ID` включает контрольный режим без новых часов
и frontend-записи. Общие обёртки и прежний engine trace остаются и в контроле:
это измеряет добавочный эффект новых отметок, а не весь эффект относительно
полностью неизменённого бинарного сервера. Дополнительный заголовок также
входит в сравниваемое отличие.

Точки hook проверены по первоисточникам vLLM v0.32.0:
[completion serving](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/completion/serving.py),
[FastAPI router](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/openai/completion/api_router.py),
[регистрация middleware](https://github.com/vllm-project/vllm/blob/v0.32.0/vllm/entrypoints/serve/middleware/register.py).
Версия проверяется при запуске. Проверки с fake-классами выполнены локально;
первое реальное исполнение нового hook на GPU остаётся частью прогрева.

## Анализ определён до сбора данных

Сначала проверяется полнота, затем сравниваются интервалы и повторы.

- Для каждого блока, длины и условия: все значения TTFT, внешняя добавка,
  составляющие до движка, медиана, среднее, диапазон и межквартильный размах.
  Сохраняются prompt SHA256 и фактические длины.
- Для каждой on/off пары: разность клиентского и серверного TTFT, TPOT и внешней
  добавки. По каждой длине и условию объединяются оба блока, но различия блоков
  также показываются отдельно. Пары с нарушенным фоном не скрываются.
- Предупреждение о влиянии инструментовки срабатывает, если абсолютная медиана
  парной разности клиентского TTFT превышает `max(5 мс, 5% среднего off-TTFT)`.
  Такой исход ограничивает переносимость новых отметок на исходный профиль;
  он не является поводом повторять опыт до более удобного результата.
- Для четырёх потоковых серий: клиентские и серверные TTFT/TPOT, очередь,
  внешняя добавка и новые интервалы; ошибки неизменной v2 по точным серверным
  приходам. Показать все сочетания TTFT 250/500/1000 мс и TPOT 30/35/40 мс,
  ложные успехи и ложные отказы. Все предложения входят в знаменатель.
- Отдельно показать накопление расхождения очереди и времени генерации по порядку
  приходов и периодам непрерывной занятости. Совпадение средних не заменяет
  проверки отдельных составляющих.

Это описательные результаты при конечной выборке, без p99, стационарной ёмкости
и доверительных интервалов по запросам с предположением их независимости.
Никакой новый порог не подбирается после просмотра результатов. Прежде чем
обучать модель v3 по этим данным, нужно отдельно зафиксировать её правило
обучения и способ новой проверки.

## Полнота и причины остановки

[Исполнитель](../../tools/runpod_frontend_workload.py) сохраняет план, исходные
SSE, реальные предложения и отказы, engine/frontend trace, серии, `progress.json`,
summary и SHA256. Файлы новых опытов не смешиваются с v1/v2.
[Локальный аудитор](../../tools/audit_frontend_measurements.py) проверяет все
613 идентификаторов, 533 frontend-записи, 613 engine-записей, фактические длины,
согласованность часов, полные окна серий, завершение между сериями и наличие фона.
Неполные, ошибочные и неотправленные запросы сохраняются; они не превращаются
в успешную оценку точности отбрасыванием.

Ошибка контракта на прогреве прекращает измерения с выгрузкой и удалением pod.
У каждого запроса жёсткий срок до 120 с, одновременно до 64 клиентских запросов,
измерительная программа ограничена 2400 с. Контроллер ограничивает всю попытку,
ожидание инфраструктуры, загрузку, измерения и экспорт; фиксированные сроки
не продлеваются при ошибках API. Вторая попытка возможна только после разбора
технического сбоя, сохранения первой попытки и подтверждённого удаления,
в пределах общего бюджета. Неудачные диагностические результаты, большой
overhead или плохая точность модели не разрешают повтор для улучшения цифр.

## Бюджет и завершение

[Политика](../../configs/runpod/frontend-v1-policy.json): **до $5 и четырёх
GPU-часов суммарно, максимум два выделения, одна A40 одновременно**.
Compute ≤$0.75/ч, compute с диском ≤$0.77/ч. Container disk 80 GB,
persistent/network volumes запрещены. Подготовка, все попытки, экспорт и удаление
входят в общий учёт. Это управляющие пределы локального контроллера, а не
гарантированный предел списаний провайдера.

[Проверка каталога и бюджета](serving-frontend-v1-preflight.json) от 14.11.2026:
A40 Secure **$0.59/ч**, доступность **LOW**, диск оценивается в $0.011112/ч.
Активных pod Most-Queue при проверке нет. Ожидаемые 30–45 минут — примерно
**$0.30–0.45**. Консервативное окно работы 4500 с плюс резерв завершения 900 с
даёт **$0.901668 на попытку**; две такие попытки — $1.803336 и три часа.
Перед create цена, наличие, CUDA и остаток общего бюджета проверяются заново.
Текущая проверка отклоняет аренду из-за `authorized=false`; расчёт с разрешением
сохранён только как проекция и не разрешает трату.

Новый журнал после разрешения:
`~/.local/state/most-queue/runpod/serving-frontend-v1-2026-11-14/`.
Старые журналы не сбрасываются. Контроллер и detached watchdog запускаются
до платного create, точный ID записывается сразу после ответа. После нормального
конца, ошибки, Stop или срока — bounded export и terminate с последующим
свежим GET/inventory подтверждением отсутствия. Ни один pod не остаётся работать
во время ожидания решения пользователя.

Локальный watchdog переживает завершение агента, но не потерю всего host
или связи с провайдером. Для нового цикла требуется принять этот же остаточный
риск либо обеспечить отдельный независимый путь очистки. Здесь предложен прежний
согласованный режим локального watchdog; его принятие относится к разрешению
именно этого нового цикла. Оплата/auto-pay аккаунта не меняются.

## Команды и локальные проверки

Построение расписания без сети и GPU:

```bash
.venv/bin/python tools/runpod_frontend_workload.py --plan-only \
  --seed 2026111404 --config configs/runpod/frontend-v1-workload.json \
  > /tmp/frontend-v1-plan.json
```

После разрешения контроллер использует частную копию утверждённой политики
и тот же постоянный журнал; публичный файл остаётся `authorized=false`.
Команда ниже является только read-only проверкой и сама не создаёт GPU:

```bash
.venv/bin/python tools/runpod_pilot.py preflight \
  --policy configs/runpod/frontend-v1-policy.json \
  --profile configs/runpod/frontend-v1-profile.json \
  --state-dir ~/.local/state/most-queue/runpod/serving-frontend-v1-2026-11-14
```

Без разрешения она откажет в переходе к аренде. Команда `run` выполняется
с утверждённой частной политикой после сохранения разрешения; остальные аргументы
те же. Аудит выгруженных данных после удаления pod:

```bash
.venv/bin/python tools/audit_frontend_measurements.py \
  /path/to/export/measurements --output frontend-audit.json
```

Локально пройдены 198 целевых проверок на Python 3.10 и 3.12: прозрачность
middleware, конкурентные запросы, отмена, ошибки записи, точные пути импорта,
детерминированный план, жёсткое завершение worker, часы и полнота экспорта.
Полный прогон: **4276 passed**, 19 прежних предупреждений, 853,62 с.
Без `slow`: **4258 passed**, 19 предупреждений, 677,84 с. Оба используют
`.venv`, `-n 8`, `OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 PYTHONPATH=.`.
Black/isort и pylint новых файлов проходят, pylint — 10/10. Проверена копия
семи загружаемых файлов вне репозитория с удалёнными именами импортов;
расписание совпало. Python 3.10 и 3.12 дают побайтово одинаковый план.

Перед публикацией подготовки проверены локальные ссылки, JSON и отсутствие
секретов. Все 18 научных SHA256 прежнего v2 неизменны. Изменения инструментария
добавлены отдельными файлами; код `most_queue`, выпущенный пакет и тег v2.12
не менялись. Первая реальная GPU-проверка нового wrapper ещё не выполнялась.
