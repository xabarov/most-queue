# Символьная проверка перед численной

История эпиков most-queue (EPIC-035 k² в единицах, EPIC-039/041 ошибка расщепления исходящего
потока, EPIC-066 формула фазовых моментов) показывает общий паттерн: ошибка в ручном выводе CTMC
или момента чаще всего **алгебраическая**, но ловится только числовым сравнением с ИМ/DES --
дорого (нужен прогон на 10^5-10^6 заявок) и поздно (после того как код уже написан). SymPy ловит
тот же класс ошибок на этапе вывода формул, дёшево и раньше: строй генератор/момент из символов,
проверяй тождества символьно, и только потом подставляй числа.

## Когда применять

- Перед кодированием нового CTMC-варианта (новая ветка/тип обслуживания/нетерпение) -- построй
  генератор $Q$ на маленьком символьном примере ($b_{\max}=2$, 2 ветви и т.п.) и проверь его
  структурные свойства, не дожидаясь численного теста.
- При выводе точной формулы момента (через $(-A)^{-1}\mathbf{1}$, $2(-A)^{-2}\mathbf{1}$ и т.д.) --
  проверь на символьном $A$ малой размерности, что формула согласуется с прямым символьным решением
  $A\boldsymbol\pi=\mathbf{0}$ или с $\mathbb{E}[T]=\int_0^\infty t\,f(t)\,dt$ через `integrate`.
- При выводе тождества вида "баланс потоков" (например `eq:utilization` в
  `batch-service-sla-single`) -- проверь тождество на символьных параметрах, не только на
  числовом примере из таблицы.

## Базовый приём: генератор из символов + row-sum-to-zero

```python
from sympy import symbols, Matrix, simplify, zeros

lam, mu1, mu2, p1, gamma = symbols('lambda mu_1 mu_2 p_1 gamma', positive=True)

# Q строится ИЗ ТЕХ ЖЕ формул переходов, что и в Python-коде конструкции (не переписывай
# их "на глаз" -- копируй выражения интенсивностей, чтобы символьная модель была той же
# моделью, а не её пересказом).
Q = Matrix([
    [-(lam + mu1*p1 + mu1*(1-p1)), mu1*p1, mu1*(1-p1)],
    [lam, -(lam + mu1), 0],
    [0, mu2, -(lam + mu2)],
])

row_sums = simplify(Q * Matrix.ones(Q.shape[1], 1))
assert row_sums == zeros(Q.shape[0], 1), row_sums  # генератор обязан иметь нулевые суммы строк
```

Это именно тот тест, который словил реальный баг расщепления исходящего потока в EPIC-041 --
численный DES-тест заметил эффект только при нетривиальном $r_k>1$, а row-sum-to-zero ловит его
символьно и мгновенно, при любых значениях параметров сразу.

## Приём: вырожденный случай -- символьная подстановка, не числовая

Когда у конструкции есть известный вырожденный предел (b=1, k=1, p1=1, a=1, gamma=0 и т.п.),
подставляй его символьно в общую формулу и сравнивай с уже известным (более простым) точным
результатом через `simplify(general.subs(...) - known)` -- должно получиться `0` как объект,
а не "близко к нулю":

```python
general_P_sla = ...  # выражение из общего вывода, символьное
known_P_sla_b1 = ...  # формула для b_max=1, выведенная независимо (базовый случай EPIC-032)
assert simplify(general_P_sla.subs(b, 1) - known_P_sla_b1) == 0
```

Если `simplify(...)` не даёт `0`, но и не доказывает неравенство -- не считай это "наверное,
численная погрешность sympy": `simplify` работает точно над рациональными/символьными
выражениями, остаточное нетривиальное выражение значит, что формулы действительно разные.
Сначала разберись, в каком упрощении дело (попробуй `cancel`, `factor`, `trigsimp` по отдельности;
проверь, что `assumptions=` (`positive=True`/`real=True`) объявлены при создании символов, иначе
`sqrt`/`log`/ветви могут помешать), только потом признавай результат неоднозначным.

## Приём: численная сверка остаётся обязательной, но второй

Символьная проверка -- **не замена** DES/ИМ-сравнения (таблицы "расчёт vs ИМ" в статьях), а более
дешёвый и ранний первый фильтр. Символьная проверка подтверждает внутреннюю непротиворечивость
конструкции (генератор корректен, формула момента совпадает с альтернативным выводом); численная
сверка с независимым DES подтверждает, что сама модель отражает реальную систему. Нужны обе -- см.
`[[reference_epic_workflow]]` и раздел про регрессионные тождества в
`.claude/skills/queueing-articles/SKILL.md`.

## Практические ограничения

- Символьный генератор имеет смысл только для **малой** размерности состояния (вручную выписанные
  несколько состояний, не полный $b_{\max}=32$ случай) -- цель не пересчитать всю цепь символьно
  (SymPy на это не рассчитан, `Matrix.inv()` на большой символьной матрице практически не
  завершится), а проверить *локальный* кусок конструкции (один переход, одно тождество) который
  потом обобщается в Python на произвольный размер индуктивно/по шаблону.
- `solve`/`simplify` над выражениями без объявленных `positive=True`/`real=True` могут застрять в
  комплексной ветви или не упроститься -- всегда объявляй `lam, mu, ... = symbols('...', positive=True)`
  для интенсивностей и вероятностей, это и есть реальная область определения модели.
- Это инструмент проверки вывода, не замена чтения формулы глазами -- если результат неожиданный,
  сначала перепроверь, что символьная модель -- это действительно та же модель, что в Python/статье
  (одинаковые обозначения, одинаковый порядок состояний), а не паразитная опечатка при переносе.
